# OrbitScore Signal Chain DSL Specification v1

Status: 正本（specs-v2）/ 2026-07-18 制定 / 受け皿 issue: \#506 / 決定ログ: DESIGN_DISCUSSION_RECORD §15（決定 \#64–#77）+ 本文内の決定 \#78（`master` 予約・SC.2.1）/ 実装: \#495 言語サービスと同時設計（本仕様の制定時点では未実装）

<div class="warn">

**位置づけ**: 本仕様は `effect()` / `instrument()` / 文字列ルーティングの**表記と名前空間の刷新**である。 エンジン側のミキサーグラフ実体（MX 仕様のバス・ルーティング・LinkAudio ゲート）は不変。 audio シーケンスの `play()` 意味論は一切変更しない（運用規則5）。 既存の文字列形 API はすべて互換として存置する（§SC.8）。

## SC.0 全体像

    // ── ミキサー空間を init して派生させる
    var mix    = init global.mixer        // 卓そのもの
    var master = mix.output(1, 2)         // 物理アウト 1-2 = メイン
    var subout = mix.output(3, 4)         // 物理アウト 3-4（マルチアウト）
    var drums  = mix.sum                  // グループバス
    var verb   = mix.aux                  // センドリターン
    var duck   = mix.aux                  // サイドチェーン搬送も aux（役割は受け手が決める）

    // ── リターン側のチェーン（バスもシーケンスと同じ書式）
    verb.HogeReverb(size: 0.8).master

    // ── トラック
    kick.audio("kick.wav").chop(16).play(1, 5, 9, 13)
        .CLAPTestEffect(mix: 0.5)
        .HogeComp(threshold: -18, sidechain: duck)
        .verb(0.3)                        // aux 名 → send（位置 = プリ/ポスト）
        .FugaEQ(low: 2)
        .drums                            // sum 名 → 本流の出力先（宣言層・括弧なし）

    bass.audio("bass.wav").play(1, 9).duck(1.0).drums
    drums.GlueComp(ratio: 2).master
    lead.Serum(preset: "Pluck 01").TALReverb4(size: 0.6).subout

## SC.1 二層意味論 — 宣言は集合・信号は列

| 層 | 属するもの | 順序の意味 |
|----|----|----|
| **宣言層** | audio / chop / play / gain / pan / 出力先ノード名（括弧なし）/ instrument 役のプラグイン呼び出し / ミキサー宣言 | **可換**。どこに書いても同じ。同一項目の再宣言は後勝ち。 |
| **信号層** | effect 役のプラグイン呼び出し / send（aux 名メソッドを含む） | **この層内の相対順序だけ**が接続順になる。宣言層の文がどこに挟まっても影響しない。 |

<div class="norm">

**規範**: (1) チェーン1本と行分割呼び出しは完全等価（同一の評価列であるため）。 (2) トポロジーは構造で固定される: **パターン(play) → instrument → エフェクト列 → 出力先**。 利用者が順序で制御できるのはエフェクト列の中身と send の位置のみ。 (3) `play()` の意味論は本仕様の影響を受けない。

</div>

## SC.2 ミキサー宣言

### SC.2.1 mixer 空間とノード派生

    var mix = init global.mixer

| 派生宣言 | 意味 | 備考 |
|----|----|----|
| `var master = mix.output(1, 2)` | 物理出力チャンネル対（出力エンドポイント） | 複数宣言でマルチアウト。デバイス ch 数超過は起動/デバイス切替時に警告（#484 D4 と接続） |
| `var drums = mix.sum` | グループバス（合流点） | MX.2 の sum と同一実体 |
| `var verb = mix.aux` | センド用バス | MX.4 の aux と同一実体。サイドチェーン搬送も aux で行う（汎用 bus 型は設けない — 決定 \#74） |

<div class="norm">

**規範**: (1) `global.mixer` は暗黙に1つ存在し、`init` は同一空間への名前付きハンドル取得である（卓は1枚）。 (2) 宣言された識別子は名前空間を確保し、以後 (a) send のバス名メソッド (b) 出力先指定・`sidechain:` 等の引数、として使える。 (3) 解決優先順位: **既知 DSL メソッド名 \> 宣言済みミキサー名 \> プラグインカタログ名**（DSL メソッドの最優先は shadow 防止のための実装決定・#514）。衝突時は言語サービスが警告する。 (4) **バス（sum / aux）自身もレシーバである**: シーケンスと同じ書式でプラグインチェーン・出力先指定を持てる（例: `verb.HogeReverb(size: 0.8).master`）。 (5) send / 出力先が作るグラフは DAG でなければならない。循環は評価時に明示エラー。 (6) ミキサー宣言の無いファイルは**暗黙 master(1,2)** を持つ（現行互換・素朴な1ファイル経路の保護 — 決定 \#75）。 (7) **`master` は出力エンドポイント専用の予約名である**: `mix.output(...)` に `master` と名付けるのは正当（そのノードが master そのもの）だが、**sum / aux に `master` と名付けるのは予約語衝突として明示エラー**とする。宣言形（`var master = mix.sum`）・文字列形（`global.sum("master")`）の双方で拒否する。 (8) **裸のミキサー名参照は、同名が sum / aux 双方に宣言されている場合 loud エラーとする**。sum → aux の暗黙優先解決を行ってはならない。kind の明示には文字列形（`global.sum("drum")` / `global.aux("drum")`）または kind 付きノード変数（`var drums = mix.sum`）を使う。永続 identity / MCP wire 形式である接頭辞 receiver（UIH.5「receiver 名前空間（規範）」の `sum:<name>` / `aux:<name>`）は DSL 表面に持ち込まない。

</div>

> **決定 \#78（`master` の予約）**: SC.4 の `.master` は「本流出力へ戻す」意味を持つ予約語である（決定 \#77 の括弧なし = 出力先指定と一体）。一方で sum / aux の宣言名には制約が無かったため、`global.sum("master")` を宣言すると以後 `.master` がその sum バスに解決され、**予約語の意味が無警告で失われる**（レビューで再現・#523）。`master` は DAW 文脈で sum バスの名前として選ばれやすいため、現実に起こる。
>
> sum / aux 側のみを拒否するのは、`var master = mix.output(1, 2)` が SC.2.1 の表とコード例の双方で正当な形として示されているため。出力エンドポイントに `master` と名付けることは予約語の意味と一致しており、衝突ではない。

### SC.2.2 import による卓の共有と拡張

    // mod/mixer.orbs — 定番の卓
    var mix    = init global.mixer
    var master = mix.output(1, 2)
    var verb   = mix.aux
    verb.HogeReverb(size: 0.8).master

    // song.orbs — 曲側
    import { mix, master, verb } from "./mod/mixer.orbs"
    import * from "./mod/mixer.orbs"              // フラット star import も可（決定 #72）
    var tapeDelay = mix.aux                       // 曲固有の追加派生

<div class="norm">

**規範**: (1) import 構文は既存 IM.1〜IM.6 のまま（新構文なし）。加えてフラットな `import * from` を許す。 (2) 実体は import 時の評価で共有空間に生まれる。名前は列挙（または \*）でスコープに入れた分だけ見える。 (3) `{ mix }` のみの import でも `mix.aux` 等での拡張は可能（aux はメソッドであるため）。

</div>

## SC.3 プラグイン呼び出し（メソッド形）

### SC.3.1 形

    receiver.PluginName(param: value, ...)     // receiver = シーケンス or バス

<div class="norm">

**規範**: (1) パーサは未知メソッド名を受理し、解釈時に「宣言済みミキサー名 → プラグインカタログ」の順で解決する（文法は静的・語彙は動的）。 (2) 引数はすべて名前付き。パラメータ名はプラグインの parameter enumeration（CLAP/VST3 API）に由来する。`()` はデフォルト値のまま挿す。 (3) effect 役の呼び出しは信号層、instrument 役の呼び出しは宣言層に属する（SC.1）。 (4) instrument は1シーケンスに1つ・後勝ち（差し替え）。トポロジー上の位置は構造固定であり記述順と無関係。**各シーケンスのインスタンスは独立で、同一プラグインの宣言でも共有されない。差し替えは新インスタンスの準備成功を待って原子的に切り替わり、失敗時は旧インスタンスが保持される**（SC.5 の失敗モデル (i) prepare-commit 型 — スロットに名前→実体の間接層があるレシーバに適用される）。複数シーケンスを 1 インスタンスへ合流させる形（サミング / マルチティンバー）は暗黙には生じず、明示宣言による後続 stage の拡張とする（core spec PH.4 参照）。

</div>

> **v1 の現在地（規範4）**: per-sequence インスタンス化は **#540 P1 で実装済み**
> （`PluginInstrumentManager` + instrument slot pool）。同一シーケンスへの異 spec 再宣言による
> **原子的差し替え（prepare → commit・失敗時は旧保持・差し替え前 state 自動保存）は #618 で実装済み**。
> effect チェーンの後勝ち・ブロック置換は未実装（#522）。

### SC.3.2 名前の正規化と衝突

<div class="norm">

**規範**: (1) 正規化: カタログ名から英数字のみを連結する（"TAL Reverb 4" → `TALReverb4`）。先頭が数字の場合は `_` を前置。 (2) 正規化で表現できない名前（非英数字のみ等）はメソッド形の対象外とし、逃げ道（`effect("名前")`・SC.8）を使う。 (3) format 衝突（同名が CLAP と VST3 双方に存在）は予約引数 `format:` で解消する。未指定は CLAP 優先（PC.2 と同一規則）。

</div>

### SC.3.3 予約引数

| 引数 | 意味 | 備考 |
|----|----|----|
| `format:` | "clap" \| "vst3"（将来 "au"） | 同名衝突の解消 |
| `vendor:` | ベンダー名 | 同名別ベンダーの解消 |
| `sidechain:` | 宣言済み aux をサイドチェーン入力へ接続 | 識別子を渡す。M2 multi-bus（#409）実装まで明示エラー（silent 無視禁止） |
| `outs:` | マルチアウト instrument のポート→バス割り当て | `outs: { "kick": bdBus }`。#409 実装まで明示エラー |
| `preset:` | プリセット適用 | 対応 format のみ |
| `enabled:` | バイパス（状態保持） | `kick.HogeComp(enabled: false)` |

<div class="norm">

**規範**: プラグイン側に同名の実パラメータが存在する場合は予約語が勝ち、警告を出す。実パラメータへは enumeration の ID 指定で到達可能にする。

</div>

## SC.4 ルーティング — ノードの型がメソッドの意味を決める

    .verb(0.3)      // aux 名（量を取る）        → send（信号層・位置が意味を持つ）
    .drums          // sum 名（括弧なし）        → 本流の出力先（宣言層・後勝ち）
    .master         // output 名（括弧なし）     → 本流の出力先（宣言層・後勝ち）

<div class="norm">

**規範**（決定 \#77）: (1) **aux 名メソッド = send**。`send(識別子, amount: x, enabled: b)` の糖衣であり、send が唯一の分岐 primitive。第2位置引数は `amount:` の省略記法。 (2) **sum / output 名メソッド（括弧なし）= 本流の出力先指定**。宣言層に属し後勝ち。`output(識別子)` の関数形は互換として残す。 (3) send はチェーン上のその位置の信号をタップする: エフェクトの前 = プリ、後 = ポスト。複数可。send は分岐であり本流を変えない。 (4) **送り先の役割は受け手が決める**: 同じ aux を、リバーブのチェーンが受ければリターン、他プラグインの `sidechain:` が受ければサイドチェーンになる。送る側は区別を持たない。 (5) バス名以外の目的別動詞（aux() 別名等）は設けない。動的語彙は「プラグイン名」「宣言済みミキサー名」の2種に限る。

</div>

> **v1 の現在地（規範3 のタップ位置）**: **v1 は post-insert 固定**で、チェーン内の send の位置は無視される。
> core spec `INSTRUCTION_ORBITSCORE_DSL.md` MX.3 が以前から「send は post-fader 固定（v1）・pre/post 切替は将来拡張」と宣言しており、本 spec 側にその staging が書かれていなかった乖離を解消する記述である（規範3 の到達点は変更しない）。
>
> **理由**: v1 は「1レシーバ = 1 insert」の制限下にあり、タップ点の表現は複数 insert のスロット index と不可分。daemon の routing state（`bus_sends`）にタップ点の表現がない。
>
> **実装時期**: **#517 S4**（#522）。受け入れ基準は「`.Effect().verb(0.3)` と `.verb(0.3).Effect()` が異なる結果になること」。

## SC.5 ライブコーディング意味論

<div class="norm">

**規範**: (1) **インスタンス同一性** = (レシーバ, 正規化名, レシーバ内の同名出現順)。 (2) **再評価 = パラメータ更新**: 同一インスタンスへの再呼び出しは、音を止めずに指定パラメータのみを更新する（二重挿入しない）。これがライブのパラメータ操作であり、#460 オートメーションの静的端点。 (3) **新しい名前の評価 = チェーン末尾に追加**。 (4) **ブロック再評価 = 置き換え**（決定 \#73）: 評価単位は空行区切りブロック（現行 REPL の確定単位と同一）。ブロックを再評価すると、そのブロックに現れた構成で当該レシーバのチェーンを置き換え、消えたプラグインはアンロードする。1行単独の評価は更新/追加のみで削除しない。 (5) 帰結として**コメントアウトがバイパスの最速 UI になる**: ブロック内の行を `//` で殺して再評価 → アンロード、コメントを外して再評価 → 復帰。 (6) 明示削除は `remove("名前")`（出現順指定 `remove("名前", n)`）。`enabled: false`（状態保持バイパス）と使い分ける。 (7) ミキサー宣言の再評価は冪等（後勝ち）。使用中バスの削除は「参照が残っている」エラー。

</div>

> **v1 の現在地（規範7 の後勝ち）**: v1 は「同一内容の再宣言が冪等」に加えて、**単一 insert の異 spec 再宣言 = 差し替え**（規範4 の後勝ちのうち単一 insert の部分集合）と **`remove("名前")`**（規範6）を実装する（#625）。宣言の**内容が変わる**再宣言のうち、mixer 宣言そのもの — node kind の変更（`mix.sum` → `mix.aux`）、output チャンネルの変更、mixer handle の別 Global への付け替え — は引き続き**明示エラー**であり、REPL ではエンジン再起動まで解消できない。ブロック再評価による置換（規範4 全体）とチェーン（複数 insert）も引き続き #522。
>
> **失敗モデルは 2 型ある（#625）**:
> **(i) prepare-commit 型** — スロットに名前→実体の間接層があるレシーバ（v1 では instrument）。差し替えは新インスタンスの準備成功を待って原子的に切り替わり、失敗時は旧インスタンスが無傷で保持される。
> **(ii) in-place 型** — スロットが bus 名で位置固定なレシーバ（v1 では effect insert: master / seq / sum / aux）。差し替えは同一スロットの建て直しで行われ、窓の間は dry 素通し（ソース音は途切れない・insert だけが一時的に外れる）。旧インスタンスの解体**前**に失敗した場合は旧 insert が保持され、解体**後**に失敗した場合は dry 素通しへ縮退する（無音にはならない）。縮退からの復旧は同じ宣言の再評価のみで行える（エンジン再起動不要）。差し替え・削除の直前に旧 insert の state は自動保存される。
>
> **理由**: 真の後勝ち（値が変わる再宣言の反映）には、使用中 routing の差し替え・旧バスの解放・plugin のアンロード・参照整合・rollback が要る。これは規範(2)(4) のライブ意味論そのものであり、それらと一体で実装されるべきもの。
>
> **実装時期**: **#517 S4**（#522）。受け入れ基準は「kind 変更・チャンネル変更・Global 付け替えが、エンジン再起動なしに後勝ちで反映されること」。
>
> **v1 のエラーは stage 表記を含む**（ユーザーがいつ使えるようになるかを知れるようにするため）。

## SC.6 エディタ支援（言語サービス要件）

- `kick.` 直後: 通常メソッド + 宣言済みバス名 + レシーバに挿せる役割のプラグイン名を候補に出す。`kick.e` と打てばエフェクト名が、pitch シーケンスで `.i` と打てば instrument 名が絞り込まれる（名前自体が候補であるため）。
- プラグイン名確定後の `(` でパラメータ名補完（enumeration から。範囲・単位を detail に）。予約引数も同列に出す。
- 出力先・`sidechain:` の位置では宣言済みミキサー名のみを出す（文脈限定）。
- 実装段階: 第1段 = カタログ + regex 文脈で名前系のみ。第2段 = \#495 言語サービスでシンボルテーブル・レシーバ種別判定・パラメータ補完。

## SC.8 互換と移行

<div class="norm">

**規範**: (1) `effect("名前")` / `instrument("名前")` / 文字列バス形（`global.sum("drums")`・`output("drums")`）はすべて存置する（後方互換 + 素朴経路の恒久保護 + 正規化不能名の逃げ道）。 (2) 文字列形で宣言された名前もメソッド化の対象になる。 (3) docs / learning site はチェーン形を正、文字列形を代替として記載する。

</div>
