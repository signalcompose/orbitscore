## SC.0 全体像

    // ── ミキサー空間を init して派生させる
    var mix    = init global.mixer        // 卓そのもの
    var master = mix.output(1, 2)         // 物理アウト 1-2 = メイン
    var subout = mix.output(3, 4)         // 物理アウト 3-4（マルチアウト）
    var drums  = mix.sum                  // グループバス
    var verb   = mix.aux                  // センドリターン
    var duck   = mix.aux                  // サイドチェーン搬送も aux（役割は受け手が決める）

    // ── リターン側のチェーン（バスもシーケンスと同じ書式）
    verb.HogeReverb(size: 0.8).master

    // ── トラック
    kick.audio("kick.wav").chop(16).play(1, 5, 9, 13)
        .CLAPTestEffect(mix: 0.5)
        .HogeComp(threshold: -18, sidechain: duck)
        .verb(0.3)                        // aux 名 → send（位置 = プリ/ポスト）
        .FugaEQ(low: 2)
        .drums                            // sum 名 → 本流の出力先（宣言層・括弧なし）

    bass.audio("bass.wav").play(1, 9).duck(1.0).drums
    drums.GlueComp(ratio: 2).master
    lead.Serum(preset: "Pluck 01").TALReverb4(size: 0.6).subout

## SC.1 二層意味論 — 宣言は集合・信号は列

| 層 | 属するもの | 順序の意味 |
|----|----|----|
| **宣言層** | audio / chop / play / gain / pan / 出力先ノード名（括弧なし）/ instrument 役のプラグイン呼び出し / ミキサー宣言 | **可換**。どこに書いても同じ。同一項目の再宣言は後勝ち。 |
| **信号層** | effect 役のプラグイン呼び出し / send（aux 名メソッドを含む） | **この層内の相対順序だけ**が接続順になる。宣言層の文がどこに挟まっても影響しない。 |

<div class="norm">

**規範**: (1) チェーン1本と行分割呼び出しは完全等価（同一の評価列であるため）。 (2) トポロジーは構造で固定される: **パターン(play) → instrument → エフェクト列 → 出力先**。 利用者が順序で制御できるのはエフェクト列の中身と send の位置のみ。 (3) `play()` の意味論は本仕様の影響を受けない。

</div>

## SC.2 ミキサー宣言

### SC.2.1 mixer 空間とノード派生

    var mix = init global.mixer

| 派生宣言 | 意味 | 備考 |
|----|----|----|
| `var master = mix.output(1, 2)` | 物理出力チャンネル対（出力エンドポイント） | 複数宣言でマルチアウト。デバイス ch 数超過は起動/デバイス切替時に警告（#484 D4 と接続） |
| `var drums = mix.sum` | グループバス（合流点） | MX.2 の sum と同一実体 |
| `var verb = mix.aux` | センド用バス | MX.4 の aux と同一実体。サイドチェーン搬送も aux で行う（汎用 bus 型は設けない — 決定 \#74） |

<div class="norm">

**規範**: (1) `global.mixer` は暗黙に1つ存在し、`init` は同一空間への名前付きハンドル取得である（卓は1枚）。 (2) 宣言された識別子は名前空間を確保し、以後 (a) send のバス名メソッド (b) 出力先指定・`sidechain:` 等の引数、として使える。 (3) 解決優先順位: **既知 DSL メソッド名 \> 宣言済みミキサー名 \> プラグインカタログ名**（DSL メソッドの最優先は shadow 防止のための実装決定・#514）。衝突時は言語サービスが警告する。 (4) **バス（sum / aux）自身もレシーバである**: シーケンスと同じ書式でプラグインチェーン・出力先指定を持てる（例: `verb.HogeReverb(size: 0.8).master`）。 (5) send / 出力先が作るグラフは DAG でなければならない。循環は評価時に明示エラー。 (6) ミキサー宣言の無いファイルは**暗黙 master(1,2)** を持つ（現行互換・素朴な1ファイル経路の保護 — 決定 \#75）。 (7) **`master` は出力エンドポイント専用の予約名である**: `mix.output(...)` に `master` と名付けるのは正当（そのノードが master そのもの）だが、**sum / aux に `master` と名付けるのは予約語衝突として明示エラー**とする。宣言形（`var master = mix.sum`）・文字列形（`global.sum("master")`）の双方で拒否する。 (8) **裸のミキサー名参照は、同名が sum / aux 双方に宣言されている場合 loud エラーとする**。sum → aux の暗黙優先解決を行ってはならない。kind の明示には文字列形（`global.sum("drum")` / `global.aux("drum")`）または kind 付きノード変数（`var drums = mix.sum`）を使う。永続 identity / MCP wire 形式である接頭辞 receiver（UIH.5「receiver 名前空間（規範）」の `sum:<name>` / `aux:<name>`）は DSL 表面に持ち込まない。

</div>

> **決定 \#78（`master` の予約）**: SC.4 の `.master` は「本流出力へ戻す」意味を持つ予約語である（決定 \#77 の括弧なし = 出力先指定と一体）。一方で sum / aux の宣言名には制約が無かったため、`global.sum("master")` を宣言すると以後 `.master` がその sum バスに解決され、**予約語の意味が無警告で失われる**（レビューで再現・#523）。`master` は DAW 文脈で sum バスの名前として選ばれやすいため、現実に起こる。
>
> sum / aux 側のみを拒否するのは、`var master = mix.output(1, 2)` が SC.2.1 の表とコード例の双方で正当な形として示されているため。出力エンドポイントに `master` と名付けることは予約語の意味と一致しており、衝突ではない。

### SC.2.2 import による卓の共有と拡張

    // mod/mixer.orbs — 定番の卓
    var mix    = init global.mixer
    var master = mix.output(1, 2)
    var verb   = mix.aux
    verb.HogeReverb(size: 0.8).master

    // song.orbs — 曲側
    import { mix, master, verb } from "./mod/mixer.orbs"
    import * from "./mod/mixer.orbs"              // フラット star import も可（決定 #72）
    var tapeDelay = mix.aux                       // 曲固有の追加派生

<div class="norm">

**規範**: (1) import 構文は既存 IM.1〜IM.6 のまま（新構文なし）。加えてフラットな `import * from` を許す。 (2) 実体は import 時の評価で共有空間に生まれる。名前は列挙（または \*）でスコープに入れた分だけ見える。 (3) `{ mix }` のみの import でも `mix.aux` 等での拡張は可能（aux はメソッドであるため）。

</div>

## SC.3 プラグイン呼び出し（メソッド形）

### SC.3.1 形

    receiver.PluginName(param: value, ...)     // receiver = シーケンス or バス

<div class="norm">

**規範**: (1) パーサは未知メソッド名を受理し、解釈時に「宣言済みミキサー名 → プラグインカタログ」の順で解決する（文法は静的・語彙は動的）。 (2) 引数はすべて名前付き。パラメータ名はプラグインの parameter enumeration（CLAP/VST3 API）に由来する。`()` はデフォルト値のまま挿す。 (3) effect 役の呼び出しは信号層、instrument 役の呼び出しは宣言層に属する（SC.1）。 (4) instrument は1シーケンスに1つ・後勝ち（差し替え）。トポロジー上の位置は構造固定であり記述順と無関係。**各シーケンスのインスタンスは独立で、同一プラグインの宣言でも共有されない。差し替えは新インスタンスの準備成功を待って原子的に切り替わり、失敗時は旧インスタンスが保持される**（SC.5 の失敗モデル (i) prepare-commit 型 — スロットに名前→実体の間接層があるレシーバに適用される）。複数シーケンスを 1 インスタンスへ合流させる形（サミング / マルチティンバー）は暗黙には生じず、明示宣言による後続 stage の拡張とする（core spec PH.4 参照）。

</div>

> **v1 の現在地（規範4）**: per-sequence インスタンス化は **#540 P1 で実装済み**
> （`PluginInstrumentManager` + instrument slot pool）。同一シーケンスへの異 spec 再宣言による
> **原子的差し替え（prepare → commit・失敗時は旧保持・差し替え前 state 自動保存）は #618 で実装済み**。
> effect チェーンの後勝ち・ブロック置換は未実装（#522）。

### SC.3.2 名前の正規化と衝突

<div class="norm">

**規範**: (1) 正規化: カタログ名から英数字のみを連結する（"TAL Reverb 4" → `TALReverb4`）。先頭が数字の場合は `_` を前置。 (2) 正規化で表現できない名前（非英数字のみ等）はメソッド形の対象外とし、逃げ道（`effect("名前")`・SC.8）を使う。 (3) format 衝突（同名が CLAP と VST3 双方に存在）は予約引数 `format:` で解消する。未指定は CLAP 優先（PC.2 と同一規則）。

</div>

### SC.3.3 予約引数

| 引数 | 意味 | 備考 |
|----|----|----|
| `format:` | "clap" \| "vst3"（将来 "au"） | 同名衝突の解消 |
| `vendor:` | ベンダー名 | 同名別ベンダーの解消 |
| `sidechain:` | 宣言済み aux をサイドチェーン入力へ接続 | 識別子を渡す。M2 multi-bus（#409）実装まで明示エラー（silent 無視禁止） |
| `outs:` | マルチアウト instrument のポート→バス割り当て | `outs: { "kick": bdBus }`。#409 実装まで明示エラー |
| `preset:` | プリセット適用 | 対応 format のみ |
| `enabled:` | バイパス（状態保持） | `kick.HogeComp(enabled: false)` |

<div class="norm">

**規範**: プラグイン側に同名の実パラメータが存在する場合は予約語が勝ち、警告を出す。実パラメータへは enumeration の ID 指定で到達可能にする。

</div>

## SC.4 ルーティング — ノードの型がメソッドの意味を決める

    .verb(0.3)      // aux 名（量を取る）        → send（信号層・位置が意味を持つ）
    .drums          // sum 名（括弧なし）        → 本流の出力先（宣言層・後勝ち）
    .master         // output 名（括弧なし）     → 本流の出力先（宣言層・後勝ち）

<div class="norm">

**規範**（決定 \#77）: (1) **aux 名メソッド = send**。`send(識別子, amount: x, enabled: b)` の糖衣であり、send が唯一の分岐 primitive。第2位置引数は `amount:` の省略記法。 (2) **sum / output 名メソッド（括弧なし）= 本流の出力先指定**。宣言層に属し後勝ち。`output(識別子)` の関数形は互換として残す。 (3) send はチェーン上のその位置の信号をタップする: エフェクトの前 = プリ、後 = ポスト。複数可。send は分岐であり本流を変えない。 (4) **送り先の役割は受け手が決める**: 同じ aux を、リバーブのチェーンが受ければリターン、他プラグインの `sidechain:` が受ければサイドチェーンになる。送る側は区別を持たない。 (5) バス名以外の目的別動詞（aux() 別名等）は設けない。動的語彙は「プラグイン名」「宣言済みミキサー名」の2種に限る。

</div>

> **v1 の現在地（規範3 のタップ位置）**: **v1 は post-insert 固定**で、チェーン内の send の位置は無視される。
> core spec `INSTRUCTION_ORBITSCORE_DSL.md` MX.3 が以前から「send は post-fader 固定（v1）・pre/post 切替は将来拡張」と宣言しており、本 spec 側にその staging が書かれていなかった乖離を解消する記述である（規範3 の到達点は変更しない）。
>
> **理由**: v1 は「1レシーバ = 1 insert」の制限下にあり、タップ点の表現は複数 insert のスロット index と不可分。daemon の routing state（`bus_sends`）にタップ点の表現がない。
>
> **実装時期**: **#517 S4**（#522）。受け入れ基準は「`.Effect().verb(0.3)` と `.verb(0.3).Effect()` が異なる結果になること」。

## SC.5 ライブコーディング意味論

<div class="norm">

**規範**: (1) **インスタンス同一性** = (レシーバ, 正規化名, レシーバ内の同名出現順)。 (2) **再評価 = パラメータ更新**: 同一インスタンスへの再呼び出しは、音を止めずに指定パラメータのみを更新する（二重挿入しない）。これがライブのパラメータ操作であり、#460 オートメーションの静的端点。 (3) **新しい名前の評価 = チェーン末尾に追加**。 (4) **ブロック再評価 = 置き換え**（決定 \#73）: 評価単位は空行区切りブロック（現行 REPL の確定単位と同一）。ブロックを再評価すると、そのブロックに現れた構成で当該レシーバのチェーンを置き換え、消えたプラグインはアンロードする。1行単独の評価は更新/追加のみで削除しない。 (5) 帰結として**コメントアウトがバイパスの最速 UI になる**: ブロック内の行を `//` で殺して再評価 → アンロード、コメントを外して再評価 → 復帰。 (6) **【#628 で撤回】** 明示削除は `remove("名前")`（出現順指定 `remove("名前", n)`）— **SC.10.3 が置き換える**。ラック形では「配列から消す」が削除であり、`remove()` は役割が重複する。`enabled: false`（状態保持バイパス）の意味論は SC.10.2 へ移した。 (7) ミキサー宣言の再評価は冪等（後勝ち）。使用中バスの削除は「参照が残っている」エラー。

</div>

> **v1 の現在地（規範7 の後勝ち）**: v1 は「同一内容の再宣言が冪等」に加えて、**単一 insert の異 spec 再宣言 = 差し替え**（規範4 の後勝ちのうち単一 insert の部分集合）と **`remove("名前")`**（規範6）を実装する（#625）。**`remove()` は #628 で撤去された** — 削除は「配列から消す」に一本化された（SC.10.3c）。宣言の**内容が変わる**再宣言のうち、mixer 宣言そのもの — node kind の変更（`mix.sum` → `mix.aux`）、output チャンネルの変更、mixer handle の別 Global への付け替え — は引き続き**明示エラー**であり、REPL ではエンジン再起動まで解消できない。ブロック再評価による置換（規範4 全体）とチェーン（複数 insert）も引き続き #522。
>
> **失敗モデルは 2 型ある（#625）**:
> **(i) prepare-commit 型** — スロットに名前→実体の間接層があるレシーバ（instrument、および **#628 以降の effect チェーン編集**）。差し替えは新インスタンスの準備成功を待って原子的に切り替わり、失敗時は旧インスタンスが無傷で保持される。
> 🔴 **#628 以降、effect チェーンの編集（要素の追加・削除・差し替え・`enabled` 切替・パラメータ更新）はすべて (i) prepare-commit 型である**（rack child が 1 プロセス内で新 stage list を prepare し、block 境界で 1 回だけ swap する — SC.10）。**編集中も旧チェーンが鳴り続け、失敗すれば旧チェーンが無傷のまま残る。差し替えの dry 窓は存在しない。**
> **(ii) in-place 型** — スロットが bus 名で位置固定なレシーバ。**#628 以降、この型が残るのは「チェーン → 空」の teardown・stream 停止・crash respawn の 3 つだけ**（チェーン編集は (i) へ移った）。以下は #625 時点の単一 insert の記述であり、上記 3 経路に読み替える。差し替えは同一スロットの建て直しで行われ、窓の間は dry 素通し（ソース音は途切れない・insert だけが一時的に外れる）。旧インスタンスの解体**前**に失敗した場合は旧 insert が保持され、解体**後**に失敗した場合は dry 素通しへ縮退する（無音にはならない）。縮退からの復旧は同じ宣言の再評価のみで行える（エンジン再起動不要）。ただし、回復不能な attach 失敗はスロット隔離となり、この場合はエンジン再起動が必要。差し替え・削除の直前に旧 insert の state は自動保存される。
>
> **理由**: 真の後勝ち（値が変わる再宣言の反映）には、使用中 routing の差し替え・旧バスの解放・plugin のアンロード・参照整合・rollback が要る。これは規範(2)(4) のライブ意味論そのものであり、それらと一体で実装されるべきもの。
>
> **実装時期**: **#517 S4**（#522）。受け入れ基準は「kind 変更・チャンネル変更・Global 付け替えが、エンジン再起動なしに後勝ちで反映されること」。
>
> **v1 のエラーは stage 表記を含む**（ユーザーがいつ使えるようになるかを知れるようにするため）。

## SC.6 エディタ支援（言語サービス要件）

- `kick.` 直後: 通常メソッド + 宣言済みバス名 + レシーバに挿せる役割のプラグイン名を候補に出す。`kick.e` と打てばエフェクト名が、pitch シーケンスで `.i` と打てば instrument 名が絞り込まれる（名前自体が候補であるため）。
- プラグイン名確定後の `(` でパラメータ名補完（enumeration から。範囲・単位を detail に）。予約引数も同列に出す。
- 出力先・`sidechain:` の位置では宣言済みミキサー名のみを出す（文脈限定）。
- 実装段階: 第1段 = カタログ + regex 文脈で名前系のみ。第2段 = \#495 言語サービスでシンボルテーブル・レシーバ種別判定・パラメータ補完。

## SC.8 互換と移行

<div class="norm">

**規範**: (1) `effect("名前")` / `instrument("名前")` / 文字列バス形（`global.sum("drums")`・`output("drums")`）はすべて存置する（後方互換 + 素朴経路の恒久保護 + 正規化不能名の逃げ道）。 (2) 文字列形で宣言された名前もメソッド化の対象になる。 (3) docs / learning site はチェーン形を正、文字列形を代替として記載する。

</div>

## SC.10 ラック — チェーンを値として書く（#628）

> **制定**: 2026-08-27 / owner との設計議論（#628）で確定。DAW リサーチ（Bitwig / Live）を
> 踏まえ、**削除・バイパス・チェーンを 1 つのモデル**として定める。
> 経緯と棄却案は `docs/design/628-effect-chain-model.md`。

### SC.10.1 形

    kick.effect([
      "FabFilter Pro-C 2",
      plugin("FabFilter Pro-Q 3", enabled: false),
      layer([
        [],
        ["ValhallaRoom", Gain(db: -10)],
      ]),
      "FabFilter Pro-L 2",
    ])

| 語 | 意味 |
|----|----|
| `[...]` | **直列チェーン**。`chain([...])` の糖衣 |
| `"名前"` | **カタログのプラグイン**（既定値）。`plugin("名前")` の糖衣 |
| `layer([...])` | **並列**。effect / instrument で同じ語 |
| `plugin("名前", ...)` | 引数が要る時の完全形 |
| `Gain(db: n)` | **標準プラグイン**（大文字始まりの呼び出し・SC.10.8） |

<div class="norm">

**規範**: (1) **`[...]` は常に直列**であり、深さや文脈で意味を変えない。並列は常に `layer([...])` と書く。 (2) **プラグイン形式（CLAP / VST3）は DSL 表面に現れない**（`PLUGIN_CAPABILITY_ABSTRACTION_v1` CAP.6-1）。必要な時だけ予約引数 `format:` で解消する。 (3) **3 つのカテゴリは構文で区別される**: **`"文字列"` = カタログのプラグイン** / **`Gain(...)` のような大文字始まりの呼び出し = 標準プラグイン**（SC.10.8）/ **`layer(...)` のような小文字の呼び出し = 構造**。カテゴリが構文で分かれるため、標準プラグインとカタログのプラグインは**名前が衝突しない**（3rd-party の "Gain" は `"Gain"` と書けば必ず取れる）。 (4) **カタログのプラグインをメソッド形（正規化名の呼び出し）で指す形は撤回する**（SC.10.9）。

</div>

### SC.10.2 無効化 — その合成の単位元になる

<div class="norm">

**規範**: `enabled: false` は「**自分がいる合成の単位元になる**」ことを意味する。したがって **直列では素通し**（信号をそのまま渡す）、**並列では無音**（合算に何も足さない）となる。プラグインは**ロードされたまま**であり、state も保持される。空の直列チェーン `[]` が素通しブランチになるのは同じ原理（直列合成の単位元）である。

</div>

この規則により、A/B 切り替えは専用の構文を必要としない。直列に並べて片方を無効化すれば A/B になり、**両方有効（直列接続）** と **両方無効（素通し）** も同じ形で書ける。

### SC.10.3 削除は「配列から消す」

<div class="norm">

**規範**: insert の削除は、**ラックの配列からその要素を消して再評価する**ことで行う。専用の削除メソッドは設けない。削除された insert の state は、アンロードの直前に自動保存される（SC.5）ので、書き戻せば復元される。

</div>

> **改訂（#628）**: 旧 SC.5 規範6 の `remove("名前")` / `remove("名前", n)` は**撤回**する。
> ラック形では「配列から消す」が削除であり、`remove()` は役割が重複する。
> **出現順が DSL 表面に現れる箇所はこれで無くなる**（`remove` の第2引数が唯一の露出だった）。

### SC.10.3b 文字列単発形は「完全な像」である（owner 確認済み 2026-08-27）

<div class="norm">

**規範**: `receiver.effect("名前")` は **`receiver.effect(["名前"])` と完全に等価**であり、チェーン全体の像を置き換える。したがって `effect([A1, A2])` の後に `effect("B")` を評価すると **A1 と A2 はアンロードされ、チェーンは `[B]` になる**。

</div>

> **根拠**: 同じ動詞が**引数の形で意味を変える**（配列なら置換・文字列なら追記）のは説明不能に
> なる。SC.5 規範3「新しい名前の評価 = チェーン末尾に追加」は規範2-4 のライブ意味論
> （評価単位・ブロック置換）と一体であり、それらは #522 スコープである。v1 では単発形も
> ラック形も**同じ「完全な像」の規則**に従う。
>
> 既存 `.orbs` の 1 insert 形は、長さ 1 のラックとして**可観測挙動が保たれる**
> （宣言・冪等再宣言・異 spec 後勝ち・state 復元・linkAudio ゲート）。

### SC.10.3c `remove()` の撤去（owner 確認済み 2026-08-27）

<div class="norm">

**規範**: `remove("名前")` は**即時に撤去**する（未知メソッドとして拒否される）。移行用の
専用エラー文言は設けない。

</div>

> **根拠**: 既存の楽譜で `remove()` を使っているものが無い（owner 確認）。使われていない
> 表面に移行期間を設けても、語彙から消す作業を先送りするだけになる。

### SC.10.4 ラックは値（レシピ）である

    var glue = ["FabFilter Pro-C 2", "FabFilter Pro-Q 3"]

    kick.effect(glue)
    snare.effect(glue)      // 別インスタンス

<div class="norm">

**規範**: (1) ラックの束縛（`var x = [...]`）は**レシピを束縛するだけ**で、プラグインを起動しない。プラグインが起動するのは**レシーバへ適用された時**である。 (2) 同じラックを複数のレシーバへ適用しても、**インスタンスは共有されない**（SC.3 規範4 の instrument と同じ扱い）。 (3) ラックは**値**であり参照ではない。束縛を書き換えても、既に適用済みのレシーバは**そのレシーバの文を再評価するまで変化しない**。

</div>

> **根拠**: 実行のための評価と、変数へ束縛するための評価は別物である（owner・#628）。
> 参照にすると波及範囲がテキストから読み取れず、UI を持たない環境では危険側に倒れる。

### SC.10.5 再評価 — 差分で対応づける

<div class="norm">

**規範**: (1) ラックの再評価は**後勝ち**である（SC.5 規範7 と同じ）。 (2) 新旧の配列は**名前の並びの最長共通部分列（LCS）**で対応づける。対応がついた要素は**生かしたまま**（音を止めず・state を保ったまま）、対応のつかない旧要素だけをアンロードし、新要素だけをロードする。 (3) **出現順はインスタンスに固定される** — テキストから数え直さない。これにより、同名プラグインを含むチェーンから 1 つ削除しても、残った側の state は自分のものであり続ける。 (4) LCS が一意に定まらない場合は**前方の一致を優先**する。 (5) **同名プラグインの並べ替えは表現できない** — 同じ名前のエントリはテキスト上で区別できないため、state は位置に従う。

</div>

> **背景**: (3) が無いと、`[A, B, A]` から先頭の `A` を消した時に残った `A` の出現順が
> 1 → 0 へ繰り上がり、**消したはずの insert の state を読み込む**。v1 でこれが表面化して
> いないのは insert が 1 つに制限されていて出現順が常に 0 だからで、**複数 insert を許した
> 瞬間に現れる**。木（`layer`）はこれを悪化させるだけで、原因ではない。
>
> state ファイル名は `[receiver, role, normalizedName, occurrence]` から作られる
> （`project-state-store.ts`）。(3) の方式では**この形式は変わらない**ため、既存の保存済み
> state はそのまま読める。

### SC.10.6 instrument も同じ形

    cb.instrument(layer([
      ["Kontakt 8"],
      ["Serum", Gain(db: -6)],
    ]))

<div class="norm">

**規範**: (1) instrument も `layer` で複数を並列に持てる（1 つのパターンを複数音源で鳴らす）。音源を直列に繋ぐ意味は無いため、**複数の instrument を裸の配列に並べることは明示エラー**とする。 (2) instrument ブランチの無効化・削除は、**その音源で発音中のノートの発生源を止める**ため、強制 note-off の対象である（core spec の note-off 規定に本ケースを加える）。

</div>

> **SC.10.7 は欠番**（v1 の段階の節を末尾へ移し SC.10.11 とした・2026-08-27）。

### SC.10.8 標準プラグイン（owner 確定 2026-08-27）

    kick.effect([
      "ValhallaRoom",        // カタログ = 文字列
      Gain(db: -10),         // 標準 = 大文字始まりの呼び出し
    ])

<div class="norm">

**規範**: (1) OrbitScore が提供する 1st-party のエフェクト / 楽器は、**engine に DSP を抱えず、標準プラグインとして提供する**（`POST_2.0_PLUGIN_STRATEGY` の確定原則）。 (2) 形式は **CLAP**。 (3) **アプリに同梱**し、OS のプラグインディレクトリに依存しない。 (4) 標準プラグインは**言語の語彙として解決**し、**カタログを引かない**。したがってカタログのプラグインとは**名前空間が分かれ、衝突しない** — 同名の 3rd-party は `"Gain"` と文字列で書けば必ず取れる。接頭辞は不要。 (5) 標準プラグインは **UI を持たない**。パラメータは DSL に直接書く。 (6) 帰結として標準プラグインは **state ファイルを持たない**（音はすべてテキストにあるため）。差分（SC.10.5）では「パラメータ更新」の対象であり、state の保存・復元の対象外である。

</div>

> **CLAP を選んだ理由**: VST3 は 2025-10（VST 3.8）に **MIT** へ再ライセンスされたため
> ライセンス上の差は無い。残るのは (a) **実装が軽い**（C ABI・COM 風の参照カウントや
> インタフェースクエリが不要）— 標準プラグインは**群として増える**予定なので効く、
> (b) 標準が CLAP であることで、**利用者の手持ち（VST3 中心）と混在したチェーンが日常的に
> 発生する** — 「1 つの child が両フォーマットを同居ホストする」機構の核心が、gated テストの
> 中だけでなく**通常の使用で常に検証される**（owner）。format の広さは選定理由にならない
> （ホストは自分たちのものだけ）。
>
> **(5)(6) の含意**: パラメータがテキストにあるため、標準プラグインは**最初から LLM が
> 操作できる面**である。3rd-party プラグインは UI で作った音が state に入るので人間の領分。
> 役割が分かれる（`mem:human-knobs-vs-llm-dsl-params`）。
>
> **`gain` が言語の要素でなくなった経緯**: 当初 `gain(db:)` をチェーンの要素（engine 内蔵）
> として設計したが、確定原則「engine に DSP を抱えない」に反していた。標準プラグインに
> することで **v1 の特例（「プラグインを含まないラックはエラー」）が消える**。

### SC.10.9 カタログのプラグインは文字列で指す（owner 確定 2026-08-27）

<div class="norm">

**規範**: カタログのプラグインは **`"名前"` または `plugin("名前", ...)`** で指す。**SC.3.1 / SC.6 のメソッド形（正規化名の呼び出し）は撤回する。**

</div>

> **根拠**: (1) 実名は正規化すると見た目が変わり、元の名前で検索できなくなる
> （`"FabFilter Pro-Q 3"` → `FabFilterProQ3`）。 (2) メソッド形を残すと、**標準プラグインと
> カタログのプラグインが同じ見た目**になり、SC.10.1 規範3 のカテゴリ分けが崩れる。
> 環境を移した時に壊れるのは**カタログ側だけ**なので、この区別には実用上の意味がある。
> (3) 正規化の衝突（別製品が同じ識別子になる）も同時に消える。
>
> **代償**: 引数付きは `plugin("名前", enabled: false)` となりメソッド形より長い。これは
> **補完で埋める**（SC.10.10）。

### SC.10.10 プラグインを挿す UX（owner 確定 2026-08-27）

<div class="norm">

**規範**: (1) **文字列リテラルの中でカタログ補完が出る**こと。ラックの配列の中・`layer` の入れ子の中でも同様に出る（#463 C3 の補完はラック形でも退行させない）。 (2) **プラグイン UI は、楽譜上のプラグイン名を Cmd+Click して開く**のを主経路とする。エディタが構文木の位置からパスを解決するため、**DSL に index やパスを露出させない**（PH.2c の `ui([index])` の **index 形は撤回**する）。 (3) **DSL からも開ける**（下記 SC.10.10.1）。人間だけでなく **LLM が DSL 経路で駆動できる**ようにするため（`mem:llm-drives-orbitstudio-through-dsl`）。 (4) MCP 経路（`open_plugin_ui`）は `chain_path` 指定で維持する。

</div>

> **なぜ Cmd+Click か**: ラックは入れ子になり得るので、位置は 1 次元の index では指せない
> （ブランチ番号 + 位置が要る）。エディタはカーソル位置から構文木上の位置を知っているので、
> **書き手が数えなくてよい**。出現順を DSL 表面から追い出した SC.10.3b と同じ方向。
>
> **別 issue とするもの**: プラグイン一覧の Quick Pick（「何を挿すか探している」時の入口・
> 補完は名前の断片を覚えている時にしか効かない）と、**カタログに無い名前の診断**
> （現状は評価するまで分からない・#610 と同じ場所）。

#### SC.10.10.1 `ui()` — 名前で指し、一致するもの全部を開く（owner 確定 2026-08-27）

    cb.ui()                       // instrument の UI
    cb.ui("ValhallaRoom")         // 名前が一致する insert の UI（複数一致なら全部）
    cb.ui("ValhallaRoom", false)  // 閉じる

<div class="norm">

**規範**: (1) 無引数形は **instrument の UI** を開く（instrument は 1 つなので指定が要らない）。 (2) 第 1 引数に**カタログ名の文字列**を取り、**一致する insert すべての UI を開く**。`layer` の入れ子も含めチェーン全体から探す。 (3) **同名が複数あっても曖昧にならない** — 選ばずに全部開くため。#617 の設計方針「複数同時オープンを制限しない」と一致し、**出現順を DSL 表面に出さずに済む**。 (4) 第 2 引数 `false` は同じ規則で**閉じる**。 (5) **標準プラグインは UI を持たない**（SC.10.8）ので、標準プラグイン名を渡すのは明示エラーとする。 (6) 一致が 0 件のときは loud に失敗する（黙って no-op しない・#617 の受け入れ基準）。

</div>

> **なぜ index ではなく名前か**: index 形はラックの入れ子を指せず（SC.10.10 規範2）、
> 出現順を表面に出すと SC.10.3b / SC.10.5 で追い出した概念が戻ってくる。名前 + 「全部開く」なら
> **どちらの問題も起きない**。
>
> **なぜ effect も対象にするか**: instrument だけ DSL から開けて effect が開けない形は、
> **LLM から見て実害**になる（LLM は Cmd+Click できない）。owner 判断 2026-08-27。

### SC.10.11 v1 の段階

<div class="norm">

**規範**: 記法は本節の全体を v1 で確定させる。ただし **`layer`（並列）の実装は PDC（plugin latency 補償）とセットで後続とする**。並列は遅延の異なるブランチを合算するため、PDC 不在のままではコムフィルタとして**音の劣化**が生じる（core spec の既知制約「PDC なし — 並列経路の位相整合は保証しない」）。直列チェーンでは遅延が一様に加わるだけなのでこの問題は生じない。

</div>
