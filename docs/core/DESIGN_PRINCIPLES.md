# OrbitScore プロダクト設計原則

owner 確定（2026-07-28・#541/#543 の設計議論で確立）。**規範**であり、これに反する設計は
提案段階で却下する。個別機能の仕様より上位に位置する。

---

## 1. LLM-first — 「LLM が使えない機能があること自体が、このソフトウェアの敗北」

OrbitStudio は人間と LLM の共有媒体であり、LLM は第一級ユーザーである。

- **すべての能力は、まずプログラマブルな面（MCP / DSL）として存在しなければならない。**
  UI はその上に載る人間向けのビューであって、UI にしか無い能力を作った時点で設計の誤り
- 新機能の設計レビューでは常に問う: 「**LLM はこの機能を MCP から使い、結果を検証できるか**」
- 規格側が持つプログラマブルな到達面（VST3 `IEditController` パラメータ / program list・
  CLAP params 拡張・MIDI CC）は、UI 実装の有無にかかわらず MCP に引き出す

### 例外の封じ込め

プラグイン独自 UI でしか到達できない操作（規格外のライブラリブラウザ等）は現実に存在する。
これらは排除できないが、**「一度きりの初期化イベント」に封じ込める**: 人間が UI で行った結果は
state として機械管理系に取り込まれ、以後の再現・複製・演奏は無人で行えること。
人間が**常駐**しなければ使えない形は不可。

## 2. 人間製成果物への依存禁止

**ワークフローのどのステップも、人間が手作業で生成した成果物を前提にしてはならない。**

- 実例（却下済み）: 「外部 DAW で `.vstpreset` を書き出して持ち込む」— プラグインが他ホストで
  開ける保証は無く（所有 DAW・ライセンス・ホスト互換）、人間の手作業が前提になった時点で誤り
- テストへの適用: fixture・期待値・state 等のテスト資産はすべて機械が生成する
  （詳細は [`../testing/E2E_HARNESS_SPEC.md`](../testing/E2E_HARNESS_SPEC.md)）

## 3. 人間と LLM の対称ワークフロー

同じ目的に対して人間の面と LLM の面を**対称**に設計し、**両者は同じ状態に合流し、
同じ機構で永続化される**。

例: プラグインの音色選択（DAW ループ・#541）

| ループ段階 | 人間の面 | LLM の面 |
|---|---|---|
| プラグイン指定 | DSL 記述 | MCP evaluate |
| 音色を作る / 選ぶ | プラグイン UI（#474） | param enumeration / set・preset 選択・state 取得 API |
| 記録・復元 | 自動（共通） | 自動（共通）+ MCP から明示操作も可 |

LLM 側 API はループの必須半身であり「UI 実装後の残項目」ではない。

## 4. 意図と登記の分離

- **`.orbs`（人間・LLM が書く）= 意図の宣言。** 音楽的内容・プラグイン指定はここだけが正本
- **プロジェクトファイル（機械が書く）= 環境と派生状態の登記。** DSL と重複するフィールドを
  持たない（二重管理の禁止）。自動生成・自動維持・atomic 書き込み・人間が読めるテキスト
- 派生データ（自動保存された state 等）を人間のファイルに書き戻さない
  （保存のたびに楽譜が機械に書き換えられ、ライブコーディングの編集と衝突するため）

## 5. 既存の関連原則（再掲・変更なし）

- 素朴な単一 `.orbs` 経路は永遠に保護する（プロジェクト機構はオプトイン）
- audio シーケンスの `play()` 意味論は変更しない
- 仕様と実装が乖離する場合は spec 側を先に更新する（spec = 単一信頼情報源）
