# WCTM 機械の耳 — 実装案 10（計画案）

## 日付
2026-07-03

## 位置づけ

[WCTM_MACHINE_LISTENING_RESEARCH](WCTM_MACHINE_LISTENING_RESEARCH.md)（deep research サーヴェイ・同日）の結論に基づく実装計画案。
**実装着手前に owner 決定事項 D1-D4 の確定が必要。** spec への反映（WCTM_SYSTEM_SPEC §2 / §3.1 / §10.6 の改訂）は決定後に別 PR で行う。

各案は独立採用可能な単位で設計し、案10 が推奨の段階的統合。工数は 1 人日ベースの目安。

## 案1: Operator-First Minimal Floor（全介助・最小特徴量の床）

- **耳**: onset/energy のみ（fzero~ + fluid.onsetslice~/ampslice 連結・楽器別マイク）。クロック = **オペレーター/ドラマーのタップ → Bridge → エンジン経由で Link set**（#283 実証済み経路の再利用）。位置 = **オペレーターのセクション送り（TouchOSC/フットスイッチ）+ エンジン bar counter**。
- **新規開発**: Bridge の小節窓集約（spec §3.1 どおり）+ タップ/セクション送りの OSC 受け。Max パッチは既製オブジェクトのみ。
- **根拠**: 数十年の実戦パターンそのもの（human-in-the-loop）。spec §10.6 推奨案 (a)+(b) の素直な実装。「Vamp till cue」の直接転用。
- **リスク**: 極小。機械は追従者寄り（美学的判断は owner）。オペレーター負荷が集中（盲点5）。
- **工数**: 1-1.5週。**これが床。全ての他案はこの上に積む。**

## 案2: Confidence-Gated Auto Beat（自動ビート補助 + 信頼度ゲート + タップ上書き）

- **耳**: 案1 に自動テンポ推定を**補助**として追加。第一候補 = **vb.aubio~ の tempo メソッド**（ARM ネイティブ・要スパイク: buffer~ ベースの逐次解析が実用レートで回るか）。第二候補 = BeatNet を Python daemon 化し**内部確度（CRNN 活性化）を fork で露出** → OSC。
- **ゲート**: 推定テンポとタップ/現行テンポの乖離 + 確度低下で**追従凍結**（spec §2 の信頼度ゲート = 結合度 0）。タップは常に上書き権限。
- **根拠**: Music Plus One / Dannenberg 系の「自動 + 人間ゲート」= 最も実証されたアーキパターン。
- **リスク**: ジャズでの自動トラッキング実戦報告ゼロ（本調査確認）→ **だから補助に限定**。BeatNet fork は追加工数。
- **kill-criteria**: W5 までにリハ音源で 8 割の小節で ±5% 以内のテンポ推定が出なければ**タップのみに退行**（案1 に畳む・手戻りゼロ）。
- **工数**: +1-2週（vb.aubio~ 経路なら短い）。

## 案3: MIDI Ears / Voyager 型（シンボリック側路）

- **耳**: guitar = **Jam Origin MIDI Guitar 2**（本番は MG3 でなく 2・ベンダー推奨に従う）→ ノート/和音イベント。trumpet = クリップマイク（DPA 4099 系）+ **fluid.pitch~（confidence 付き）→ MIDI 化**。drums = トリガー任意（同時打点欠落の仕様を認識の上）。
- **効果**: LLM 文脈が「onsetCount=7」から「D-F-A-C を弾いた」に変わる = semantic gap を側路で越える。和声の耳（案4）の入力品質も桁上げ。
- **根拠**: Voyager 40 年の実戦前例（単音側）。
- **前提確認（今すぐ・調達前）**: ①ギタリストの楽器仕様（スチール弦か/エレクトリックか/装着許容）②MG2 の Apple Silicon 実機動作 ③密なジャズヴォイシングでの精度（実機で試す以外に確定手段なし）。
- **kill-criteria**: W4 末までに実機で「コンピングの和音が root+quality レベルで概ね取れる」が確認できなければ guitar は audio 特徴量（案1）に退行。trumpet 側は独立に判断（成立可能性が高い）。
- **工数**: 1-2週 + 調達。**調達リードタイムがあるため採否判断は最速で。**

## 案4: Harmonic-Fit Position Verifier（和声一致度による位置検証）

- **耳**: 小節窓 pitch-class ヒストグラム（入力 = 案3 の MIDI があれば最良 / なければギター専用マイクの fluid.chroma~）を、リードシート既知の**期待ハーモニー（厳密コードでなく調域/ダイアトニック集合の粗いアンカー）**と Fujishima コサイン類似度で照合。数小節の移動平均で「位置確度スコア」を出し、**低下時にオペレーターへ警告**（自動修正はしない）。ヴァンプ対応は Nakamura の停止×再開確率パターンを小節レベル HMM に借用。
- **実装位置**: **Max でなく Bridge 側（TypeScript）**。純関数（PC ヒストグラム × テンプレート類似度）なので**オフラインでリハ録音に対して先にテスト可能**（= 耳なし検証の資産再利用思想）。
- **根拠**: 構成要素は全て枯れている。ATTYA 固有の混同マップ（盲点7）を先に機械計算して脆弱遷移を特定できる。
- **リスク**: **統合は前例ゼロの新規設計**。リハーモナイズとドリフトの識別不能という構造的限界（粗アンカーで緩和するが消えない）。ピアノ支配問題（案5 が前提)。
- **kill-criteria**: W5 までにリハ録音のオフライン再生で「故意にずらした位置を 8 小節以内に検出」できなければ**警告レイヤーごと落とす**（案1 の位置管理は無傷 = 手戻りゼロ）。
- **工数**: 2-3週（オフライン検証込み）。挑戦枠。

## 案5: Self-Listening Bleed Mask(自己聴取・被りマスク)

- **内容**: ①物理定石（クリップ/高指向性マイク + ゲート）を土台に、②**ピアノ MIDI onset/duration を Bridge に共有し、ピアノ発音と重なる解析窓の人間楽器特徴量の信頼度を機械的に下げる/マスクする**。③適応フィルタ（RLS/Wiener）は本番では**やらない**（ライブ実証なし・音楽信号での漏れ削り事故の文献あり）。
- **根拠**: 加害源 MIDI 既知は文献にない好条件。信号処理ゼロの時刻ゲーティングなら実装は小さく副作用もない。
- **効果**: 案1-4 全ての耳の信頼性を底上げする横断レイヤー。
- **工数**: 0.5-1週（Bridge 側タイムスタンプ照合のみ）。**費用対効果最良。**

## 案6: Explicit-Position LLM Context（形式は与える・耳はテクスチャ専念）

- **内容**: LLM 側の設計原則を確定する案。①**形式内位置（コーラス n・セクション A2・小節 5/8・現行コード）は必ず明示ラベルで注入**（特徴量からの推論に期待しない — ReaLJam の実証を教訓に）②プロンプト = static prefix（スキル + リードシート .orbs + 演奏指示）+ rolling suffix（位置ラベル + 直近 2-4 小節の特徴量表 + .orbslog 末尾）で**キャッシュ最適化**（Anthropic 公式指針どおり）③出力スキーマは OrbitScore DSL に固定（記法バイアス回避）④特徴量エンコーディング（表 vs 要約）は W4 に小さく A/B。
- **根拠**: 全て一次資料（ReaLJam 評価・Anthropic 公式・JAMMIN-GPT）に接地。
- **工数**: pi ハーネス実装（W-Runtime）の中で吸収可能。**追加コストほぼゼロ・全案と直交。**

## 案7: External Analysis Daemon（解析を Max の外へ）

- **内容**: Max は収音 + ルーティング + 最小 onset に徹し、重い解析（chroma/分類/テンポ補助）を**外部プロセス**に出す。選択肢 A = Python（aubio/BeatNet/librosa）。**選択肢 B = Rust: 既存 `orbit-audio-verify` の計測プリミティブ（onset/RMS/帯域エネルギー等）を realtime daemon 化**（資産再利用・dep 最小・既にテスト済みの語彙）。OSC/WebSocket で Bridge へ。watchdog + 自動再起動（node.script の再起動機構 or 自前 supervisor — エンジンの EffectChildSupervisor パターンを流用可）。
- **根拠**: 査読論文に採用実例・クラッシュ隔離が構造的に得られる・**録音に対するオフライン再現テストが可能になる**（Max パッチはテスト困難、外部デーモンは CI 可能）。
- **リスク**: プロセス間配線が増える。B は engine チームの工数を WCTM に割く判断が要る。
- **工数**: 1.5-2週。案2/案4 の実装先としても機能（vb.aubio~ が倒れたらここに逃がす）。

## 案8: Neural Ears in Max（nn~ / Data Knot）— 非推奨（検討済み）

- **内容**: nn~ で TorchScript 解析モデル、または Data Knot のドラム分類。
- **非推奨の根拠**: nn~ は生成系（RAVE）の実戦は豊富だが**解析系の公開モデル不在** = 自前 TorchScript 化の工数 + 前例なし。Data Knot は **alpha・M1 クラッシュ報告（開発者認知）** = クリティカルパス禁止。5 週間の制約と手戻り最小方針に不適合。
- **再訪条件**: 本番後の作曲ハーネス期に、時間制約なしで。

## 案9: Score-Following 導入（Antescofo）— 非推奨（検討済み）

- **非推奨の根拠**: 保守は継続しているが、**自由即興の hands-free 実行機能はない**（設計者明言）・反復/スキップに弱い（Nakamura 比較実測）・「似た繰り返し区間での誤検出」は AABA の教科書的リスク・ライセンス形態未確認。「入れれば位置が分かる」は成立しない = 期待値と実態の乖離が最大のツール。
- **再訪条件**: 10 分の形式に through-composed（譜面固定）セクションを設ける演出判断がなされた場合、その区間限定で。

## owner 決定事項（実装着手前に確定すべき 4 点）

- **D1 自律度**（spec §10.6 の保留事項そのもの）: 位置は「与える」（オペレーター主・推奨）か「検出させる」寄りか。案4 を警告レイヤーに留めるか、位置決定に関与させるか。
- **D2 テンポ権限の向き**: spec「Max → Link 駆動」vs 実装済み #283「エンジンがリーダー」。**推奨 = タップ/トラッカー入力を Bridge/エンジン経由で Link に流す**（実証済み経路再利用・Max からの直接 push は不安定と確認済み）。spec §2 の改訂が必要。
- **D3 ギター側路**: ギタリストの楽器仕様確認 + MG2 調達の可否（費用 $150 + 実機検証時間）。W3 中に。
- **D4 ドラムセンシング**: マイクのみか、トリガー併用か（同時打点欠落の仕様を許容するか）。Max オペレーター協議と合わせて。
