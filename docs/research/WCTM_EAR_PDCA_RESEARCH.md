# Research: 耳の PDCA — sideman × OrbitScore 資産による機械的検証ループ

## 調査日
2026-07-04

## 調査目的

owner 提起（2026-07-04）の 4 仮説を検証し、実装提案に落とす:

1. **sideman を合成 ground-truth 生成器**として使えば、耳（特徴抽出・位置検証・和声一致度）の PDCA を人間の耳もライブバンドも無しで機械的に回せる（orbit-audio-verify「耳なし検証」哲学の聴取側への拡張）
2. **一曲特化**（ATTYA 等）から始めて精度を上げ、人間がレパートリーを増やすように曲ごとのプロファイルを足す — 大量学習データでなくアルゴリズム的 PDCA で。IRCAM が諦めた汎用ジャズ ACE でなく「曲既知・合成校正」という別問題設定なら勝ち筋があるのでは
3. **OrbitScore DSL を理解の基盤**に: 生成器の入力も耳の出力ラベルも LLM スキルも同一の度数語彙
4. 「**ジャズ的な音の空間情報**」の捕捉（多義的 — 解釈候補ごとに評価・要 owner 確認）

前提: [WCTM_MACHINE_LISTENING_RESEARCH](WCTM_MACHINE_LISTENING_RESEARCH.md)（サーヴェイ）と [WCTM_LISTENING_IMPLEMENTATION_PROPOSALS](WCTM_LISTENING_IMPLEMENTATION_PROPOSALS.md)（実装案 10・W3-W8 ロードマップ）の**上に積む**。既存ロードマップのゲートは置き換えない。

## 調査方法

deep-research ハーネス（Workflow・**Sonnet 5 × 16 agents**）: sideman リポジトリ直接調査 → 4角度並列スイープ（sim-to-real / 曲既知聴取 / PDCA 機構 / 音空間）→ load-bearing claim 敵対的検証 8 件（**CONFIRMED 3 / REFUTED 5**）→ 提案起草 → **批評（22 攻撃・high 7）→ 改訂**の 2 周。owner 指示どおり一度の調査で終わらせず批評・改訂を機械的に組み込んだ。

> REFUTED の主な成果: ①「sideman にバッチドライバは未実装」→ **誤り。`headless-backend.test.ts` / `sim-log.test.ts` に実装・検証済みのドライバが既に 2 種存在**（提案の工数が下がる方向の訂正）②「score-only モデルは合成→実転移で劣化ほぼ無し」→ 小編成（≤5 楽器）限定の現象と訂正 ③ Kritsis 2021 は「曲ごと較正」でなく汎用単一モデルと訂正。

## sideman 実態（リポジトリ直接調査の要点）

- **リアルタイムの「プログラマブルなジャズ伴奏楽器」**（リード + pad + ベース + ドラム生成・研究/演奏用・プロダクトではない）。**将来の Max/OrbitScore DSL 移植を意図しコアはフレームワーク非依存 TS**。
- 進行は `harmony.ts` に **`[rootPc, quality, bars, functionTag]` タプルでハードコード**（Blues・Rhythm changes・枯葉・**All The Things**・Donna Lee 等の実在スタンダード）。外部リードシート入力経路は無い。
- 出力 = ビート基準 `NoteEvent`（pitch/onsetBeat/durBeats/vel/voice/source）。**MIDI/audio ファイル書き出し機構は無い**（SF2 WebAudio / WebMidi / Headless の 3 バックエンド・全てリアルタイム）。
- **意図的に非決定論的**（`Math.random()` 直呼び・シード注入不可・devlog に「シード固定比較は不要」の設計判断）。ただし**1 回の実行結果を凍結すれば決定論的な回帰フィクスチャになる**ため合成コーパス生成のブロッカーではない。
- **`NoteEvent.source`（human/agent/replay）はコード内コメントで OrbitScore の `evalSource` 概念を明示参照** — 仮説 3 の橋渡し設計は sideman 側に既に部分的に存在する（発明でなく確認）。
- **UNLICENSED・private・owner IP**（auto-deploy 無効化済み）→ sideman 由来データの扱いに全案共通のガバナンス境界が要る（後述）。

## 結論サマリ（勝ち筋と限界の切り分け）

1. **仮説 1 は「記号/ラベル層」に限って成立し、生音特徴量の較正には転用できない。** sideman の合成レンダ（SF2・量子化 NoteEvent・クリーンミックス）は、本番の耳が直面する実会場の問題（クロス被り・部屋・swing のミクロタイム）を含まない。合成 PDCA が正しく較正できるのは**和声一致度位置検証（実装案4）と LLM 文脈ラベル（案6）の記号層のみ**。クロック（案1/2）・bleed マスク（案5）・テクスチャ（案3 audio 経路）の閾値は合成では埋まらない。
2. **sim-to-real の定量的裏付け**（外部一次資料・敵対的検証済み）: 合成コード認識 AAM は合成テストで 97% でも実音楽への転移はジャンル依存で大幅劣化（本計画に最も近い直接前例）/ ドラム転写では**合成データの多様性が量より効く**（プリセット 8→512 でギャップが実測で縮む）/ ピアノ転写は録音条件だけで **-16.55 F1** 崩壊（音響条件過適合は合成なしでも起きる）。→ **耳ロジックを記号/構造シグナル側に寄せるのが最良の緩和**（本調査の最重要 design implication・仮説 2 の DSL 基盤方針と整合）。
3. **一曲特化の耳には数十年の前例がある**: Raphael の Music Plus One は**曲ごとに HMM を訓練する per-piece 較正**そのもの。ただし前例が耐えるのは**タイミング/構造逸脱まで**であり、**リハーモナイズ（和声的置換）への耐性を実証した前例は皆無** — 一曲特化でもこの限界は消えない（粗い調域アンカー + 小節集約の緩和は既存計画どおり維持）。
4. **「合成音源 = ground truth」は MIR の確立手法であり新規性はない**。新規性があるのは (a) **生成器と検証器が同一の度数語彙（OrbitScore DSL）を共有する**構成 (b) orbit-audio-verify の**検証文化**（GRM 独立・純関数スコアボード・固定許容値・凍結フィクスチャ）の聴取側移植。ただし**スコアリング層そのものは net-new**（再利用できるのは文化と器）。
5. **循環の罠（sideman で校正し sideman で評価）は実在の測定された現象**（deepfake 検出器の in-domain >90% → 未知生成器で崩壊等）。対策 = **独立ホールドアウト（owner 実演奏の簡易録音）を必須とし、較正セット単体の精度を内部判断にも使わない運用規律**（案E）。
6. **「音空間」の 3 解釈**（和声空間 / 音域・テクスチャ空間 / 物理音場）のうち、**近期に低リスクな較正経路があるのは和声空間のみ**。テクスチャ空間（spectral centroid/roughness — IRCAM Orchidée 系の枯れた表現）は post-concert パイロット（案G）、物理音場は既存計画の bleed 対策（案5・実測）に帰着。

# Part I: 検証済み主要知見（角度別・要点）

## A. 合成 ground truth と sim-to-real

| 知見 | 根拠 |
|---|---|
| 合成コード認識（AAM 3000曲・完全ラベル）: 合成テスト Root 97.47% → 実 pop に転移は妥当・実クラシックで急落（+1pp のみ）。**生成器の作曲慣習が認識能力に漏れる** | arXiv:2508.05878（本計画の最直接前例） |
| ドラム転写: 実データが常に最良だが、**合成の多様性**（プリセット 8→512・伴奏あり・human MIDI）がギャップを実測で縮める。「サイズでなく多様性」 | arXiv:2407.19823 |
| ピアノ転写: 録音条件の狭さだけで 97.32→80.77 F1。**音響 augmentation 訓練で劣化 19.2→2.5 pt** | arXiv:2402.01424 |
| 合成のみ訓練 + adversarial domain confusion で実転移ギャップ縮小（大ギャップには限界） | arXiv:2312.10402 |
| **score-only（記号のみ）モデルの転移劣化ほぼ無しは小編成（≤5 楽器）限定**（検証で訂正） | arXiv:2503.07352 |
| 循環の罠は命名・測定された現象（LLM 合成ベンチの bias factor / deepfake 検出器の cross-generator 崩壊） | arXiv:2409.11968 他（検証済） |

## B. 曲既知・一曲特化の聴取

- score-informed 分析（分離/転写/整合）は成熟分野で、**既知シンボリック情報は一貫して精度を上げる**（DECIBEL: TISMIR 10.5334/tismir.81・一次確認）。ただし全ての利得は「**音源が参照に忠実に従う**」条件付き。
- ジャズ ACE が pop/rock 比で実質的に難しいことは JAAH（ISMIR 2018）一次資料で確認。
- **Music Plus One（Raphael）= 一曲特化耳の実証前例**（曲ごとに HMM + 潜在テンポ過程を訓練・リハ録音で較正）。
- **前例が耐える逸脱はタイミング/構造（テンポ・ミス・リピート/スキップ）のみ。リハーモナイズ耐性を実証/ベンチした前例は本調査でも不在**。

## C. PDCA 機構（自社資産）

- **バッチ駆動は既に可能**: `headless-backend.test.ts` / `sim-log.test.ts` + `analyze-log.mjs` が実装・検証済みの駆動実例（検証で「未実装」claim を訂正）。新規に書くのは薄い凍結スクリプトのみ。
- **オラクルの指標（コード一致 precision/recall・位置ドリフト小節誤差・境界誤警報率）は orbit-audio-verify に現存せず net-new**。再利用は文化（GRM 独立・純関数・固定許容値・凍結フィクスチャ）。
- Pitch DSL v1.1 は進行記述の主要プリミティブ（度数スタック・chords stdlib・`.root(n)`・`global.key()`）を備えるが **Phase 1 未完了**（検証で「既に書ける」を「プリミティブは有るが統合未完」に訂正）。
- **既存 W3-W8 ロードマップのゲートはどれも合成 PDCA を前提にしていない** → 本調査の成果は既存計画の**置換でなく追加の検証ケース**として位置づける。

## D. 音空間の表現

- chroma/HPCP・spectral centroid・roughness = 非深層学習の枯れたアンサンブル・テクスチャ表現。IRCAM Orchidée/Orchidea = 心理音響基準の低次元 timbre-space の production 前例。
- 実時間ジャズの blind 和声推定は IRCAM 自身がやっていない（Antescofo/OMax/ImproteK は和声グリッド既知が前提）— 既存サーヴェイの結論を別角度から再確認。
- blind ビートトラッキングは 2021-2025 の深層学習系で進展があり「abandoned」の強い言い方は不正確（ただしジャズ実戦の前例不在は変わらず）。

# Part II: 提案 A-G（批評→改訂済み）

> **全案共通のガバナンス境界**: sideman 由来データ（fixture・ラベル・few-shot 例）は社内境界内のオフライン検証・教材生成にのみ使用。成果物は**静的スナップショットとして凍結**し、本番ランタイム（pi ハーネス/daemon）に sideman への実行時依存を作らない（UNLICENSED/private IP）。
>
> **master switch**: 以下の pre-0807 判定は全て「**ATTYA が本番セットリスト曲である**」という未確認の前提に立つ。owner 確認が最優先（確認事項 §先頭）。非該当なら A/C/D/E/F は post-concert へ一括降格。

## 案A: 単曲の OrbitScore DSL 手動移植（dog-food）[pre-0807]
ATTYA の進行を**ツールを介さず** Pitch DSL v1.1 の度数語彙で手書き。目的を二層分離: (1) Pitch DSL Phase 1 の dog-fooding（ATTYA が本番曲か否かと独立に価値）(2) WCTM 本番チャート整備（本番曲の場合のみ）。
**最小実験**: 最初 8 小節を手書きし sideman 実データ由来 quality が chords stdlib で表現できるか確認（1日）。
**kill**: Phase 1 が 0807 前に使用可能にならなければスキップ。ATTYA 非該当なら (1) のみに縮小。

## 案B: レパートリー拡張用の半自動進行コンバータ [post-concert]
sideman `REAL_PROGS` → OrbitScore 度数記法の機械変換 + 人手レビューのハイブリッド（トライトーン等距離の曖昧性は声部進行規則なしに機械解決できないと実データで確認済み）。stdlib 拡張はレキサー/パーサーに触るため**委譲規律上 Opus 直列** — Pitch DSL Phase 1-3 を阻害しないことが着手前提。
**最小実験**: Rhythm changes の既知反例を機械変換し機械化可能範囲を列挙（1-2日）。
**kill**: 全 REAL_PROGS 網羅変換 + 無作為 20 件レビューで反例率 2 割超なら機械化を諦め案A の都度手書きへ。

## 案C: オフライン検証への合成フィクスチャ追加 [pre-0807 = 凍結まで]
既存 sim-log ドライバを 1 回実行し ATTYA 演奏を**凍結**（半日）。W4-W5 オフライン検証への**実接続は D1（owner 決定・PR #372）確定後** — D1 が実装案4 の実装先（Bridge TS / Rust daemon）を決めるため、ゲート順序を逆転させない。
**リスク**: 本番 Bridge が受けるのは Max 経由 OSC 特徴量（ジッタ・欠落あり）で sim-log のクリーン NoteEvent と形状が異なる → **OSC 劣化版 fixture（信頼度低下・onset 欠落注入）を併設**。
**kill**: 時間表現の整合アダプタが 1 日超なら先送り。**検出器不在・D1 未確定の間、この fixture のスコアを内部 go 判断に使わない**。

## 案D: 記号レベル位置一致度オラクル [pre-0807 = 単体テストまで]
orbit-audio-verify の検証文化を記号層に拡張した**スコアボード（純関数・固定許容値）**。pre-0807 はオラクル・ロジックの単体テストに限定（D1 非依存で独立に価値）。ラベルは現状 sideman functionTag/コード表記を直接使用 — **仮説 3（DSL 共通基盤）はこの段階では未検証**と明記し、Phase 1 完了後に `.orbs` パース経由へ切替を検討。
**最小実験**: 完全一致 / 1小節オフセット / 誤警報のみ / **正当なリハーモナイズを誤検出しない** / 無音小節 — の 5 合成ケース + **量子化クリーン版 vs タイミング揺らぎ（±数十ms）注入版の劣化差分報告**（1日）。
**kill**: 消費する検出器の計画が無ければスタブ止まり。リハーモナイズ誤警報が許容外なら粗アンカー緩和を検証してから採用判断。

## 案E: 独立ホールドアウト = 循環の罠対策（運用規律）[pre-0807 必須]
Corpus A = sideman 生成（較正用）と別に、**Corpus B = owner 自身の実演奏の簡易録音（スマホ可・15分規模）**を独立ホールドアウトとして確保。**先送り不可の規律**: sideman 単独の精度を、Corpus B 比較を経ないまま**内部の意思決定（kill 判定・go/no-go・owner 報告）に使うことを禁止**（対外公表だけでなく内部判断にも適用）。
**kill**: 検出器不在の間は録音確保のみで実比較は先送り可。規律自体は即時適用。

## 案F: functionTag ベース LLM few-shot 教材生成 [pre-0807]
sideman の functionTag（tonic/subdominant/dominant）から「小節N・機能・コード → 説明」の few-shot 例を .orbslog 語彙で作成し、pi ハーネスの和声位置言及の品質を無例示ベースラインと比較。**functionTag は設計者の解釈であり ground truth にしない** — owner 見立てと食い違う小節は除外/注記。
**最小実験**: held-out 10-15 小節・固定採点基準で比較（半日-1日）。
**kill**: 有意差なしなら即打ち切り（コスト極小）。

## 案G: register/texture 空間 ear パイロット [post-concert]
「音空間」= テクスチャ解釈の場合のパイロット。**sideman にオフラインレンダ機構が無い**ため、まず SF2→WAV キャプチャ手段の実現性のみ検証（代替 = headless Chromium 録音の工数込み・半日-1日）。有意味な特徴量は **Max 側（fluid.spectralshape~ 等）で同一素材を再計算し数値整合を確認**してから採用。
**kill**: キャプチャに 1 日超の追加実装が要るなら保留 / owner が texture 解釈でないと明言したら取り下げ / 合成内でさえ差が出なければ終了。

## 推奨シーケンス

- **Day 0（最優先・master switch）**: ATTYA が本番セットリスト曲かを owner に確認。
- **Day 1（並列・D1 非依存の範囲のみ）**: 案A（8小節手書き）+ 案C（fixture 凍結のみ）+ 案D（オラクル単体テスト）+ 案F（few-shot 比較）— 全て 1 日以内・独立採用可。
- **Day 1-2**: 案E の録音確保を並行依頼。
- **判断ゲート**: D1 確定（PR #372 の owner 決定 4 点）までは案C/D の実データ本接続に着手しない。D1 で実装案4 の実装先が定まった時点で「本番の実コードパス」への接続に入る。
- **post-concert**: 案B（コンバータ）・案G（texture ear）・**フル PDCA 最適化ループ本体**（sideman バッチ生成 → パラメータ探索）は本番後に、pre-0807 の薄いスライスの知見を踏まえて設計。

## 仮説の判定（改訂後の正直な位置づけ）

| 仮説 | 判定 |
|---|---|
| 1. sideman で耳の PDCA | **記号/ラベル層に限定して成立**。生音特徴量の較正には不成立（合成が本番の音響問題を含まない）。フルループは post-concert 研究トラック |
| 2. 一曲特化から | **前例あり（Music Plus One）で妥当**。ただしリハーモナイズ限界は一曲特化でも残る |
| 3. DSL を理解基盤に | **方向は資産と整合**（sideman 側に evalSource 参照が既在・sim-to-real 緩和とも一致）だが、**本提案群では未検証**（現段階のラベルは sideman 直結・Phase 1 完了後に `.orbs` 経由へ切替検討） |
| 4. 音空間の捕捉 | 3 解釈に分解。**和声空間のみ近期経路あり**（実装案4 に帰着）。texture = 案G（post-concert）・物理音場 = 既存 bleed 対策（実測） |

1. 【**master switch**】ATTYA（等の例示曲）は本番セットリスト曲か研究例示曲か — 案A/C/D/E/F の pre-0807 妥当性を決める。

   **設計上の帰結（曲タイプで耳のアーキが分岐する）**:
   - **Option 1 スタンダード（リードシート有）**: 耳 = 和声一致度位置検証（案D/実装案4）。sideman PDCA フル適用（枯葉/ATTYA/Rhythm changes はプリセット既在）。弱点 = リハーモナイズ限界・AABA 反復混同。
   - **Option 2 リフベース・フリー形式**: 耳 = **リフ/テーマ検出**（onset パターン + ピッチ輪郭テンプレート照合）— 和声推定問題を「解く」のでなく**「消す」**（IRCAM が諦めた点の側路）。形式 = 粗い状態機械（テーマ→フリー→回帰→終止）で位置問題が激減・「Vamp till cue」運用と同型。**sideman は進行ベースで生成器不適合 → OrbitScore engine 自身の決定論レンダがリフの perfect ground truth**（orbit-audio-verify 直結・資産再利用むしろ強化）。他者作品は権利確認要 → **オリジナルのリフ曲を最初から .orbs で書けばテーマ = ground truth そのもの**（「機械のために書かれた曲」という作品コンセプト）。フリー区間は LLM 文脈がテクスチャのみに薄くなる点は演出判断。
   - **Option 3 ハイブリッド**: リフ = 位置のハードアンカー（ドリフトをリセット）+ リフ間の進行セクションのみ案D を限定適用 — 位置検証の最大弱点（ドリフト累積）をリフが構造的に抑える。
   - 曲タイプ決定までの実務: 案D のオラクル単体テスト・案E の規律は**両オプション共通で有効**（先行可）。案A の手書き移植と案C の fixture は Option 1 確定後。Option 2 に傾く場合はリフ検出の最小スパイク（engine レンダしたテーマの self-detection）を先に立てる。
2. D1（自律度等・PR #372 の owner 決定 4 点）の確定時期 — 0807 後にずれる場合、案C/D の本接続は事実上 post-concert。
3. 「音の空間情報」の意図 = 和声位置 / 音域・テクスチャ / 物理音場のどれか（複合か）— 案G の投資判断待ち。
