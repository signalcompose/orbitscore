## 1b. 🔴 機能の持ち方 — コアは最小に保ち、機能はプラグインで足す（両側に適用される原理）

**これは新しい決定ではない。** 既にあった立場を、地図の上位に明文化する（owner 2026-09-03「**オーディオエンジンのコア機能以外の
プラグイン化・モジュール化や DSL のプラグイン化などで拡張性を担保してかつライセンス問題を解決しましょう**、という話になったはずです」/
「**DSL も同じようにプラグインで機能が追加できるようにしよう**」）。

### 1b.1 既にある根拠（引用）

| 出典 | 記述 |
|---|---|
| `POST_2.0_PLUGIN_STRATEGY.html` §1（2026-06-30・#362） | 業界規格の採用は「leverage（てこ）」。「規格に乗れる所は乗り、**自分たちにしか作れない fundamental（audio DSL / scheduling / engine の差別化要素）に希少な開発リソースを寄せる**」。「以降の §2–§7 はすべてこのメタ原則のインスタンス」 |
| 同 §2「Engine は fundamental に保つ — effects/instruments は plugin」 | 「fundamental engine（audio DSL + scheduling + plugin host substrate + DSL→plugin 制御）に **effects/instruments の DSP を抱え込まない。1st-party を作るときも engine 内ではなく別の CLAP/VST plugin として作る**」「帰結: engine に compressor/limiter/normalizer/EQ 等の DSP を実装する提案はしない」 |
| 同 §5 | 「LinkAudio は**出力の 1 つ**（銀の弾丸ではない）」 |
| SC.10.8（2026-08-27） | 「OrbitScore が提供する 1st-party のエフェクト / 楽器は、**engine に DSP を抱えず、標準プラグインとして提供する**」 |
| #292 §1（Epic・唯一の不変条件） | 「**engine の依存を permissive に保ち、GPL は隔離する**」 |
| #671 冒頭（owner 2026-09-02） | 「**DSL もプラグイン化して拡張性をあげたい**」「OrbitScore DSL Plugin みたいな独自のもの」「そうすると **LinkAudio も Link も疎結合になります**」 |

### 1b.2 1 つの原理が両側に現れる

| 側 | 原理の現れ | 地図の節 |
|---|---|---|
| **オーディオ** | **出口の一般化** — `output` はライン上の要素。LinkAudio は「出口の 1 つ」であって特別なバスではない | §4.A.1 / §4.A.2 |
| **オーディオ** | **標準エフェクト / 楽器は CLAP で同梱**（engine に DSP を持たない） | §4.B（#669・Patina）/ SC.10.8 |
| **オーディオ** | **engine 内の機能をプラグインへ切り出す**（LinkAudio egress → CLAP・Link テンポ → DSL Plugin・ユーザー DSP → in-process WASM） | §4.E 切り出し表 |
| **DSL** | **語彙をプラグインで足す**（DSL Plugin: 語彙 + 実装 + 型 + docs + テストを 1 単位で登録） | §4.E（#672 契約 → #671 実装） |
| **DSL** | **LLM から発見できる**こと（プラグインが足した語彙が MCP の `get_dev_doc` / 補完 / 診断に届く） | §4.E（#672 A5）/ §4.K（#615） |
| **配布** | **ライセンス問題は「隔離」ではなく「外へ出す」で解ける** — engine 本体に GPL が残らない | §4.J（#321 / #670） |

**ライセンスは目的ではなく帰結**である（owner「拡張性を担保して**かつ**ライセンス問題を解決」）。#321 の「feature-gated 薄 crate で隔離」は
拡張点が無かった時点での解であり、#671 の拡張点が入れば同じ機能が**プラグインとして engine の外**に置ける（#671「engine は Ableton Link を
一切知らない。#670 の GPL 論点が構造的に解消する」）。

### 1b.3 ✅ 裁定済み: 「コア」は**先に定義しない。境界を引いた残りがコア**（owner 2026-09-03）

`PLUGIN_STRATEGY` §2 は fundamental engine を「**audio DSL + scheduling + plugin host substrate + DSL→plugin 制御**」と定義した（2026-06-30）。
しかし #671 は **audio DSL の語彙そのものをプラグインで足す**と言っており、この定義の「audio DSL」の内側に線が要る。#672 A3 は
「core の語（`tempo` `beat` `length` `start` `stop` `run` `loop` `play` `instrument`）が『何を提供するか』がそのまま拡張点になる」と
書くが、**これは候補であって確定ではない**。

🔴 **owner 裁定（2026-09-03）— 定義の順序が決まった:**

> **コアという定義があるわけではなくて**、VST, CLAP, 標準プラグイン、DSP プラグイン（Ableton Link みたいなやつとか）、
> 多分**今後標準シンセプラグインとかも出てくる**でしょう（MIDI 以上の表現力を求める場合に）、加えて DSL プラグインなど、
> **そういう境界線を作っていくと自然と DSL 部分、オーディオエンジン部分のコアが決まってくる**のでは？

**「コアとは何か」を先に決めてから外を切り出すのではない。外側の境界を 1 つずつ引いていくと、残ったものがコアになる。**
したがって #672 は「コアの定義待ち」で止まらず、**引くべき境界を順に規定すればよい**。

| 引く境界 | 状態 |
|---|---|
| **VST3 / CLAP**（3rd-party） | 既存（out-of-process child） |
| **標準プラグイン** | 既存（`orbit-std-gain`）/ #669 で compressor 等 |
| **DSP プラグイン**（Ableton Link のようなもの） | 🔴 **未規定** — #672 の主眼の 1 つ。LinkAudio をここへ出すとライセンス問題も同時に解ける |
| **標準シンセプラグイン** | 🔴 **今後出てくる**（owner: MIDI 以上の表現力が要る場合・#497 と接続） |
| **DSL プラグイン** | #671 |

判断材料として本地図が提供するのは §4.E の切り出し表（何が engine の中にあり、どの種に出せるか）である。

**この原理の適用順**（§2 の全体図と同じ）: 出口の一般化（§4.A.1）と契約（#672）が先、個別の切り出し（LinkAudio CLAP 化・Link DSL Plugin 化・#670）は後。

#### 4.A.1 🔴 モデル: 出力はライン上の要素である — 機能の持ち方の話（owner 2026-09-03）

> 例えば Output にスルーがあると同じ音を `gain.output.output` みたいに1つのシーケンスを複数のアウトに向けたり、`gain.linkaudio.effect.gain.output` みたいにエフェクト前の音を LinkAudio に送ったりとかできますよね。そういうことを言ってます。

##### 4.A.3.1 🔴 owner 裁定（2026-09-03）: 宛先は**エンドポイント宣言**にする

数値 render bus のままだと **owner が求めたプレースホルダ**（上書きせず版を残す）を書く場所が無い。3 案を出して **(c) を採用**:

| 案 | 書き方 | 代償 |
|---|---|---|
| (a) 番号のまま | `output(3)` | ファイル名が DSL の外。**プレースホルダを書けない** |
| (b) ファイル名を直接 | `output("stems/kick.wav", thru: true)` | 簡単。**SC.2.1 の「宛先はすべて宣言されたノード」から外れる** |
| **(c) エンドポイント宣言** ✅ | `var stem = mix.render("stems/kick_%v.wav")` → `output(stem)` | 宣言が増える → **テンプレートで解消**（下） |

```orbs
var master = mix.output(1, 2)                   // 物理アウト（SC.2.1・既にある）
var stem   = mix.render("stems/kick_%v.wav")    // ファイル（新設）

kick.output(stem, thru: true).output(master)
```

**宛先がすべて「宣言されたノード」に揃う**（SC.2.1 規範 (4)「バス自身もレシーバ」と同じ軸）。番号もファイル名も物理アウトも特別扱いされない。

🔴 **トラック別レンダリングはテンプレートで解く。** (c) の素朴形はトラック 30 本で宣言 30 行になり、`output(1)` から明確に後退する:

```orbs
var stems = mix.render("stems/%n_%v.wav")   // %n = そのシーケンスの名前

kick .output(stems, thru: true).output(master)   // → stems/kick_001.wav
snare.output(stems, thru: true).output(master)   // → stems/snare_001.wav
```

✅ **`%n` は実装可能**（2026-09-03 実測）: シーケンスは変数への代入時に名前を受け取る（`sequence.ts:197-200` `setName` →
`stateManager.setName` + `global.registerSequence`）。エラー文言も既にそれを使っている（`sequence.ts:354`）。**追加の記法は要らない。**

**合流の規則は 1 本**: 🔴 **解決後のパスが同じなら合算**（#611 決定 1 と同じ規則）。同じノードでも**テンプレートなら分かれ、固定名なら混ざる**。

**pre / post fader が無料で解ける**: DAW が書き出し時に聞いてくるオプションは、**タップの位置がそのまま答え**になる
（memory `audio-line-order-is-the-model`）:

```orbs
kick.output(stems, thru: true).effect(comp).output(master, db: -6)   // 生（pre）
kick.effect(comp).output(stems, thru: true).output(master, db: -6)   // comp 後（post）
```

#### 4.P.1 DSL 表面 — owner のスケッチ（2026-09-03・確定ではない）

> サンプリングも**インプットからオーディオが渡される DSL で表現されるべき**なのでは？
> `input.rec(オーディオの play と似たように書くとパンチインアウトとかも表現できる？).effect` のように**順番でドライの録音かウェットの録音かも決められる。**（owner・逐語）

**スケッチであって確定ではない**（§4.A.1 の `thru` と同じ扱い。DSL の表面は owner 確認を経て確定する — memory `dsl-surface-needs-owner-confirmation`）。

**帰結（§4.A.1 の規則が入力側にも効く）**: **`rec` はライン上の要素であり、位置が dry / wet を決める。** 専用のフラグは要らない — `output` のタップ位置がチェーン上の位置で決まるのと同じ規則（#649 §7.6「置いた位置で役割が決まる」）:

```js
input.rec().effect("Reverb")     // ドライを録る（録音の後にエフェクト）
input.effect("Reverb").rec()     // ウェットを録る
```

**パンチイン / アウト = `play()` と同じパターン**（owner の提案）: `input.rec(1, 0, 0, 1)` のように書けば、**録るスロットを拍の分割で指定**できる。録音専用の構文が要らない — 「専用の語を作らない」（#649 / SC.10）と同じ流儀。

**出口との対称性**（案）:

| | 出口（§4.A.1・裁定済み） | 入口（本節・スケッチ） |
|---|---|---|
| 要素 | `output(宛先, thru, db)` | `rec(パターン, …)` |
| 位置の意味 | どこまでの信号を出すか（タップ点） | どこまでの信号を録るか（dry / wet） |
| 時間の指定 | — | `play()` と同じパターン（パンチイン / アウト） |
| 宛先 | master / sum / aux / Link / render bus | 録ったものの**名前**（テイク・§9） |
| スルー | `thru: true` = 先へも流す | 🔴 **main の読み・owner は言っていない**: `rec(…, thru: true)` = 録りながら先へ流す = **入力モニター**。同じ属性が別の意味を持つのではなく、**同じ意味**（先へも流す）が文脈で「モニター」と呼ばれるだけ |

**確認した事実（一次情報）**:

| 問い | 答え | 根拠 |
|---|---|---|
| (1) `input` は DSL 語彙にあるか | **無い。** `runtime.ts` の `GLOBAL_DSL_METHODS` / `SEQUENCE_DSL_METHODS`、`sequence.ts`、`global.ts` に `input` / `rec` / `record` は 0 件。**新しい主語**になる。文の受け手は今 **globals / sequences / mixer nodes の 3 種**（`process-statement.ts:72-79`）なので、`input` は **4 番目の受け手**か、**シーケンスの一種**（audio / instrument / midi と並ぶ）かを決める必要がある。#643 のオプションカタログ（audio / instrument / midi）に **input は無い** — instrument と同じ「feed（block 粒度）で土台に乗るソース」として足すのが自然に見えるが**設計判断** | grep / `643-mixer-foundation-design.md:157-165` |
| (2) `play()` のパターン記法は録音に流用できるか | audio の `play(1, 0, 1, 0)` は **スライス番号 = 音の選択・`0 = rest`**（core spec:842, 890）。録音では「**録る / 録らない**」の 2 値になり、**同じ記法で意味が違う**（1..n の番号に意味が無い）。流用するなら `rec` では `1 / 0` だけを受理するか、別の値集合を定義するかが論点 | core spec §Slice Indexing |
| (3) `rec` で録ったものはどこへ行くか | **未設計。** #679 の論点「録れたものの同一性（`chop()` / slot の対象になるか）」「保存先（#456）」そのもの。`audio()` の素材にするなら**名前が要る** = テイクの命名 = `output` のプレースホルダ（§4.A.3 (e)）と同じ関心 | #679 本文 |

**帰結の整理**: (1) を「input はソースの一種（feed）」と決めれば、**入力ラインは出力ラインと同じ土台（insert bus）に乗り、`rec` は `output` と同じ資格の要素**になる — 対称性がそのまま実装の形になる。**これは main の読み**であり、#679 の設計で owner が裁定する。

**未決（§9）**: `input` の位置づけ（受け手か・シーケンスの一種か）/ `rec` の引数（パターンの値集合・宛先 = 名前）/ 入力側のスルーも `thru` でよいか / 録ったものが `audio()` の素材になる経路と命名。

**統合**: 無し。**#679 本文に「レコーディング機能」の別名を追記**（§6.2）— 語で引けるようにする。本節のスケッチも #679 本文に転記する（§6.2）。
