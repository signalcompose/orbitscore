## 1. Splice — MCP サーバがあるので統合の形が変わる（#666）

> これAPIとかないのかなぁ、、、／ VST3だとLLM側から使えないよね。／ **というかMCPサーバあるじゃん。**

**事実確認**: Splice は**公式のリモート MCP サーバ**を提供している。エンドポイントは
`https://mcp.splice.com/mcp`、現在 **beta**。自然言語でのサンプル検索・stack 構築・
ダウンロードまで持ち、Claude Code / Codex / Cursor / VS Code から接続できる。

**構図が変わる**:

| | 誰が使うか | 何をするか |
|---|---|---|
| Splice Sounds VST3（#666 の元案） | **人間** | アプリ内でブラウズ・試聴・ダウンロード |
| Splice MCP サーバ | **LLM** | 検索してローカルへダウンロード |

LLM は MCP から落とし、OrbitScore は**落ちてきたファイルのパスを受け取るだけ**でよい。
Splice 連携を自前で実装する必要がない。

**#666 のスコープが縮む**: 「Splice を統合する」ではなく
「**ダウンロード先を OrbitScore のプロジェクトが解決できる形にする**」。
これは import 宣言（#456 系）と同じ問題に落ちる。

**制約**: ダウンロードはアカウント・サブスクリプション・クレジットに依存するので、
**CI や無人 E2E からは駆動できない**。beta なので契約が変わりうる。

**過去の誤り**: 以前 main が「Splice に公開 API は無い」と書いたのは誤りだった
（検索語が悪く別物の Splice を拾っていた）。公式の Splice Sounds VST3 も実在しカタログにも載っている。

## 2. リアルタイム・サンプリング — **issue 未起票**

> AudioDSL にリアルタイムに楽器の演奏をサンプリングするような仕組みを追加して
> （サンプルのトリガーは何かしらの恣意的なトリガーもしくはループの頭、など考えないとならない）、
> それを AudioDSL の中で使えるようにしたい。
> ある意味 DAW の入力を作り分けだけど、Ableton, Bitwig, Opcode Vision 的なオーディオの扱いになるのかなと。

**現状との距離**: OrbitScore には**オーディオ入力の経路が無い**。capture（`capture.rs`）は
出力を WAV へ書くもので、入力ではない。cpal は入力ストリームを扱えるので土台はある。

**設計で詰めること**:

- **トリガーの意味論**（owner 自身が「考えないとならない」と書いている箇所）。
  「ループの頭」は transport が持つ情報なので DSL から指せる。「恣意的なトリガー」は
  MCP からの明示コマンドか、DSL の評価そのものか
- **録れたものの同一性**。録音結果は `chop()` や `slot` の対象になるのか、
  それとも別種のソースなのか。既存の audio シーケンスと同じ語彙で扱えるのが望ましい
- **保存先とプロジェクト**。録音は消えては困るので、#456 の import / プロジェクト概念と接続する
- **レイテンシと同期**。入力ストリームと出力ストリームの位相をどう合わせるか

**参照される DAW**: Ableton / Bitwig / Opcode Vision。Vision が挙がっているのは、
おそらく「録ったものをそのままシーケンスの素材として扱う」感覚を指している。

## 3. VST3 / CLAP を CC で変更する — **issue 未起票**

> あと VST3 や CLAP に cc を使って変更等ができるようにする必要があるよね。

**現状**: プラグインへ送れるのはノート主体で、**パラメータをシーケンスから動かす経路が無い**。
音色は UI で作って state として保存・復元する形（#474 系）に寄っている。

**設計で詰めること**:

- **CC そのものを送るのか、プラグインのパラメータを直接動かすのか**。
  VST3 も CLAP もパラメータは ID で持ち、CC とは別系統。CC を送れば受ける側の
  マッピング次第になり、パラメータ ID を指せば確実だが**名前の解決**が要る
- **DSL の表面**。#649 で確定した「メソッドチェーンの順序が信号順」と衝突しない形にする
- **記録**。人間がつまみで動かした値は DSL に残らない（既知の論点）。CC / パラメータ
  オートメーションは DSL に載るので、この非対称が解消する方向でもある

**関連**: #672（DSL Plugin / DSP Plugin の契約）、#644（シーケンス種別に使えない setter の診断）

## 4. 標準プラグインに Patina を検討（#669）

> 標準プラグインを用意する。https://github.com/ShmKnd/Patina を使うことを検討したい。

**事実確認**（2026-09-02）: `ShmKnd/Patina` は実在。**C++17 の標準ライブラリのみ**で書かれた
アナログモデリング DSP ライブラリ（BBD ディレイ、コンパンダ、トーン回路、真空管アンプ等）。
**JUCE も Boost も外部依存も無し**。**MIT**。

**相性**: 良い。OrbitScore は既に `orbit-std-gain` を **CLAP プラグインとして同梱**する経路を
持っている（#628 で通した）。Patina を CLAP でくるむのは、その経路にそのまま乗る。
依存が標準ライブラリだけなのでバンドルとライセンスの検討も軽い。

**#669 との関係**: #669 は「compressor / limiter / normalizer を標準 CLAP プラグインとして
作り直す」。Patina はまさにその中身の候補になる。

## 5. 専用シンセに unworklet を検討 — 🔴 ホストが違う

> unworklet を採用して orbitscore に専用シンセを組み込む。標準エフェクターにも使えるのかも含めて
> レイテンシーなどの計測をして実用できるかどうか検討したい。12EDO 以外の音程とか初期にあった
> １５半音を十二分割する新しいドレミ、みたいなものを表現できるようになると平均率の別の拡張も
> できるので。前例はあると思うけどこの辺は要調査。midi で表現するのがかなり難しいので。
>
> ただ標準エフェクターなどは https://github.com/ShmKnd/Patina こっちの方がいいかも。
> unworklet はユーザーランドにエフェクターを解放するための仕組みにしておくといいかも。
> シンセもフィックスしちゃうなら Patina でいいかもなんけど、unworklet だと楽に更新できるという
> 良さがあるよね。この辺は比較したい。

**事実確認**（2026-09-02）: `yuichkun/unworklet` は実在・**MIT**。説明は
"A declarative framework for writing **Audio Worklet**-based DSP in **TypeScript**, compiled to
**WebAssembly** with realtime-safety guarantees."

🔴 **ここに前提の食い違いがある。** unworklet は **AudioWorklet = ブラウザの WebAudio** を
ホストとする枠組みで、そのリアルタイム安全性の保証も AudioWorklet スレッドについてのもの。
OrbitScore のエンジンは **Rust の native daemon（cpal）**であり、ブラウザではない。

したがって「unworklet を採用する」と言うとき、実際にありうる形は次のどれかで、**それぞれ別物**:

| 形 | 内容 | 代償 |
|---|---|---|
| A. WASM だけ借りる | unworklet が吐く WASM を daemon 側で `wasmtime` 等で回す | AudioWorklet 由来の RT 安全性の保証は**付いてこない**。実行系を自前で書く |
| B. 記法だけ借りる | 宣言的な DSP 記述の設計を参考に、Rust 側で同等を作る | 実装コストは全部こちら持ち。更新の容易さも得られない |
| C. ブラウザ面を作る | WebAudio 版の実行面を別に持つ | 二重のエンジン。#670（エンジンを別 repo へ）とは逆方向 |

**owner の狙いは「ユーザーランドにエフェクターを解放する」「楽に更新できる」**なので、
本質は **DSP をユーザーが書いて差し込める仕組み**であって、unworklet 固有の話ではない。
これは **#671 / #672（OrbitScore DSL Plugin と DSP Plugin の契約）と同じ問題**を見ている。

**比較の前に決めるべき問い**: 「ユーザーが書いた DSP は、どのプロセスの、どのスレッドで走るのか」。
ここが決まらないと、unworklet と Patina は**同じ土俵に乗らない**（前者は実行系の話、
後者は DSP ライブラリの話）。

**音律の動機**: 12EDO 以外・「15 半音を十二分割」を表現したいという要求は
[[orbitscore-synth-dsl-vision]]（#497）と同じ。**MIDI では表現しにくい**ので自前シンセが要る、
という筋は一貫している。前例の調査は未実施。

## 7. 出力チャンネルとスルー（#611）

> これもデバイスが使えるチャンネルは全て使えるようにしたいよね。あとどこにアウトを指すかは
> DSL で自由にしたらいいよね。ちなみに、オーディオ信号はスルーするしない、をつけると
> 複数のアウトを１つのオーディオラインに作ったり、エフェクトマーの音をアウトして
> エフェクト後の音もアウトしてみたいなことができるようになるよね。

**#611（ミキサーの出力側）に直結**。3 つの要求が入っている:

1. **デバイスが持つ全チャンネルを使えるようにする**（現在 8ch @ 2048 で instrument が無音になる問題あり）
2. **アウトの位置を DSL で自由に指せる**
3. 🔴 **「スルーする / しない」** — これが新しい。信号をそこで**分岐させて先へも流す**か、
   **そこで出して終わりにする**かを選べると、**エフェクト前とエフェクト後の両方を出せる**

3 は send / insert の区別を、専用の語ではなく**オーディオライン上の 1 要素の属性**として
表現する案になっている。#649 の「フェーダーという段は作らない・順序がモデル」と同じ思想。
