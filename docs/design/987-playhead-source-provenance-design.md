## 1. 到達点

拡張は `play(` を探さない。エンジンが、鳴らした slot ごとに「その音を作った文字範囲」を
`[STEP]` で伝える。拡張はその範囲を、評価を送ったときに記録した文書の位置へ写し、
送ったあとの編集に合わせてずらして光らせる。

不変条件は 1 つ: **表示は音に従う**。表示が切り替わるのは、新しい出どころを持つ音が鳴ったときだけ。

| 条件（owner 指定） | 不変条件からの帰結と仕組み |
|---|---|
| 新しいパターンが**実際に鳴り始めた瞬間**に切り替わる | 出どころはパターンと一緒に保存され、**周期を予約する時点で**予約する音に結び付く（§6.5）。先読みで予約済みの周期は古い出どころのまま鳴る |
| 評価に失敗したら表示は古いまま | 失敗したフレームはパターンを書き換えない（Q2）ので、出どころも変わらない |
| 文書の外から来たパターンが鳴ったら、その seq の表示を消す | MCP の `evaluate_orbitscore` の評価にも ID を振り、拡張はその ID を「文書の外」と記録する（§7.1） |
| チェーンの途中の `play(` にも付く | パーサがチェーンの各段の `play` について位置を記録する（§6.2） |
| コメント・文字列の判定はパーサに任せる | 位置はトークンから作る。拡張は位置を決めるためにテキストを読まない |
| 入れ子（`argPath` の `1.0`）と stack は今の振る舞い | 引数の木をたどる（§6.4）。stack は声部が stack 自身の `argPath` を持つので（F7）、木の上でも 1 単位になる |
| audio の `play()` の意味論は変えない | 出どころは観測用のデータで、タイミングの計算はこれを読まない（`argPath` と同じ扱い。`calculate-event-timing.ts:84-88`） |

## 3. 全体像

```
拡張（層 3）                            エンジン（層 2）
───────────────────────────────         ──────────────────────────────────────
評価を送る
  //#documentDirectory <dir>       ──▶  （メタ行。フレームの外）
  evalId を振る（例 k3f-42）
  //#evalBegin {"evalId":"k3f-42"} ──▶  フレームを開く
  <ユーザーが書いた行だけ>                フレームの行を溜める
  //#evalEnd                       ──▶  1 回でパース（位置の木を作る）→ 1 回で実行
  表に登録: k3f-42 → {文書, 各行の          L2: 位置の木を要素と同じ歩調で変換
    文書の位置, 送った文字列}               Sequence: パターンと出どころを一緒に保存
                                         周期を予約: 予約する音に出どころを結ぶ
                                   ◀──  [STEP] hh 5 1760…123 k3f-42@0:23-0:24
STEP を受ける
  表から文書の位置へ写す（送った後の編集でずらす）
  写した範囲の文字列が送った文字列と同じか確かめる
  atEpochMs に光らせる
```

責任の分け方:

- **エンジン**: 「この slot を鳴らしたのは、評価 `k3f-42` のテキストの、この範囲」まで。文書・URI・編集は知らない
- **拡張**: 評価 ID → 文書と位置の表。送った後の編集で位置をずらす。テキストは確かめるためだけに読む

| # | 論点 | 決定 | 根拠 |

## 5. wire

### 5.1 抽象モデル（層に依存しない）

```ts
/** 評価の要求。evalId は送る側が振る（エンジンのセッションの中で一意）。 */
interface EvalRequest { evalId: string; code: string }

/** code の中の位置。line = 0 始まりの行、character = その行の中の 0 始まりの UTF-16 の位置。 */
interface SourcePosition { line: number; character: number }

/** その slot を鳴らしたテキストの範囲（end は含まない）。 */
interface SourceRange { evalId: string; start: SourcePosition; end: SourcePosition }

interface StepEvent {
  seq: string
  argPath: string               // 今と同じ（L2 の後の木の添字）。診断と構造の識別に残す
  atEpochMs: number
  source: SourceRange | null    // null = 送る側が ID を付けたフレームから来ていない
}
```

`source: null` になるのは: ID の無いフレーム / フレームの外の行（人が stdin に直接打った等）/
`import` したファイル / F26 の経路 / 将来の replay（ID を付けない場合）。

### 5.2 送る側

```
//#documentDirectory /path/to/dir
//#evalBegin {"evalId":"k3f-42"}
hh.play(1, 0, 0, 1, 0, 1, 0, 0)
LOOP(hh)
//#evalEnd
```

- メタ行（`//#documentDirectory`、将来の `//#sourceFile`）はフレームの**前**（設計 694 §3.2 の順）
- 属性は JSON の object。知らないキーは無視する（設計 694 の `evalSource` と同居できる）
- `evalId` が `^[A-Za-z0-9_-]{1,64}$` に合わなければ診断を出し、ID 無しとして扱う
- 属性の無い `//#evalBegin` も受け付ける（ID 無し）
- フレームの中に `//#` のメタ行が来た場合（設計 694 §4.1 は即時に処理する）、**その行を空行としてフレームに残す**。行番号を保つため

### 5.3 受け取る側: `[STEP]`

```
[STEP] <seq> <argPath> <atEpochMs> <src>
<src> := "-" | <evalId> "@" <sl> ":" <sc> "-" <el> ":" <ec>
```

例: `[STEP] hh 5 1760871234567 k3f-42@0:23-0:24`（上の例の 6 個目の要素 `1`）

- 行・列は D6 の 0 始まり。`evalId` は `@` を含まないので、`@` で 2 つに分けて読む
- `argPath` は残す（gated E2E の既存の検査 `:3101` と、構造の識別のため）
- **JSON 行にしない理由**: 受け手（`playhead.ts:42`）・E2E・dev サイトの文法の引用がすべて書き換わる。項目が 1 つ増えるだけなら、行末を固定しない E2E はそのまま通る。stdio の書式は層 2 の型付き RPC で置き換わる予定（`NATIVE_MIGRATION_2026-09.md` §3「プロトコルは作り直す案」）なので、今の書式に拡張性を作り込む価値が低い
- 出どころの種類を足すとき（`import` したファイル等）は `<src>` の先頭に接頭辞を足す（例 `f:<id>@…`）。今は作らない

### 5.4 互換

- エンジンと拡張は同じ `.vsix` で出荷される（F33）。版のずれは開発時の古いビルドに限られる
- **新しい拡張 + 古いエンジン**: `<src>` が無い行 → `source: null` → 表示は消える（誤った位置には付かない）
- **古い拡張 + 新しいエンジン**: 行末固定の正規表現（F2）に合わない → 何も光らない

## 6. エンジンの変更

### 6.1 REPL（`repl-mode.ts`）— 設計 694 PR-L2 を先に入れる

- `//#evalBegin [json]` でフレームを開き、`//#evalEnd` で閉じる。フレームの中の行は溜めるだけ
- `//#evalEnd` で `parseAudioDSL(frameCode, { sourceId: evalId })` を 1 回、`execute()` を 1 回
- パースに失敗したらフレーム全体を実行しない（診断に積む）。未完（`EOF`）もフレームでは構文エラー
- 閉じていないフレームがある状態での `//#evalBegin` / `//#evalMark` の扱いは設計 694 §4.1 の表のとおり
- フレームの外の行（人が直接打つ行）は今どおり行単位（ID 無し）
- `crlfDelay: Infinity`（D18）
- 仕様の正本（`SESSION_LOG_SPEC_v1.md` §3.1 と core spec の評価の単位の記述）を、実装より先に直す（運用規則 6）

この PR は B′ の前提であると同時に、設計 694 の #695 の受け入れそのもの。

### 6.2 トークナイザとパーサ

- `AudioToken` に終わりの位置（行・列）を足す
- `parseAudioDSL(code, { sourceId })` を受け付ける。`sourceId` があるときだけ、`play` の呼び出しごとに**位置の木**を作る。無いときの IR は今と同じ（`tests/golden-ir.json` と既存の `toEqual` が動かないこと）
  - 位置の木の節: `{ range, children? }`。`play` の引数の並び（`collapseScopedRun` の後）と同じ形
  - 置き場所: 本文の呼び出しなら `SequenceStatement`、チェーンの段なら `MethodChain` に `playSource` として
- `import` したファイルは `sourceId` 無しでパースする（D16）

### 6.3 インタプリタと `Sequence`

- `dispatchCall` の中で、`effect` / `instrument` の特別扱い（`process-statement.ts:284-293`）と同じ場所に `play` を置き、`playSource` があれば `seq.playWithSource(elements, source)` を呼ぶ。`play(...elements)` は `playWithSource(elements, null)` を呼ぶだけ
  - `callMethod` は引数の配列を展開して渡す（`evaluate-method.ts:25-37`）ので、`Sequence` 側で配列の同一性から出どころを引くことはできない
  - `playWithSource` は DSL の語彙ではない。`tests/interpreter/signal-chain-dispatch.spec.ts:759` の分類に内部 API として足す（#523 と同じ型の穴を作らない）
- `TimedEvent` を作る 2 か所（F11）を 1 つの関数にまとめ、その中で各 `TimedEvent` に出どころ（D11）を付ける。`argPath` は解決後の木から決まるので、再計算しても同じ出どころが付く
- 再宣言はパターンを消さないので、出どころも残る（F12）

### 6.4 L2 と光らせる単位

`resolveElements` / `resolveElement` が、要素と同じ歩調で位置の木を変換する。規則は 1 つ:

- **1→1 の構造**（`( )`・`{ }`・scoped・modified・stack）: 元の節を、子も同じ歩調で変換して保つ
- **1→N で生まれた要素**（`x*n` の各コピー・パターン変数が差し込んだ兄弟・和音名から作った stack）: **書いた文字の節**（`x*n` 全体・名前）を指し、子を持たせない

光らせる範囲は、根から `argPath` の添字を、**子がある限り**たどった節の範囲。表は作らない。

| 書き方 | 今（拡張がテキストを読む） | B′ |
|---|---|---|
| `play(1, (2, 3))` の `1.0` | `2` | `2`（同じ） |
| `play([1, 3, 5], 0)` | `[1, 3, 5]` 全体 | 同じ（声部が stack の `argPath` を持つ・F7） |
| `play((1,0)(2,3).root(5), 1)` | run 全体 | **`1`・`0`・`2`・`3` を順に** |
| `play(1*3, 0)` | 2 歩目以降がずれる（F8） | 3 歩とも `1*3`、4 歩目が `0` |
| `play(A, 1)`（`A` は 2 つの兄弟を差し込む） | ずれる | 2 歩とも `A`、3 歩目が `1` |
| `play((1)(2), 3)` | ずれる | `(1)` の `1` → `(2)` の `2` → `3` |

run の中へ降りない形が良ければ、scoped の節の子を落とすだけで変えられる（1 か所）。

### 6.5 予約と `[STEP]` の整形

- 待ち行列へ写すものを `argPath` から `StepMarker { argPath, source }` に変える（audio の `scheduleEvent` / `scheduleSliceEvent` / `scheduleStepMarker`、note/MIDI の `scheduleStepMarker`）
- `source` は**周期を予約する時点で** `TimedEvent` から写す（D12）。ループ中の `play()` は次の周期の予約から、`run()` 中の `play()` はその場の予約し直しから、新しい出どころになる（F10）。どちらも音と同じ時点
- 整形関数 `formatStepLine(seq, marker, atEpochMs)` を 1 つにし、audio と note/MIDI が使う（D14）
- `[STEP]` が出ない場合（mute・drift guard・`liveSequences` から外れた後）は今と同じで、表示は前の slot に残る（本件の対象外）

## 7. 拡張の変更

### 7.1 送る側

- `writeCodeToEngine` は「送る行の並び + 各行の文書の位置（または対応無し）」を受け取り、`evalId` を振ってフレームを組む。送れたら表に登録する
  - エディタ: 選択範囲・subject-block・単独文のそれぞれで、送った各行の文書の位置と文字列を記録する（subject-block は行が飛び飛びになるので、行ごとに記録する）
  - MCP の `evaluate_orbitscore`: 種類「文書の外」
  - MCP の `run_selection` はエディタの経路そのもの（`run-selection.ts:216-231`）なので、文書の評価として記録される
- 表はエンジンの世代（`engineGeneration`）ごと。エンジンの停止・再起動で空にする
- 表の大きさ: 1 評価あたり送った行数ぶん。4 時間のセッションで 10 秒に 1 回評価しても約 1,500 件なので、消す仕組みは作らない

### 7.2 受ける側

- `src` が `-` / 表に無い ID / 「文書の外」→ その seq の表示を消す
- 文書の評価 → active entry を `{ seq, evalId, range }` にする。描くたびに表から文書の範囲を求める（PR #988 の M6 と同じ形。古い座標を持たない）
- 描く先: 見えているエディタのうち、URI が一致するものすべて（分割表示を含む）

### 7.3 編集の追従（純関数・vscode に依存しない）

- 各行の対応を区間の並び `{ 列の開始, 文書の位置, 長さ }` で持つ。初めは 1 行 1 区間
- `onDidChangeTextDocument` の各変更を**配列の順に逐次**、その時点の位置に対して当てる（F30。`vscode-languageserver-textdocument` の `update` と同じ当て方）
  - 区間が変更より前 → そのまま。後ろ → 長さの差だけずらす。重なる → 重ならない部分だけ残して分ける
- 文書を閉じても対応は捨てない。開き直した後は §7.4 の確認で、合っているものだけ描く

PR #988 の `shiftPlayCallAnchor` とその表形式のテスト（P9〜P11）、vscode モックの `onDidChangeTextDocument` の拡張は、ここに移して使う。

### 7.4 描く前の確認

写した範囲の文書の文字列が、送ったときのその範囲の文字列と**同じとき**だけ描く。違えば、その `[STEP]` ではその seq の表示を消す（次の slot の範囲が合っていればまた付く）。

- 位置を決めるためには読まない。確かめるためだけに読む（Q6）
- これで「編集の追従の当て方」（§13 U1）を誤っても、誤った文字は光らない
- 前の表示を残すと、鳴っていない引数に付く。最初の `play()` へ戻すと、別の場所に付く（Issue の完了条件 5）

## 9. 棄却した案

| 案 | 棄却の理由 |
|---|---|
| エンジンに文書の URI と位置を渡し、`[STEP]` で文書の位置を返す | 送った後の編集はエンジンから見えない。結局拡張で位置をずらすことになる |
| エンジンが評価 ID を振り、拡張へ送り返す | 往復が 1 つ増え、ID が返るまで `[STEP]` を待たせる処理が要る |
| 世代番号だけを `[STEP]` に載せる（#987 コメントの案） | 「いつ」は正確になるが「どこ」は拡張がテキストを探すまま。F8 も残る |
| 行ごとの実行のまま、REPL がバッファの開始行と `trim()` の分を補正して座標を作る（下書きの案） | 行ごとの実行（#607 / #608 / #612 が起きた所）の上に座標の補正をもう 1 層足すことになる。フレームをまたぐバッファの扱いも要る。Q2 が否決されたときの代案として残す |
| メタ行・挿入行をフレームに残し、拡張の表で「対応無し」として吸収する（下書きの案） | 座標が拡張の挿入の都合に結び付く。挿入を廃止した時点で座標の数え方が変わる |
| 位置を AST の object の節に持たせる | 葉が素の `number`（F23）。葉を object にすると、パターンを読む全箇所が変わる |
| 位置を `WeakMap`（配列 → 位置）で横に持つ | L2 が配列を作り直すたびに黙って失われる |
| パターン単位に evalId を 1 つ持つ（下書きの案） | 1 つのパターンの中に、別の評価から来た部分（パターン変数の定義）を持てない（D11） |
| 光らせる単位を表で決める（下書きの案） | 木を作る段階で決まっている。表は木と別に保守が要る |
| `[STEP]` を JSON 行にする | §5.3 |

## 11. ネイティブ版（OrbitStudio.app）への引き継ぎ

- **そのまま引き継ぐもの（層 2）**: 1 フレーム 1 評価、パーサの位置の木、L2 の歩調を合わせた変換、光らせる単位の規則、予約時に出どころを結ぶ仕組み
- §5.1 の抽象モデルは、層 2 の型付き RPC（`NATIVE_MIGRATION` §3「評価のメソッド + リクエスト ID + イベントストリーム」）にそのまま載る:
  - `evaluate({ code, evalId })` → 結果（`//#evalMark` の役目もここに入る）
  - イベント `step { seq, argPath, atEpochMs, source }`
  - D5 でフレームの中身をユーザーのテキストだけにしたので、`code` の座標と今のフレームの座標は**同じ**。読み替えは要らない
- **置き換わるもの（層 3）**: `//#evalBegin {…}` と `[STEP] …` のテキストの書式。拡張の「表 + 区間による編集の追従」は、Monaco では編集に追従する decoration（`deltaDecorations` で作り、`getDecorationRange` で読み戻す）で置き換えられる見込み（§13 U4）
- **座標**: D6 は LSP の数え方（0 始まり）。Monaco は 1 始まりなので、クライアントで 1 足す
- **subject-block を層 2 へ移す場合**（`NATIVE_MIGRATION` §3 の §12 補正）: 評価の要求に文書とカーソルが入る。`SourcePosition` を「要求したテキストの中の位置」と読めば、`StepEvent` の形は変わらない
- **ID の振り手**: RPC では受け手（層 2）が振って返す形にしてよい。`[STEP]` から見れば中身を解釈しない文字列なので影響しない

## 15. 分け方と検証

### 15.1 PR と束

「振る舞いを変えない PR」と「変える PR」を同じ束に入れない（`BUNDLE_BRANCH_WORKFLOW.md` §5.1）。

| 順 | 単位 | 中身 | 振る舞い | 検算の機会 |
|---|---|---|---|---|
| 1 | main 直行 PR（設計 694 の PR-L2 を兼ねる） | 仕様の正本の改訂 → 1 フレーム 1 評価・`//#evalBegin {json}`・メタ行をフレームの前へ・挿入と `globalInitialized` の廃止・`text.trim()` の廃止・`crlfDelay` | **変わる**（評価の単位） | gated E2E: 選択の中に構文エラーがあると何も実行されない / `kick_loop.orbs` の相対パスが鳴る / 既存の gated 全件 |
| 2 | 束 A（エンジン） | トークンの終わりの位置・位置の木・L2 の歩調・`TimedEvent` の出どころ・`playWithSource`・`StepMarker`・整形関数の一本化・`<src>`。拡張は `<src>` を**読み捨てる**ように受け手だけ直し、`evalId` を送る | 拡張の見た目は**変わらない** | `sourceId` 無しの IR が動かない（golden）。gated E2E で生の `[STEP]` の `<src>` を検査 |
| 3 | 束 B（拡張） | 表・区間の追従・描く前の確認・`[STEP]` から描く・文字列検索の削除・行単位の受け手・dev サイトと CHANGELOG | **変わる** | §8 の場面を vscode モックの統合テストと実機で |

行数の見積もり（推測）: 1 = 300〜400 行、束 A = 900〜1,300 行、束 B = 700〜1,000 行。

### 15.2 テスト

| 層 | 内容 |
|---|---|
| エンジンの単体 | トークンの終わりの位置 / 位置の木（コメント・文字列・複数行の引数・チェーンの段）/ フレームの評価（構文エラーで何も実行しない・メタ行・閉じていないフレーム）/ L2 の歩調（§6.4 の表の各行）/ 再計算しても出どころが同じ / **先読みで予約済みの周期は古い出どころのまま鳴る** / 整形関数（共有 fixture） |
| 拡張の単体 | `[STEP]` の文法（共有 fixture・`<src>` 有り・無し・壊れた形）/ 区間の追従（前に挿入・行の中の編集・行の削除・1 回の通知に複数の変更）/ 送った行と文書の位置の対応（選択・subject-block・単独文）/ 描く前の確認 |
| 拡張の統合（vscode モック） | 本物の `runSelection` → `[STEP]` → `editor.setDecorations` で §8 の各行 |
| 実機 gated E2E | debug モードの生の `[STEP]` 行で: ① チェーンの `play(` に `<src>` が付く ② 2 つ目の `play()` を流した後、`evalId` が**周期の最初の slot で**切り替わり、周期の途中では変わらない ③ 構文エラーのフレームの後も `evalId` が変わらない ④ `evaluate_orbitscore` のフレームの `evalId` が付く ⑤ `<src>` の範囲で送ったコードを切り出すと、期待する引数の文字列になる |
| 実機の見た目 | decoration は MCP から読めない（F32）。main がマージ前に §8 の場面を実機で 1 回確かめる |

最後の 1 段（拡張が文書のどこへ描いたか）を gated E2E で確かめたい場合は、debug モードだけで「描いた文書の範囲」を 1 行出力する手がある。新しい MCP ツールは作らない。要否は束 B の設計時に決める。
