## 1. 到達点

拡張は `play(` を探さない。エンジンが、鳴らした slot ごとに「その音を作った文字範囲」を
`[STEP]` で伝える。拡張はその範囲を、評価を送ったときに覚えた文書の位置へ写し、
編集に合わせてずらして光らせる。

満たすこと（owner 指定）と、それを満たす仕組み:

| 条件 | 仕組み |
|---|---|
| 新しいパターンが**実際に鳴り始めた瞬間**に切り替わる | 出どころはパターンと一緒に保存され、**ループの各周期を予約する時点で**予約される音に結び付く（§6.5）。先読みで積んだ古い周期は古い出どころのまま鳴る |
| 評価に失敗したら表示は古いまま | 失敗した `play()` はパターンを書き換えないので、出どころも書き換わらない（§6.3） |
| 文書の外から来たパターンが鳴ったら、その seq の表示を消す | MCP の `evaluate_orbitscore` の評価にも ID を振り、拡張はその ID を「文書の外」と記録する（§7.1） |
| チェーンの途中の `play(` にも付く | パーサがチェーンの各段の `play` の引数の位置を記録する（§6.2） |
| コメント・文字列の判定はパーサに任せる | 位置はトークンから作る。拡張はテキストを読まない |
| 入れ子（`argPath` の `1.0`）と stack は今の振る舞い | 光らせる単位の規則を 1 つの純関数にし、今の規則を再現する（§6.4） |
| audio の `play()` の意味論は変えない | 出どころは観測用のデータで、タイミングの計算はこれを読まない（`argPath` と同じ扱い。`calculate-event-timing.ts:84-88`） |

## 3. 全体像

```
拡張（層 3）                           エンジン（層 2）
──────────────────────────────         ─────────────────────────────────────
評価を送る
  evalId を振る (例 e42)
  //#evalBegin {"evalId":"e42"}   ──▶  フレームを開く。行を数え始める
  <フレームの各行>                        パーサ: play() の各要素の位置を記録
  //#evalEnd                              （フレームの行・列で）
  origin[e42] = {文書 URI,                L2: 位置の木を要素と一緒に変換
    フレームの各行 → 文書の位置}          Sequence: パターンと出どころを一緒に保存
                                         ループの周期を予約: 予約する音に出どころを結ぶ
                                    ◀──  [STEP] hh 5 1760…123 e42@3:14-3:15
STEP を受ける
  origin[e42] から文書の位置へ写す
  （送った後の編集でずらす）
  atEpochMs に光らせる
```

責任の分け方:

- **エンジン**: 「この slot を鳴らしたのは、評価 `e42` のテキストの、この範囲」まで。文書・URI・編集は知らない
- **拡張**: 評価 ID → 文書と位置の表。送った後の編集で位置をずらす。描くだけで、テキストを読み直さない

## 4. 決定表

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| D1 | 評価 ID を振るのは誰か | **送る側（拡張）**。エンジンは中身を解釈しない文字列として扱う | 表を持つのは送る側。今の stdio では、エンジンが振ると ID を送り返す往復が要る。層 2 の RPC では受け手が振る形に変えられる（§11） |
| D2 | ID の載せ方 | 既存のフレーム行に JSON の属性として載せる: `//#evalBegin {"evalId":"e42"}` | 設計 694 §4.1 が決めた属性の仕組みと同じ（F20）。仕組みを 2 つ作らない |
| D3 | ID を振る評価 | **すべてのフレーム**（エディタ・MCP とも） | 「文書の外」は拡張の表の側で表す。エンジンの扱いを経路で分けない |
| D4 | 位置の座標 | **フレームの座標**: 行 = `//#evalBegin` の次の行を 0 とする物理行の番号、列 = その行の中の 0 始まりの UTF-16 の位置、終わりは含まない（LSP と同じ数え方） | REPL は行単位で読む（F16）。改行コード（CRLF）の違いが行の中に入らない。VS Code の `Position.character` と同じ単位 |
| D5 | エンジンが文書の URI を受け取るか | **受け取らない** | 文書との対応・編集の追跡は送る側にしかできない。エンジンに URI を渡しても使い道が無い |
| D6 | 位置を作る場所 | **パーサ**。トークンに終わりの位置を足し、`play` の呼び出し（チェーンの段を含む）ごとに、引数と同じ形の「位置の木」を IR に載せる | コメント・文字列はトークナイザが処理済み（F17）。位置の扱いをパーサの外に持たない |
| D7 | L2 での位置の扱い | `resolveChords` が要素と**同じ歩調で**位置の木を変換する | F5。`argPath` は変換後の木で数えるので、変換を知っている場所でしか対応が取れない |
| D8 | 光らせる単位 | 1 つの純関数 `highlightRange(tree, argPath)` で決める。今の規則を再現する（§6.4） | 規則が 1 か所にあれば、後で変えるとき（scoped の中へ降りる等）に 1 か所で済む |
| D9 | 出どころを音に結ぶ時点 | **周期を予約する時点**。`TimedEvent` に出どころの範囲を付け、待ち行列の項目へ `argPath` と一緒に写す | F9。発音の時点で「seq の今の出どころ」を引くと、先読み済みの古い周期に新しい出どころが付く |
| D10 | `[STEP]` の書式 | `[STEP] <seq> <argPath> <atEpochMs> <src>`。`<src>` は `-` か `<evalId>@<開始行>:<開始列>-<終了行>:<終了列>` | §5.3 |

## 5. wire

### 5.1 抽象モデル（層に依存しない）

```ts
/** 評価の要求。evalId は送る側が振る（エンジンのセッションの中で一意）。 */
interface EvalRequest { evalId: string; code: string }

/** code の中の位置。line = code の 0 始まりの物理行、character = UTF-16 の 0 始まり。 */
interface SourcePosition { line: number; character: number }

/** その slot を鳴らしたテキストの範囲（end は含まない）。 */
interface SourceRange { evalId: string; start: SourcePosition; end: SourcePosition }

interface StepEvent {
  seq: string
  argPath: string        // 今と同じ（L2 の後の木の添字）。診断・構造の識別に残す
  atEpochMs: number
  source: SourceRange | null  // null = 送る側が ID を付けたフレームから来ていない
}
```

`source: null` になるのは: ID の無いフレーム（人が stdin に直接打った等）/ `import` したファイル /
CLI の `play` モード（ファイル全体の評価）/ 将来の replay（ID を付けない場合）。

### 5.2 送る側: フレームの属性

```
//#evalBegin {"evalId":"e42"}
//#documentDirectory /path/to/dir
var global = init GLOBAL
global.setDocumentDirectory("/path/to/dir")
hh.play(1, 0, 0, 1)
//#evalEnd
```

- 属性は JSON の object。知らないキーは無視する（設計 694 の `evalSource` と同居する）
- `evalId` は `^[A-Za-z0-9_-]{1,64}$`。外れたら診断を出し、ID 無しとして扱う
- 属性の無い `//#evalBegin` も今どおり受け付ける（ID 無し）
- フレームの座標の 0 行目は `//#documentDirectory` の行。拡張は**送ったすべての行**（メタ行・挿入した行を含む）について、文書の位置または「対応無し」を記録する

### 5.3 受け取る側: `[STEP]`

```
[STEP] <seq> <argPath> <atEpochMs> <src>
<src> := "-" | <evalId> "@" <sl> ":" <sc> "-" <el> ":" <ec>
```

例: `[STEP] hh 5 1760871234567 e42@4:23-4:24`

- 行・列は §4 D4 の 0 始まり。区切りの `@` `:` `-` は `evalId` に使えない文字（`-` は `evalId` に使えるので、`@` の後ろだけを数値として読む）
- `argPath` は残す（gated E2E の既存の検査 `:3101` と、構造の識別のため）
- **JSON 行にしない理由**: 受け手（`playhead.ts:42`）・E2E・dev サイトの文法の引用がすべて書き換わる。項目が 1 つ増えるだけなら、行末を固定しない E2E はそのまま通る。stdio の書式は層 2 の型付き RPC で置き換わる予定（`NATIVE_MIGRATION_2026-09.md` §3「プロトコルは作り直す案」）なので、今の書式に拡張性を作り込む価値が低い
- 将来の種類（`import` したファイルを出どころにする等）は `<src>` の先頭に種類の接頭辞を足せばよい（例: `f:<id>@…`）。今は作らない

### 5.4 互換

- エンジンと拡張は同じ `.vsix` で出荷される（F24）。版のずれは開発時の古いビルドに限られる
- **新しい拡張 + 古いエンジン**: `<src>` が無い行 → `source: null` として読む → 表示は消える（誤った位置には付かない）
- **古い拡張 + 新しいエンジン**: 行末固定の正規表現（F2）に合わない → 何も光らない

## 6. エンジンの変更

### 6.1 REPL（`repl-mode.ts`）

- `//#evalBegin` の属性を読む。フレームの状態 `{ evalId?: string; nextLine: number }` を持つ
- フレームの中の**すべての物理行**（メタ行を含む）で `nextLine` を 1 進める
- バッファの最初の行のフレーム座標を覚える。`buffer.trim()` で落ちた先頭の空行・空白の分を、パーサへ渡す開始位置（行と、最初の行の列）に足す
- バッファが**フレームをまたいだら**、そのバッファには出どころを付けない（前のフレームの未完の文に次のフレームの行が足された場合。座標が 1 つのフレームで閉じないため）
- 🔴 設計 694 の「1 フレーム = 1 回の execute」（PR-L2）を後で入れるときの制約: **物理行の番号を保つ**（メタ行を取り除くなら、その行を空行に置き換えてからパースする）。本書はこの制約を 694 側にも書き足す

### 6.2 トークナイザとパーサ

- `AudioToken` に終わりの位置（行・列、含まない）を足す
- `parseAudioDSL(code, { sourceId?, lineOffset, columnOffset })` を受け付ける。`sourceId` があるときだけ、`play` の呼び出しごとに**位置の木**を作る
  - 位置の木の節: `{ kind, range, children? }`。`kind` は要素の種類（`leaf` / `group` / `legato` / `stack` / `scoped` / `repeat` / `ref` / `modified` / …）
  - `play` の引数の並び（`collapseScopedRun` の後）と同じ形にする
  - 置き場所: 本文の呼び出しなら `SequenceStatement.playSource`、チェーンの段なら `MethodChain.playSource`
- `import` したファイルは `sourceId` 無しでパースする（D13）

### 6.3 インタプリタと `Sequence`

- `play` の段（本文・チェーンとも）は、位置の木があれば `seq.playFrom(elements, source)` を呼ぶ。`play(...elements)` は `playFrom(elements, null)` を呼ぶだけにする
  - `playFrom` は DSL の語彙ではない。`tests/interpreter/signal-chain-dispatch.spec.ts:759` の分類に「内部 API」として足す
- 失敗した `play()`（パースエラー・実行時エラー）は `playFrom` まで届かない → パターンも出どころも前のまま
- `TimedEvent` を作る 2 か所（F10）を 1 つの関数にまとめ、その中で各 `TimedEvent` に出どころの範囲を付ける

### 6.4 L2 と光らせる単位

`resolveChords` の `resolveElements` / `resolveElement` が、要素と同じ歩調で位置の木を変換する:

| 変換 | 出力の位置の節 |
|---|---|
| `x*n` | n 個の兄弟すべてに、`x*n` 全体の節（子を持たない） |
| パターン変数の名前（兄弟を差し込む） | 差し込んだ兄弟すべてに、**使った場所の名前**の節（子を持たない。定義は別の評価にあるかもしれない） |
| 和音名 → stack | 名前の節 |
| `( )` / `{ }` / scoped / stack / modified | 元の節（子も同じ歩調で変換） |

`highlightRange(tree, argPath)`: 根から `argPath` の添字をたどり、**次の場合だけ子へ降りる**:

- 節が `group`（`( )`）または `legato`（`{ }`）で、後ろにチェーンも `*n` も付いていない

それ以外（`stack`・`scoped`・`repeat`・`ref`・`modified`・葉）はその節の範囲を返す。
これは今の拡張の規則（`playhead.ts:233-273`: 要素全体が括弧の組のときだけ降りる・stack は 1 単位）を、
テキストではなく構文の上で書き直したもの。

今は壊れていて、この規則で初めて定義されるもの: `x*n`（毎回 `x*n` 全体）/ パターン変数（名前）/
連結 `(1)(2)`（それぞれの括弧へ降りる）/ 和音名（名前）。

### 6.5 予約と `[STEP]` の整形

- 待ち行列へ写すものを `argPath` から `StepMarker { argPath, source }` に変える（audio の
  `scheduleEvent` / `scheduleSliceEvent` / `scheduleStepMarker`、note/MIDI の `scheduleStepMarker`）
- `source` は**周期を予約する時点で** `TimedEvent` から写す（D9）
- 整形関数 `formatStepLine(seq, marker, atEpochMs)` を 1 つにし、audio と note/MIDI の両方が使う

## 7. 拡張の変更

### 7.1 送る側

- `writeCodeToEngine` は「行の並び + 各行の文書の位置（または対応無し）」を受け取り、
  `evalId` を振ってフレームを組み、送れたら表に登録する
  - エディタ: 選択範囲・subject-block・単独文のそれぞれで、送った各行の文書の位置を記録する。
    `trim()` で落とした先頭の空白は、最初の行の文書の位置に足す
  - `//#documentDirectory` の行・挿入した `global.setDocumentDirectory(...)` の行は「対応無し」
  - MCP の `evaluate_orbitscore`: 全行「対応無し」、種類は「文書の外」
  - MCP の `run_selection` はエディタの経路そのもの（`run-selection.ts:216-231`）なので、文書の評価として記録される
- 表はエンジンの世代（`engineGeneration`）ごと。エンジンの停止・再起動で空にする
- 表の大きさ: 1 評価あたり送った行数ぶんの数値。4 時間のセッションで 10 秒に 1 回評価しても約 1,500 件で、消す仕組みは作らない（エンジンの世代で空になる）

### 7.2 受ける側

- `[STEP]` を行単位にまとめ直した経路で読む（D12）
- `src` が `-` / 表に無い ID / 「文書の外」→ その seq の表示を消す
- 文書の評価 → `{ seq, evalId, frameRange }` を active entry にする。描くたびに表から文書の範囲を求める（PR #988 の M6 と同じ形。古い座標を持たない）
- 描く先: 見えているエディタのうち、URI が一致するものすべて（分割表示を含む）

### 7.3 編集の追従（純関数・vscode に依存しない）

- 各行の対応を「区間」の並びで持つ: `{ 列の開始, 文書の位置, 長さ }`。初めは 1 行 1 区間
- `onDidChangeTextDocument` の各変更（変更前の文書の `rangeOffset` / `rangeLength` と新しいテキスト）を当てる:
  - 区間が変更より前 → そのまま。変更より後 → 長さの差だけずらす。重なる → 重ならない部分だけを残して分ける
  - 複数の変更が 1 回の通知で来る場合の当て方は §13 U1（advisor の確認結果を反映）
- 範囲は**最初の文字と最後の文字の両方が残っている**ときだけ描く。間の文字を編集した場合は、編集後の範囲全体を描く
- 文書を閉じたら、その文書の評価の対応をすべて無効にする（閉じているあいだの変更を追えないため）

### 7.4 鳴っている範囲が編集で消えたとき

その `[STEP]` では、その seq の表示を消す。次の slot の範囲が残っていればまた付く。
前の表示を残すと、鳴っていない引数に付く。最初の `play()` へ戻すと、別の場所に付く（Issue の完了条件 5）。

## 9. 棄却した案

| 案 | 棄却の理由 |
|---|---|
| エンジンに文書の URI と位置を渡し、`[STEP]` で文書の位置を返す | 送った後の編集はエンジンから見えない。結局拡張で位置をずらすことになり、エンジン側の情報が余る |
| エンジンが評価 ID を振り、拡張へ送り返す | 今の stdio では往復が 1 つ増える。表を持つのは送る側なので、送る側が振る方が単純 |
| 世代番号だけを `[STEP]` に載せる（#987 コメントの案） | 「いつ切り替えるか」は正確になるが、「どこに付けるか」は拡張がテキストを探すまま。F8 の誤りも残る |
| 位置を AST の object の節に直接持たせる | 葉が素の `number` なので持てない（F17）。葉を object に変えると、パターンを読む全箇所が変わる |
| 位置を `WeakMap`（配列 → 位置の配列）で横に持つ | L2 が配列を作り直すたびに黙って失われる。型で追えない |
| 光らせる単位を拡張が決める（範囲の列を全部送る） | 単位はパターンの構造で決まる。構造を知っているのはエンジン。ネイティブ版で同じ規則を 2 回書くことになる |
| `[STEP]` を JSON 行にする | §5.3 |

## 11. ネイティブ版（OrbitStudio.app）への引き継ぎ

- **そのまま引き継ぐもの（層 2）**: パーサの位置の木、L2 の歩調を合わせた変換、`highlightRange` の規則、予約時に出どころを結ぶ仕組み。§5.1 の抽象モデルは、層 2 の型付き RPC（`NATIVE_MIGRATION` §3）の「評価のメソッド + リクエスト ID + イベントストリーム」にそのまま載る:
  - `evaluate({ code, evalId })` → 結果（`//#evalMark` の役目もここに入る）
  - イベント `step { seq, argPath, atEpochMs, source }`
- **置き換わるもの（層 3）**: `//#evalBegin {…}` と `[STEP] …` のテキストの書式。拡張の「表 + 区間による編集の追従」は、Monaco では
  **編集に追従する decoration**（`deltaDecorations` で作り、`getDecorationRange` で読み戻せる）で置き換えられる見込み（Monaco の API で未確認・§13 U4）
- **座標**: §4 D4 は LSP の数え方（0 始まり）。Monaco は 1 始まりなので、クライアントで 1 足す
- **subject-block を層 2 へ移す場合**（`NATIVE_MIGRATION` §3 の §12 補正）: 評価の要求が「文書とカーソル」になり、層 2 が文書の座標で範囲を返せるようになる。そのときは `SourcePosition` を「要求したテキストの中の位置」と読み替えるだけで、`StepEvent` の形は変わらない
- **ID の振り手**: RPC では受け手（層 2）が振って返す形に変えてよい。`[STEP]` の側から見れば中身を解釈しない文字列なので、影響はない
