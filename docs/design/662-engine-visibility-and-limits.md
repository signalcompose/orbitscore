## 1. 原則

> **エンジンが知っていることは、原則ユーザーにも見せる。**

owner の言葉（2026-08-31）:

> 他にも出せる項目はなるべくユーザーに出した方がいいね。

この原則は quality-of-life ではなく **ライブ演奏の要件**である。
演奏中に触れる面・見える面が無いことは、そのまま演奏の停止時間になる。

**LLM は第一級ユーザー**なので、パネルに出すものは MCP からも取れること。

## 2. レイテンシーは「値」ではなく「余裕」を出す

owner の言葉:

> レイテンシーなどはそれによってどれくらい余裕があるかわかるといいよね。

### 2.1 ミリ秒を出しても判断できない

出すべきは **コールバック締切に対してどれだけ使っているか**。

```
締切        = buffer_frames / sample_rate
              例: 512 frames @ 48 kHz = 10.67 ms

使用率      = 実測のコールバック所要時間 ÷ 締切

   35%  →  余裕あり（層を足せる）
   85%  →  危険（そろそろ落ちる）
  100%超 →  ドロップアウト
```

**これが「あと何層足せるか」の唯一の答え方**である。
DAW の Audio Performance メーターと同じ考え方。

### 2.2 平均だけでは足りない

**ピークと平均の両方を出す。** 平均だけだと「たまに締切を割る」状態が見えない。
ライブでは、たまに割ることのほうが致命的である。

### 2.3 あわせて出すもの

| 項目 | なぜ要るか |
|---|---|
| **ドロップアウト回数** | 一度でも出たら層を減らす判断材料。**0 か否かが決定的** |
| バッファサイズ / サンプルレート | 締切そのもの。使用率と並べて初めて意味を持つ |
| child プロセス別 CPU | どの層が重いか。ラック（#628）は child 単位 |

足場: `CallbackTimeStats` / `StreamStats` は既に存在する。

## 3. 「リソースが許す限り制約なし」の正直な設計

owner の言葉:

> トラック数とかエフェクト数とかは最終的にはコンピューターのリソースが許す限り制約なし、にするのが良い

### 3.1 現在は固定上限がある（実測 2026-08-31）

| 定数 | 値 | 場所 |
|---|---:|---|
| `DEFAULT_INSTRUMENT_SLOTS` | 8 | `rust/crates/orbit-audio-daemon/src/outproc_instrument.rs:87` |
| `MAX_INSTRUMENT_SLOTS` | **32** | 同 `:89` |
| `MAX_INSERT_BUS_STAGES` | **64** | `rust/crates/orbit-audio-native/src/output.rs:347` |
| `MAX_SOURCE_SLOTS` | **32** | 同 `:350` |
| `MAX_SOURCE_UNITS` | **16** | 同 `:353` |
| `MAX_LINK_CHANNELS` | 64 | 同 `:343` |

### 3.2 🔴 単純な撤廃はできない

これらは **RT スレッドに確保を持ち込まないための固定長配列**である。

> **RT スレッドに確保・ロック・syscall を持ち込まない**

は本プロジェクトの不変条件（#628 設計）であり、上限はその帰結であって、
横着や見積もりの産物ではない。**定数を大きくするのは解決ではない**（先送り）。

### 3.3 達成できる形

```
RT スレッド上では確保しない            （不変条件を守る）
      ↓
プールの拡張は off-thread で行う
      ↓
出来上がったものを atomic に差し替える
      ↓
旧プールは世代番号で退役させる          （在職中の参照が消えてから解放）
```

**この機構は既にある。** #628 の install ring と、世代番号を退役リストの中へ置く設計が
まさにこのパターンで、出荷済みである。**新しい発明ではなく、既存機構の適用。**

したがって「リソースが許す限り制約なし」は **達成可能**だが、実装は
**「定数を大きくする」ではなく「プールを動的に拡張する」**になる。

### 3.4 🔴 上限を消すなら、余裕の表示が先

**上限が消えるということは、ユーザーが自分で限界を判断するということ**である。
判断材料が画面に無ければ、上限の撤廃は「予告なく落ちる」への変更にしかならない。

**§2 が §3 の前提条件。順序を逆にしてはいけない。**

### 3.5 設定項目としての「トラック数」は最終的に消える

途中経過としては「使用 / 上限」を表示し、上限に達したら分かるようにする。
最終形では上限が無いので、表示は「使用数」と「余裕（§2）」になる。

## 4. 出せるのに出していないものの棚卸し

エンジンが持っているが、現在どこにも出していないもの:

| 項目 | 足場 |
|---|---|
| 掴んでいるデバイス名 / サンプルレート / チャンネル数 / バッファサイズ | `record_stream_config` |
| コールバック所要時間（平均・ピーク）・ドロップアウト数 | `CallbackTimeStats` / `StreamStats` |
| **コールバックが止まっていること** | 同上（#661 の発見遅れの主因） |
| ロード済みプラグイン（層ごと・フォーマット・state の有無） | 既存カタログ / seq 状態 |
| child プロセス（PID・CPU・RSS・生死・respawn 回数） | `MAX_CONSECUTIVE_FAST_RESPAWNS` の counter |
| スロット使用状況（使用 / 上限） | §3.1 の定数 |
| transport（走行中か・現在拍・テンポ・拍子） | engine 状態 |
| capture 状態（有効か・書き込み先・書き込み量） | `capture_path_from_env` |
| MCP セッション数 | 既にログには出ている |

**daemon の起動ログは現在 `listening` と `accepted connection` の 2 行しか出さない。**
どのデバイスを掴んだのかログにすら残らない。ここは最優先で埋める。

## 5. 操作として出すもの

| 項目 | 足場 | 状態 |
|---|---|---|
| **MIDI panic** | `MidiOutput.panic()` / `PluginNoteOutput.panic()` | **実装済み**。ただし `stop()` からしか呼ばれず、**ユーザーに到達する経路が無い** |
| オーディオデバイス選択 | `SelectAudioDevice` RPC（#484 D2）/ `rebuild_output_stream` | **実装済み**。ただし #661 の無音バグを直すまで出せない |
| バッファサイズ変更 | `rebuild_output_stream(..., buffer_frames, ...)` | 引数はある。live で効くかは未検証 |

**MIDI panic は「実装済みの関数にコマンドと MCP tool を繋ぐだけ」。**
鳴りっぱなしになった時に押す場所が無い、という状態が現在続いている。

## 6. 🔴 「再起動が必要」は設定ごとの性質であって、UI の飾りではない

owner の言葉:

> エンジン再起動が必要なものはその旨ちゃんと出たりして。一番いいのはリアルタイムに変更できることだけど。

- **全項目に「再起動が必要かも」と出す実装はしない。** 嘘の警告は無視されるようになり、
  本当に必要な時に効かなくなる
- 各項目について **live で変えられるかを実際に検証し**、その結果を属性として持つ
- 未検証は「不可能」ではない。**未検証と書く**

### 6.1 現時点の見立て

| 項目 | live | 根拠 |
|---|---|---|
| オーディオデバイス | 🟢 可能なはず | `SelectAudioDevice` RPC が実装済み |
| バッファサイズ | 🟡 未検証 | `rebuild_output_stream` が引数を持つ |
| トラック数 / ラック数 | 🟡 未検証 | §3 の動的拡張が入れば live |
| サンプルレート | 🔴 再起動 | ストリーム構成そのもの |

### 6.2 ライブ変更の実装範囲には「切り替わったことの確認」を含める

**#661 は「切り替えたつもりで無音になる」故障だった。**
切替 API が成功を返しても、コールバックが回っているとは限らない。

**切替後にコールバックが回っていることを確認するまでが実装。**
確認できなければ切替は失敗として報告する（もしくは元へ戻す）。

## 7. 設定は、その影響とセットで見せる

owner の言葉（2026-08-31）:

> 設定できるだけでなく、それが**どういう影響があるのかが UX 的にわかる**方がいいよね。

**数値だけ出しても判断できない。** 「バッファサイズ 512」と書いてあっても、
それを 256 にすると何が良くなり何が悪くなるのかが分からなければ、触りようがない。

### 7.1 原則: 数値を、その帰結と切り離して出さない

| 設定 | 単独で出すと | 帰結とセットで出すと |
|---|---|---|
| バッファサイズ 512 | 意味不明 | **締切 10.67 ms / 現在の使用率 35%** |
| サンプルレート 48000 | 意味不明 | 締切の分母。48k→96k で**締切が半分**になる |
| トラック数 12 | 意味不明 | **使用率 35% / メモリ 8.4 GB**（あと何層いけるか） |

**§2 の「余裕」は、この原則をレイテンシーに適用したものである。** 本節はそれを全設定へ広げる。

### 7.2 変更前: 予測を出す（プレビュー）

**確定する前に、変えたらどうなるかを見せる。**

```
バッファサイズ    512 → 256
  締切          10.67 ms → 5.33 ms
  使用率(ピーク)  35% → 約 70%   ⚠ 危険域に近づく
  出力レイテンシ  約 21 ms → 約 11 ms
```

- 予測できるもの（締切・レイテンシ）は **計算で出す**
- 予測が難しいもの（実際の CPU 使用率）は **「約」と明示**する。
  🔴 **確定値のように見せない**

### 7.3 変更後: 実測を出す（そして予測より実測を信じる）

**適用したら、実際にどうなったかを測って出す。**

```
バッファサイズ    512 → 256  ✅ 適用済み
  締切          5.33 ms
  使用率(ピーク)  62%（予測 70%）
  ドロップアウト  0
```

**予測と実測がずれたら、実測が正しい。** ずれを隠さず並べて出すことで、
ユーザーは自分のマシンでの実際の関係を学習できる。

これは #661 の教訓の一般化でもある —
**「設定した」と「そうなった」は別のこと。** 後者を測って見せる。

### 7.4 操作にも帰結を出す

設定だけでなく、押したボタンが**何をしたか**を出す。

| 操作 | 出すもの |
|---|---|
| **MIDI panic** | 「**3 ポートに all-notes-off / 発音中だった 17 音を消音**」 |
| デバイス切替 | 切替先・新しいサンプルレート・**コールバックが回り始めたこと** |
| エンジン再起動 | 再ロードしたプラグイン数・所要時間 |

**MIDI panic が「押したけど効いたのか分からない」ボタンだと、演奏中に押せない。**

### 7.5 変えられないものには、理由を出す

「再起動が必要」（§6）と同じ考え方で、**なぜそうなのかまで出す**。

```
サンプルレート  48000 ▾   🔄 エンジンの再起動が必要
                          ストリームの構成そのものが変わるため
```

理由の無い制約は理不尽に見え、理不尽な UI は信用されない。

### 7.6 🔴 予測が書けない設定は、予測を書かない

**もっともらしい数字を並べるくらいなら、空欄にする。**

予測を出す責任は「当てること」ではなく「外れた時に分かること」なので、
**外れを検出できない予測（根拠の無い推定値）は出さない**。
§7.3 の実測欄だけを出し、変更前は「実測してみないと分からない」と書く。

## 9. 決定と却下

| | 決定 | 却下した案とその理由 |
|---|---|---|
| レイテンシー表示 | **締切に対する使用率（ピーク + 平均）** | ミリ秒の生値 — 判断に使えない |
| 上限の撤廃 | **off-thread 確保 + atomic 差し替え** | 定数を大きくする — 先送りでしかない / RT スレッドで確保する — 不変条件違反 |
| 再起動の表示 | **設定ごとの検証済み属性** | 一律に警告を出す — 無視されるようになる |
| 実施の切り方 | **同じコードに触る単位** | issue ごとに 1 PR — デバイス経路を 3 回触ることになる |
| 設定の見せ方 | **値と帰結をセット + 変更前は予測・変更後は実測** | 値だけ出す — 判断できない / 予測だけ出す — 外れても気づけない |

## 10. この設計の出どころ

**2026-08-31 の実測**（本番前夜の障害調査）:

- daemon CPU **0.0%**（`--audio-device` あり）→ **0.6〜1.0%**（なし）。前者はコールバック死
- デバイス名の照合は成功しており、縮退の警告も出ていない（つまり「選択に成功して死ぬ」）
- Kontakt child 7 本が CPU 95〜99% でレンダリング中だった（**音は作られていた**）
- 成功した `instrument()` ロードは**ログに何も出さない**（出るのは失敗時だけ）
- child のプロセス名は `orbit-vst3-instrument-child`（`Kontakt` でも `plugin-host` でもない）

最後の 2 つは調査を誤誘導し、「instrument が黙って無視されている」という
誤った本命仮説を生んだ。**沈黙を「壊れている証拠」と読むのは、沈黙が正常な場合には成り立たない。**
だからこそ §1 の原則が要る。
