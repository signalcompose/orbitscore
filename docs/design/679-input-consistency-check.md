## 1. 確認の観点と結果（要約）

| 観点 | 結果 | 根拠 |
|---|---|---|
| (a) ソースの口に入力が入るか | ✅ **入る**。`BlockSource { render(frames, transport); output(unit) }`（`output.rs:270-273`）は「block ごとに 2ch を出すもの」しか要求しない。入力 = cpal の入力コールバックが書いた ring を `render` で読む `BlockSource` | doc 672 §6.1 / #643 §4（instrument = feed）|
| (b) ライン模型がそのまま乗るか | ✅ 乗る。ソースが違うだけで、`effect` / `gain` / `output(dest, thru, db)` は seq バスの `LineProgram` に対して定義されている（doc 1 §5）。`mic.effect(comp).output(stems, thru: true).output(master)` は**新しい規則を 1 つも要らない** | doc 1 §2・§5 |
| (c) `rec` = ライン要素（位置で dry / wet）は render のタップと同じ資格か | ✅ 同じ。**`rec` はタップ宛先（doc 598 §5 `RenderInstance`）に「録ったものを DSL の素材として名付ける」を足したもの**。書き込み機構（ring → writer・版・合算）は render で作る。→ 地図 §4.P.1 の「対称表」は実装上も対称になる | doc 598 §5・§16 (1)（`%v` の版 = テイク）|
| (d) パンチイン / アウトを `play()` のパターンで書く案は矛盾しないか | ⚠️ **記法の意味が違う**（`play()` は 1..n = スライス・0 = rest。録音は 2 値）。矛盾ではなく**未決**（地図 §9）。ライン模型側に制約は無い | core spec §Slice Indexing |
| (e) 入力の `thru`（入力モニター） | ✅ 同じ意味（先へも流す）。`rec(…, thru: true)` は `output(…, thru: true)` と同じ op（doc 1 §5.3 の `break on thru:false`）。**入力ソースのラインの末尾に `output(master)` を書けばモニター**なので、専用フラグの必要すら無いかもしれない（main の読み・裁定 3 で決める）| doc 1 §5.3 |
| (f) デバイス経路 | 🔴 **出力専用**。`rebuild_output_stream` / `list_output_devices` / `--audio-device` は出力側だけ（`output.rs:1473-1479` / `session.rs:1302-1330`）。入力デバイスの列挙・選択・レート・バッファは**新規**。**#662-A（`GetStatus` に真実）の後**でないと #661 型の無音を作る（#679 チェックリスト）| 地図 §4.O.1 |
| (g) サンプルレート | ⚠️ engine はデバイスレートで構築（`Engine::new(sample_rate, 2)`・doc 1 §5.5）。入力が別レートならリサンプルが要る。**今の設計は 1 レート前提**。入力の設計時に (i) 同一デバイス限定 / (ii) リサンプル / (iii) aggregate device の裁定が要る（地図 §9 の drift 行）| `output.rs:1404-1432` |
| (h) 往復レイテンシ | 🔴 測る手段が無い（`CallbackTimeStats` は出力コールバックのみ）。doc 662 の「何を測るか」に**入力側の xrun と往復**を足す行を予約する（数値目標は置かない）| `post_processor.rs:36-50` |
| (i) 録音の記録（ログ）と再現 | ✅ 矛盾なし。`.orbslog` は**原因**を記録する（doc 694 §0 原則 1）。「録った」事実は `rec` の評価（eval レコード）として残り、録れた音は現象（ファイル）。replay は `rec` を再評価するが**入力が同じ音を出す保証は無い**（ライブ演奏なので当然）。→ replay の `--verify` は入力を含むセッションでは構造比較のみ（Known Decision #21 と同じ扱い）| doc 694 §7 |
| (j) 保存先 | ✅ render の「譜面からの相対」（doc 598 §3.1）と同じ原則で置ける。#456（プロジェクト）の `states/` の隣に `takes/` のような領域を作ればよいが**名前は未決** | #598 コメント 8「決まっていること」|
| (k) プラグイン境界 | ✅ 入力は境界 4（ソースの口）の実装の 1 つ = **コアの `SourceSlot` に乗る first-party ソース**。DSP Plugin Spec §5「標準シンセプラグイン」と同じ節に「Audio I/O 入力」を 1 行足すだけ | doc 672 §6.1・§8 |
| (l) 可視化 | ⚠️ `GetStatus` に入力デバイス / 入力 xrun の field が要る（#662-A の拡張）。**今回の #662-A 設計に「入力側の field は予約（未実装は返さない）」と書いておく** | doc 662 |

**結論: 今回の設計に、入力を後から足す時に壊さなければならない箇所は無い。** 予約が要るのは (h)(l) の**測定 / 可視化の行**と、(g) の**レート前提の明記**だけ。
