## 1. 到達点（1 文）

**層 2 は 1 回の評価の要求（選択・subject-block・MCP のコード片）を 1 度にパースして文の列にし、構文エラーが 1 つでもあれば何も実行せずに位置つきで返し、無ければ文をソースの順に実行して、要求 1 つを 1 バッチ・1 記録にする。鳴っている `play()` の出どころは、engine が振る世代番号を層 2 が文の位置へ対応づけて `transport.step` に載せる。**

## 2. 現状（一次ソースと実測）

### 2.1 凍結版の区切り方 = 「パースできた最短の先頭」ごとに実行

凍結版の REPL（`packages/engine/src/cli/repl-mode.ts`）は行を 1 本ずつ受け、**行を足すたびにバッファ全体をパースし、パースできたらすぐ実行する**:

| 規則 | 一次ソース |
|---|---|
| 空でない行を足すたびに `executeCurrentBuffer(false)` | `repl-mode.ts:548-550` |
| パースのエラーの文言に `EOF` があれば「未完」として溜め続ける（#607） | `repl-mode.ts:410-418` |
| それ以外のパースのエラーは報告してバッファを捨てる | `repl-mode.ts:420-423` |
| パースできたら `execute()` を 1 回（失敗しても報告してバッファを捨てる・#612） | `repl-mode.ts:426-441` |
| 空行 2 連はバッファを強制実行する（未完でもエラーとして確定） | `repl-mode.ts:538-547` |
| `//#evalBegin` / `//#evalEnd` は `AudioLine` のバッチを開閉するだけ（パースの単位は変えない） | `repl-mode.ts:447-457` |
| 診断は `//#evalMark` まで**グローバルに**溜まる（#614） | `repl-mode.ts:381-388`・`:484-485` |

したがって**実行の単位は「行」ではなく「パースが通った最短の先頭」**である。1 行に 2 文あれば 1 回の `execute()`、複数行の文は閉じた行で 1 回。

段階 1 の層 2 の受付口（`packages/session/src/eval/evaluation-intake.ts:150-278`）はこの写しで、凍結版と同じ観測になることを差分テスト（`tests/session/eval-intake-parity.spec.ts`・台帳 P-02）が確かめている。層 2 だけが違うのは、**要求の終わりで必ず強制実行する**点（凍結版の MCP の経路と同じ。人の ⌘Enter の経路は `//#evalMark` を送らず、未完の入力が次の評価へ持ち越される — `run-selection.ts:199` → `engine-process.ts:647-692`）。

### 2.3 `InterpreterV2.execute()` の意味論（1 つの IR の中）

`packages/engine/src/interpreter/interpreter-v2.ts:133-231`:

1. `.orbslog` の記録を **`execute()` 1 回につき 1 件**（`:155-169`）
2. file import（ソースの順・深さ優先・評価ごとの cache）を**自分の宣言より先に**（`:174-195`・spec IM.2）
3. `globalInit`（**IR に 1 つだけ** — `audio-parser.ts:92-93` が後のもので上書きする）（`:197-200`）
4. `documentDirectory`（`:212-216`）
5. `sequenceInits` を**すべて**、文より先に（`:218-221` — 1 つの IR の中では宣言が前へ寄る）
6. 文をソースの順に。**1 つでも投げたら残りは実行しない**（`:224-230`）

つまり「要求を 1 度にパースして 1 回の `execute()` に渡す」（設計 694 §4.1 の `executeFrame`）と、今の行ごとの評価とは **3 点で意味が違う**: 宣言が前へ寄る / `init GLOBAL` が 2 つあると前のものが消える / 実行時エラーで残りが止まる。

**読み飛ばしに頼っている既存の `.orbs` は無い**: リポジトリに追跡されている `.orbs` 127 本を、engine の `AudioTokenizer` と `StatementParser` で文ごとに読み直し、`statement: null` になった文を数えた（2026-10-26・`48b2e92`）→ **0 件**。パースが通らない 4 本は別の理由（`time()` / `fixpitch()` が未実装 ×3・`test-polymeter.orbs` の `Unexpected token in argument: COMMA` ×1）。🔴 E2E の spec の中に文字列で書いた DSL（`tests/e2e/*.ts`）は数えていない（§7 の検算で拾う）。

### 2.5 設計 694 §4 の「フレーム」は半分だけ入った

設計 694 §4.1 は `//#evalBegin` … `//#evalEnd` の中を「`parseAudioDSL` 1 回 → `execute()` 1 回、構文エラーはフレーム全体を棄却」と決め、§4.2 で意味の変化（選択 3 文の 2 文目が構文エラーなら何も実行しない）を明示していた。凍結版に入ったのは**バッチの開閉だけ**で、フレームの中も行ごとにパース・実行している（`repl-mode.ts:447-457`・計画 `IMPLEMENTATION_PLAN_NATIVE.md` の PR-L2 の行）。#695 が開いたままなのはこのため。

### 2.6 評価はタイミングの経路に乗っていない

音の時刻を決めているのは評価ではなく発音の経路である（設計 848 §4.6 の表）: `audio()` は TS の 1 ms の poll + lookahead で daemon の時刻を付けて送り、daemon がサンプル精度で鳴らす（`rust-engine-player.ts:14-19`）。ループの次の周期は境界の `LOOP_TIMER_LEAD_MS = 100` ms 前に積む（`loop-sequence.ts:14`）。評価（パースと実行）が速いか遅いかは、**次の境界に間に合うか**にしか効かない。

## 4. 決めること

### 4.1 区切りの単位 — 3 つの層に分けて決める

「行・ブロック・意味」は、実は**別の問いの答え**である:

| 層 | 問い | 今 | 本書の推奨 |
|---|---|---|---|
| **U1 展開** | 何を評価するか（選択が空の時に何を取るか） | 選択があればその範囲、無ければカーソルの行の subject-block か単独の文（凍結版 `run-selection.ts` → 層 2 `host/selection-block.ts`） | **変えない**（D-U1） |
| **U2 分割** | 評価するテキストをどこで切って実行するか | パースが通った最短の先頭ごと（§2.1） | **要求を 1 度にパースして「文」で切る**（D-U2） |
| **U3 まとまり** | 何を同時に変える 1 まとまりにするか | 要求 1 つ = 1 バッチ（`AudioLine`）・記録は `execute()` ごと | **要求 1 つ = 1 バッチ = 1 記録**（D-U3） |

**D-U1 展開は変えない（S-eval では）**。subject-block の規則は凍結版と同じものを層 2 が持ち（`selection-block.ts`・凍結版との突き合わせは `tests/session/editor-parity.spec.ts` の 16 通り）、⌘Enter で何が評価されるかを拡張版とアプリでずらさない（設計 848 §5.4）。既知の粗さ（括弧の数を文字列やコメントの中でも数える・行頭の識別子だけで所属を決める）は、AST で subject を決める案として §8 に残す。理由: 展開を変えると「何が鳴るか」が変わり、golden（D-2）と演奏者の手の慣れの両方に触れる。U2 / U3 の変更と同じ束に入れると、差がどちらの変更から来たか切り分けられない。

**D-U2 分割 = 要求を 1 度にパースして文で切る**:

- 要求の `code` 全体を engine のパーサで 1 度に読み、**文の列（各文のソース上の範囲つき）**にする
- 「未完」の概念を捨てる: 要求の終わりで閉じていない文は、その文の構文エラー（設計 694 §4.1 と同じ。要求は提出の境界）
- 空行は文を切らない（実測 f の「空行 2 連が文を割る」は stdin に手で打つ REPL のための規則で、要求が必ず完結して届く層 2 には要らない）
- 行頭の `.` で続くチェーンは前の文に付く（実測 e。パーサは既に受けている — §2.2 の参考値）
- 文の**実行はソースの順**（§2.3 の「宣言が前へ寄る」をしない = 今の行ごとの評価と同じ順）

代案と棄却の理由:

| 代案 | 内容 | 棄却の理由 |
|---|---|---|
| 今のまま（最短の先頭） | — | 実測 c / e / f / h の誤りが残る。#695 が直らない |
| 要求 = 1 回の `execute()`（設計 694 §4.1 の `executeFrame`） | 1 度にパースして IR をそのまま `execute()` へ | §2.3 の 3 点（宣言が前へ寄る・`init GLOBAL` の上書き・実行時エラーで残りが止まる）で、**正しい DSL でも**今と結果が変わりうる → D-2 の golden に触れる危険。文の位置も IR に残らない |
| 行で切る（厳密に 1 行 = 1 評価） | — | 複数行の文（spec「Multiline Parentheses & Chaining」が保証する書き方）が書けなくなる |

**D-U3 まとまり = 要求 1 つ = 1 バッチ = 1 記録**:

- `AudioLine.beginBatchAll()` / `endBatchAll()` は今と同じく要求 1 つで 1 回（#611 §5.7）
- `.orbslog` の記録は**要求 1 つにつき 1 件**（`code` = 要求の `code`）。#695 と設計 694 §4 の目的。`SESSION_LOG_SPEC_v1.md` §3.1 の「`code` 粒度 = `execute()` 単位」は S-eval の最初の PR で先に改訂する（spec が正本・運用規則 6）
- 要求は 1 本の FIFO で直列に処理する（今と同じ・#476）

**判定を誰がするか**: すべて層 2（設計 848 §5.4 の「層 2 が同期済みの文書と範囲から決める」）。U1 は `editor.runSelection` の中で同期済みの文書から、U2 / U3 は `session.evaluate` の受付口で。エディタのクライアントは選択の位置を返すだけで、区切りの判断を持たない。

### 4.2 途中のエラー — 何を実行し、何を実行しないか

**D-E1 構文エラー = 要求の全体を実行しない**（🔴 owner 確認 Q-1）:

- パースが 1 か所でも失敗したら、**どの文も実行しない**。診断は位置つき（要求の `code` の座標・`target` があれば文書の座標も — §4.4）で返す
- 理由: (1) 1 回の評価は「同時に変える 1 まとまり」（D-U3）で、`hh.play(…)` だけが入って `LOOP(hh)` が入らない、のような**書いていない状態**を作らない (2) パースは実行の前に全部終わるので、断っても音は何も変わらない — 直して流し直せばよい (3) 設計 694 §4.2 が同じ意味の変化を既に明示し、`play`（ファイル全体を 1 回の `execute()`）の意味論と揃う (4) 参考: SuperCollider はブロックを 1 つの関数としてコンパイルし、構文エラーがあればブロックの全体を実行しない。TidalCycles もブロックを 1 つの式として評価する（いずれも一般的な知識で、本書の作成時に一次資料では確かめていない）
- 代わりに失うもの: 大きな選択の中に 1 か所の打ち間違いがあると、今は残りが鳴る（実測 c 以外の多くの形で）が、新しいかたちでは何も変わらない。演奏中にこれを嫌うなら Q-1 の B（読める文だけ実行する）になるが、**どこまでが壊れた文かの判断**（実測 c の 1 行目は閉じていないので 2 行目まで飲み込む）がパーサの回復の質に依存し、何が実行されたかが読めなくなる

**D-E2 実行時エラー = その文だけ失敗し、残りの文は実行する**（今と同じ・owner 確認 Q-2）:

- 実行時エラー（未定義のシーケンス・ファイルが無い・プラグインの attach の失敗など）は実行してみるまで分からず、**取り消せない**（前の文の効果はもう出ている）。選べるのは「止める」か「続ける」だけ
- 続ける理由: 実行時エラーの多くは環境の側（サンプルが無い・プラグインが無い）で、1 か所の欠けが他の行を巻き込まない方がよい。今の行ごとの評価と同じなので「違いの記録」に載らない（golden にも触れない）
- 診断には失敗した文の位置を付ける（今は文言だけ）

**D-E3 パーサの読み飛ばしをやめる**（#965・🔴 owner 確認 Q-3 = DSL の受け入れる入力が変わる）:

- `parse-statement.ts:80-84` / `:514-517` で `null` を返して黙っていた所を、位置つきの構文エラーにする（「文として読めない」「識別子の後に `.` が無い」）
- D-E1 と合わせると、実測 a / b / j は「何も実行せず、位置つきのエラー」になる
- 🔴 **`;` の扱いを決める必要がある**: 今は `;` が黙って捨てられており（実測 k）、`kick.play(1); hat.play(1)` が 2 文として通る。A `;` を文の区切りとして spec に足す / B `;` もエラーにする。**推奨 A**（LLM と JavaScript に慣れた人が書きやすく、既存の振る舞いを保つ）。これは DSL の構文の追加なので owner の確認が要る
- 🔴 **訂正（2026-10-26・実装の着手時に一次ソースで確かめ直した）**: `;` を捨てているのは**パーサではなくトークナイザ**（`packages/engine/src/parser/tokenizer.ts:277-279` の `default: // Skip unknown characters`）。したがって D-E3（パーサ）だけでは `;` はエラーにならない。トークナイザは `;` 以外にも、文字列とコメントの外の DSL が使わない文字（`!` `?` `$` `&` `|` `<` `>` `\` `` ` `` や英字でない文字）をすべて黙って捨てている（例: `kick.play(1, 0)!!!` が通る）。これは #965 と同じ「黙って捨てる」の別の経路なので **Q-7** に足した。追跡されている `.orbs` 127 本で、文字列とコメントの外にこの種の文字を使うものは **0**（2026-10-26 に走査）
- 影響の範囲: 追跡されている `.orbs` 127 本で読み飛ばしに頼るものは 0（§2.4）。パーサは凍結版の拡張と CLI の `play` も使うので、**凍結版の `.vsix` を main からビルドし直した場合は拡張版も厳しくなる**（4.4.0 のタグからビルドした `.vsix` は変わらない — §4.7）

### 4.3 `@import` をまたぐ評価

**D-I1 import の規則（spec IM.1〜IM.6）は変えない**。そのうえで、要求を 1 度にパースする（D-U2）ので:

- **IM.1（import は先頭）が要求ごとに効く**: 実測 h の 2 行を選んで流すと、ファイル全体を `play` した時と同じ IM.1 のエラーになる。正しいファイル（import が先頭にある）の連続した範囲を選ぶ限り、この規則には当たらない
- import の評価の順（ソースの順・深さ優先・自分の宣言が最後・評価ごとの cache）は `processFileImports`（`process-file-import.ts`）のまま。要求の中の import は、**その要求の他の文より先に**評価する（IM.2 の「import 元自身の宣言が常に最後」を要求の単位で守る）
- 実行時エラーの扱い（D-E2）は import の失敗にも同じ: import が失敗したら、その要求の残りの文は**実行しない**（import した名前に依存する文を、名前が無いまま実行しない）。🔴 これは D-E2 の唯一の例外で、今の `execute()` の振る舞い（import の失敗は投げて残りを止める・`interpreter-v2.ts:186-194`）と同じ

**D-I2 何を読み直すか** — 今と同じ（IM.5）: import 文を含む要求を評価した時だけ、import 先をディスクから読み直す。import 文を含まない要求は import 先に触れない。import 先だけを編集しても自動では反映しない（ファイルの監視は v1 の外）。

**D-I3 import 先を同期済みの写しから読むか**（🔴 owner 確認 Q-4）: ネイティブ版の層 2 は開いている文書の写しを持っている（設計 848 §5.5）。import 先が開いていて**保存していない編集**がある時:

| 案 | 内容 | 得失 |
|---|---|---|
| **A ディスク（今と同じ）** | 常にディスクのファイルを読む | CLI の `play`・`.orbslog` の replay（import の本文と sha256 を記録する・設計 694 §6）と同じ結果。保存し忘れた編集は鳴らない |
| B 開いていれば写し | 開いている文書は写しを読む | 画面に見えているものが鳴る。だが保存していない内容で鳴った演奏は、ファイルからは再現できない（replay は記録した本文で再現できる） |

**推奨 A**（S-eval では今の振る舞いを変えない。B は「よりプログラマブルな DSL」（§0 の 5）で import が増えた時に、保存していない import 先を警告する案と一緒に考える）。

**D-I4 ファイルをまたぐ名前** — 今と同じ（IM.2 の平らな名前空間・後から評価された定義が勝つ）。2 つの文書を開いた時も同じ名前空間（§0 の 5）。モジュールのスコープ（`export`・隔離）は spec が v2 に予約しており、本書では決めない。D-U2 で要求を 1 度にパースし、文ごとに位置を持つようにしておくことは、後でスコープを足す時の前提（どの名前がどの文書のどの文から来たか）になる。

### 4.4 再生位置の出どころ（#987）

**D-P1 B 案（世代番号）を採り、対応づけは層 2 が持つ**（§0 の 6 で owner が #987 に残した案）:

1. **engine**: シーケンスごとにパターンの**世代番号**を持ち、`play()` / `_play()` が呼ばれるたびに 1 つ進める。鳴った時の step（今の `[STEP]` 行 = 層 2 の `transport.step`）に世代番号を載せる。`[STEP]` を出す所は 2 つある（audio の側と `midi-scheduler.ts:172-176` — #987 のコメント）
2. **engine**: 世代番号を進めた時に、型付きの出力の口（台帳 P-07 の N1-d3）へ `{seq, generation}` を出す
3. **層 2**: D-U2 で文を 1 つずつ実行しているので、ある文の実行中に出た `{seq, generation}` は**その文のもの**と決まる。層 2 が `(seq, generation) → {evalId, 文の範囲}` を覚え、step を受けたら `transport.step.source` に `{evalId, start, end}`（鳴っている `play(…)` の呼び出しの範囲。どの引数かは今と同じく `argPath` で示す）を入れる
4. 鳴っているパターンが変わる（世代番号が変わる）まで、`source` は前の `play()` のまま。`LOOP` / `RUN` で反映されるまで表示が先に動かない（#987 の完了条件の案のとおり）

engine は文書の位置を知らない（世代番号だけ）。コメントの中の `play()`（#987 のコメントの 1）は実行されないので、構造的に選ばれない。

**D-P2 座標** — `StepSource` は今の v1 のスキーマどおり**要求の `code` の座標**（0 始まり・UTF-16）。🔴 ただし **subject-block（D-U1）は文書の離れた行を `\n` で繋いだ `code`** なので、`code` の座標から文書の座標へは `target.range` の始点を足すだけでは戻らない。そこで:

- 層 2 の中だけで「`code` の行 → 文書の行」の対応表を持つ（`editor.runSelection` が展開した時に作る。wire には載せない）
- `StepSource` に省略可能な文書の座標（`document?: {uri, version, start, end}`）を足す（🔴 プロトコルの追加 = MINOR・main / owner の確認 Q-5）。エディタは自分の文書の座標をそのまま使える
- MCP のコード片（`target` が無い）・import 先の文の `play()` は `source: null` のまま（スキーマの説明どおり）

### 4.5 実装の置き場 — TypeScript のまま

**D-L1 区切りと実行は TypeScript（層 2 の受付口 + `packages/engine` のパーサと interpreter）に置く**:

- 理由 (1): 評価は音の時刻の経路に乗っていない（§2.6）。評価の速さが効くのは「次の境界の 100 ms 前（`LOOP_TIMER_LEAD_MS`）までに実行が終わるか」だけである。1 選択のパースと実行にかかる時間は**未測**（下の再検討の条件で S-eval に測る）
- 理由 (2): DSL の意味は `packages/engine` の 1 か所（設計 848 §10.3）。区切りを Rust に移すと、パーサと interpreter（TS）の手前に別の言語の構文の知識が要り、DSL の解釈が 2 か所になる
- 理由 (3): タイミングを Rust へ移す判断は、設計 848 §4.6 の T-1（N0-d）が実測で行う（楽器のノートの 5 ms の poll が対象・台帳 P-06）。区切りの置き場とは独立に決められる
- **再検討の条件**: S-eval で「1 要求の受付から実行の終わりまで」の時間を測り（典型の選択と、ファイル全体の 2 通り）、p99 が `LOOP_TIMER_LEAD_MS` の半分（50 ms・置き値 = 台帳 P-08）を超えたら、遅い所（パース・import の読み込み・実行）を特定して置き場を考え直す

### 4.6 設計 848 §5.3.1 が #997 に回した 4 つの問いへの答え

| 問い | 答え |
|---|---|
| 区切りの単位を `target` から決めるか | **`code` から決める**（D-U2）。`target` は位置の対応づけ（診断・#987）と帰属（`.orbslog` の `sourceFile`）に使う。U1 の展開だけは同期済みの文書から（`editor.runSelection`） |
