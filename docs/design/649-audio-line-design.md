# #649 オーディオラインの設計 — フェーダーという段を作らない

**Issue**: [#649](https://github.com/signalcompose/orbitscore/issues/649)
**確定**: owner との議論（2026-08-29）
**旧稿**: `649-fader-placement-design.md`（**破棄**。ハードウェアのミキサーを写そうとしていた）

## 0. 出発点の誤り

最初この issue を「ミキサーの各段にフェーダーを新設する」と書いた。それは
**ハードウェアのミキサーを写す**設計だった。

> 技術仕様的にハードウェアを作っているわけではないわけだから、**ソフトウェアとしての
> 言語としての表現で考える**方がいいのではないでしょうか。（owner）

DAW の `pre-fader` / `post-fader` / `post-pan` が 2〜3 値しか無いのは、
**フェーダーが物理的に1つで、位置が固定されているから**である。だから「その手前か後ろか」
しか言えない。Logic が `Post Pan` を足したのも、パンという別ステージが増えたぶん選択肢を
1つ足しただけで、同じ制約の中にある。

**OrbitScore はチェーンを言語で書く。位置を語彙で指す必要がなく、書いた場所がその位置になる。**

## 1. 中核 — 2つの領域と、その境界

| | 順序が**決まっている** | 順序が**自由** |
|---|---|---|
| 何が流れるか | ノート / ピッチ / 再生の指定 | **オーディオ** |
| 例 | `play()` `root()` `octave()` `instrument()` / `audio()` `slice()` | `effect` `Gain` `send` `output` |
| なぜ | **意味が順序に依存する**（音源より後ろにピッチは置けない） | **どの順でも意味が通る。順序がそのまま結果** |

🔴 **境界は「音が生まれる点」。** instrument も audio も、そこから先は同じ扱いになる。

```js
kick
  .audio("kick.wav")        // ← ここまでが「どう鳴らすか」（順序が決まっている）
  .play("x--x")
  // ── ここから下はオーディオライン（順序が意味） ──
  .send("rev", 0.3)         // 素の音を送る
  .effect("Reverb")
  .gain(-6)
  .send("cue", 1.0)         // ゲイン込みで送る
  .output("drum")           // 出口
```

## 2. 帰結

### 2.1 「フェーダー」という段は作らない

`gain` は**チェーン上の1要素**であり、特別な段ではない。
**たまたま末尾に置かれたものが、DAW でいうフェーダー**というだけ。

### 2.2 `pre` / `post` フラグは要らない

DAW の3値は、この記法の**特殊なケース3つ**にすぎない。

| DAW の語 | この記法での書き方 |
|---|---|
| pre-fader send | `send` を `gain` より**前**に置く |
| post-fader send | `send` を `gain` より**後**に置く |
| post-pan send | `send` を `pan` より**後**に置く |

**チェーン上の任意の点から送れる**ので、3値の列挙より表現力が広い。

### 2.3 バス / マスターも同じ記法（owner 確定: 案 A）

```js
sum("drum").effect(["GlueComp", Gain(db: -3)])
global.effect(["Limiter", Gain(db: -1)])
```

**同じ資格で扱える。** 「全部が合流した後」という位置の意味は**マスターという受け皿が持つ**ので、
チェーン内の並びを固定する理由にはならない。

### 2.4 糖衣

```js
kick.gain(-6)                        // = チェーン末尾に Gain(db: -6) を置く
kick.effect(["Reverb", Gain(db:-6)]) // 明示形
```

`seq.gain()` / `global.gain()` は**チェーン末尾の `Gain` の糖衣**。

## 4. 現状との差（何が壊れているか）

| いま | あるべき |
|---|---|
| `seq.gain()` が**発音側**（`event-scheduler.ts`）に畳み込まれ、**audio 専用**で instrument に無い | チェーン要素。**audio / instrument で同一** |

## 5. 完了条件（すべてキャプチャで測る）

1. **`global.gain(-6)` が instrument の音を約半分にする** — RMS 比 **0.45〜0.55**
2. **`seq.gain(-6)` が instrument に効く**（いま存在しない機能）
3. 🔴 **`send` の位置で送られる音が変わる** — 同じシーケンスで
   `send` を `effect` の前に置いた時と後に置いた時で、**AUX の音が異なる**ことをキャプチャで示す
4. 🔴 **`send` を `gain` の前後に置き分けると、AUX への送出量が変わる／変わらない**
   （= DAW の pre/post を記法で表現できていることの証明）
5. **`gain` を `effect` の後に置くと、残響比が変わらない**（dry/wet ±10% 以内・全体 RMS は半分）
6. **バス / マスターのチェーンに `Gain` を書ける**
7. バス無し経路の出力が **bit 一致**
8. `npm test` 全緑 / cfg 4象限 / clippy 両 feature / **RT に確保・ロック・syscall を足さない**

## 6. 触ってはいけないもの

1. **RT スレッドに確保・ロック・syscall を持ち込まない**
2. **lock 順序 pump → mailbox**、sink の非ブロッキング契約
3. **`EVT_SLOTS = 2`** とその導出
4. **音が生まれるまでの順序**（`play()` / `root()` / `instrument()` / `audio()` の意味論）
5. **バス無し経路の bit 一致**
6. **`gain_random` の意味論** — 発音ごとの揺らぎ（ベロシティ相当）であり、
   **オーディオラインの要素ではない**。発音側に残す

## 7. 確定事項（owner 2026-08-29）

### 7.1 チェーンは宣言的（ただし評価の粒度は §7.4 が決める）

既存の規範:

> `effect([A1, A2])` の後に `effect("B")` を評価すると **A1 と A2 はアンロードされ、
> チェーンは `[B]` になる**（SC.10.1）

**書いた像で置き換わる。** ただし「何が1回の評価に含まれるか」は **§7.4**（主語ごとの全行）が
決める。**この2つを混同すると「gain だけ書いたらエフェクトが消えるのか」という
存在しない問いが生まれる**（実際に私と Fable が生んだ）。

### 7.2 `seq.send()` のメソッド形は**廃止**（破壊的変更・owner 了承済み）

**send の意味は位置で決まる。** チェーンの外にあるメソッド呼び出しは**位置を持たない**。

「末尾に置く糖衣として残す」と、**同じ `send` という語が2つの意味を持つ** — 一方は
「書いた場所」、もう一方は「常に末尾」。**記法モデルが消したはずの隠れた規則そのもの**になる。

したがって **`send` はチェーン要素のみ**。

### 7.3 🔴 `output` は終端ではない — 後ろに音が届かないのは位置の帰結

> アウトプットは**終端である必要はない**。例えば行が分かれてたとしても、**アウトプットよりも
> 下の行はオーディオが届かない**のが正しい。チェーンの中で終端に来てなければ、**その終端よりも
> 後ろには音が届かないだけ**であるべき。（owner 2026-08-29）

`output` は「**そこへ音が出ていく**」という要素であり、**特別な資格を持たない**。
その後ろに音が届かないのは、**書いた位置の帰結**であって「`output` が終端だから」ではない。

**行が分かれていても同じ。** `output` より下の行にはオーディオが届かない。それだけ。

🔴 **エンジンはエラーを投げない。** 「到達不能を検出して拒否する」のはランタイムの仕事ではない。
エディタの診断で「この後ろには音が流れません」と**知らせる**のは適切だが、**評価を止めない**。

> **DSL 表面（2026-09-03 確定・#611）**: この「後ろへ流すかどうか」は `output` の引数
> **`thru:`（既定 `false`）** として表面に出る。`thru: true` なら出口はタップ（分岐）になり
> 信号は先へも進み、`thru: false` ならその位置で終端する。`send` はその糖衣
> （`send(aux, db) ≡ output(aux, thru: true, db: db)`）。正本は
> [`611-output-line-design.md`](611-output-line-design.md) §2.1 / §2.3。

### 7.4 🔴 評価は「主語ごとの全行」 — 「残るか消えるか」は問いにならない

**私（main）と Fable が揃って間違えた点。** 実装を確認して確定した。

`extension.ts:2738` の **subject-based block evaluation**: 選択範囲が無いとき、エディタは
`getLineSubject` で主語（`kick` 等）を判定し、**その主語に属する全行を集めて**評価する。

```js
var kick = init global.seq
kick.audio("kick.wav").play("x--x")
kick.effect(["Reverb"])
kick.gain(-6)            ← ここで実行すると kick の全行がまとめて評価される
```

したがって **`kick.gain(-6)` だけが単独で評価されることは、通常の操作では起きない。**

> 既存の DSL の評価の仕方が、その行かもしれないし、ブロックみたいな形になっていると思うんですけど、
> **それに合わせていればいいだけの話**だと思うんですが（owner）

**「ライン全置換か部分マージか」という問いは、評価モデルを見ていなかったから出たもの。**
既存の評価粒度に従えばよい。設計に新しい規則を足す必要はない。

### 7.5 🔴 ゲインはラックの中の要素ではない — ラックは維持する

> **エフェクトとゲインは基本的に関係がない**。ここで言ってるフェーダーの話と標準プラグインの
> 話がごちゃごちゃになってる気がして。（owner）

私と Fable は `Gain` を **`effect([..., Gain(db:-6)])` とラックの中の要素**として扱っていた。
しかし**ラックが1つのオブジェクトである理由は「プラグインの順序を決めなければならない」から**
であって、**ゲインがその中にいる必然性はない**。

```js
kick.effect(["Reverb", "Comp"]).gain(-6)
     └── 順序が要るからラック ──┘  └ ラックの外 ┘
```

#### ラックは維持する（owner 確定 2026-08-29）

> エフェクトをラックにしてるところは**もう作ってある**し、ラックにしておくことで
> **チェーンの記述が汚くならない**という良さがあるので、**一旦このラックはラックで残して**
> おいて、場合によってはエフェクトだけチェーンで書けるように後からしてもいい。（owner）

- **`effect([...])` のラック記法は現行のまま**（#628/#639 で出荷済み）
- **ゲイン等はラックの外**にチェーン要素として置く
- 「エフェクトも1つずつチェーンに書ける」は**将来の選択肢として残す**（v1 では作らない）

**理由**: `layer([...])` の並列と組み合わせた時、チェーンを完全自由にすると
「どこで分岐してどこで合流するか」が増える。**ラックが塊であることが、いま複雑さを抑えている。**

### 7.6 🔴 原理は1つ

> **メソッドチェーンの順序が、オーディオラインでは決定論になる。**（owner）

要素ごとの特別扱いは**存在しない**。`gain` も `send` も `output` も `pan` も、
**オーディオラインに乗るオブジェクト**であり、**置いた位置で役割が決まる**。

「`output` は終端か」「`pan` は要素か」といった問いは、**要素ごとに特例を探す発想**から出る。
この原理の下では**問いにならない**。

## 9. 実装を読んで確定した事実

### 9.1 評価の経路は3つ。すべて `writeCodeToEngine` に収束する

| 経路 | 実装 | 粒度 |
|---|---|---|
| エディタ・**選択あり** | `extension.ts:2734-2737` | **選択テキストそのまま**。1 行でも渡せる |
| エディタ・**選択なし** | `extension.ts:2739-2785` | `getLineSubject` で主語判定 → **同一主語の全行を収集**（括弧バランスで継続行も） |
| **MCP** `evaluate_orbitscore` | `mcp-server.ts:539-556` | **呼び出し側が渡した文字列そのまま** |
| MCP `run_selection` | `mcp-server.ts:749-760` | 上のエディタ経路を呼ぶだけ。**第4の粒度は無い** |

`extension.ts:2884-2887` のコメントが明言: *"Shared by the editor Run Selection command and
the MCP evaluate_orbitscore tool so both go through the exact same path"*

🔴 **owner が言及した「同じコンテキストのものを評価する」独立経路は、実装に存在しない**
（コマンド一覧 `:369-401` を全数確認）。主語ブロック収集（同一主語 = コンテキスト）がそれに当たる。

### 9.2 🔴 エンジンは文書を持たない

**評価とは「テキストを engine の stdin に書く」ことである。** それだけ。

したがって **「再評価のたびにソースを読み直す」は物理的に不可能**。
（main はこれを前提に「新しい規則を足さずに済む」と考えていたが、**成立しない**）

engine 側の実行単位は**文**（`cli/repl-mode.ts:288-360`・FIFO で直列処理）。
**エンジンには「どこからどこまでが 1 回の評価か」が今は見えない。**

### 9.3 メソッドは完全に独立したスライスを更新する

| メソッド | 書き換えるもの | 残すもの |
|---|---|---|
| `gain()` / `pan()` | `GainManager` / `PanManager`（独立フィールド） | 他の全部 |
| `send()` | `_auxSends: Map<string, number>`（**aux 名キー・同名上書き**） | 他の全部 |
| `output()` | `_sumOutputBus` / `_renderBus` / `_outputChannel`（**別フィールド**） | 他の全部 |
| `effect()` | `_insertBus`（ラック像は置換 = SC.10.3b） | **routing フィールドは触らない** |

**統合された「ライン」状態は存在しない。** 現在の「位置」は**コードに固定で埋まっている**
（発音側 gain/pan → ラック → sends → output）。

🔴 **したがって `kick.gain(-6)` を単独評価しても `effect()` は呼ばれず、何もアンロードされない。**
v1/v2 の「像 = 評価」は**設計が発明した規則**であり、既存の動き方ではなかった。

### 9.4 位置の情報は実行時に捨てられている

`parser/types.ts:270` の `MethodChain[]` は呼び出し順を持つが、
`process-statement.ts:275-287` が index 順に `dispatchCall` するだけで、
**各メソッドが独立フィールドに書いた時点で順序は失われる**。

## 10. 設計 — 位置を「要素の属性」として持つ

> 🔴 **§10〜§12 は [`611-output-line-design.md`](611-output-line-design.md) へ移管した**（2026-09-03）。
> 実装の正本は 611 側であり、**本節は起案時の形として残す**。差分は各項の「611 での扱い」を見ること。
> §1〜§9（原理・確定事項）と §13〜§15 は本書が引き続き正本。

### 10.1 新設するのは順列 1 つだけ

**`_lineOrder`**: 要素キーの順列（例 `['rack', 'gain', 'send:rev', 'output']`）。
**値は今のスライスに残る。** 既存の独立更新モデルを壊さない。

| 要素 | 同一性 | 既存の置き場 |
|---|---|---|
| ラック | 単一 | `_insertBus` |
| フェーダー / パン | 単一 | `GainManager` / `PanManager` |
| **send** | **aux 名キー** | `_auxSends` の各エントリ |
| output | 単一 | `_sumOutputBus` ほか |

> **611 での扱い（正本）**: 順列と値を分けず **`_line: LineElement[]` に値も同居**させ、
> スライス（`_sumOutputBus` / `_auxSends` / `_renderBus`）は**廃止**する。
> `output` の同一性は「単一」ではなく **`send` と同じく宛先キー**である（同じ宛先への
> 複数 `output` は 2 要素として両方加算・doc 611 §14 (3)）。611 §2.6 / §3.1。

### 10.2 位置の更新規則（カーソル規則・評価バッチ単位）

評価バッチごと・シーケンスごとにカーソルを持ち、ライン要素の呼び出し順（= テキスト順）に:

1. **カーソル以降に存在** → 動かさない。カーソルをそこへ進める
2. **カーソルより前に存在** → カーソル直後へ移動（書いた順序の主張）
3. **新規** → カーソル直後に挿入
4. 🔴 **バッチ内にライン要素が1つしか現れなければ、何も動かない**

帰結:

- `kick.gain(-6)` **単文** → **値だけ更新。位置不変。何も消えない**
- **主語ブロック評価** → 行順がそのまま位置になる（行を入れ替えて再評価すれば並びも変わる）
- 文内チェーン `.send().effect().gain()` → `MethodChain[]` の順
- `output` の後ろに書いた要素 → output より後ろの位置（音は届かない・§7.3）

### 10.3 評価バッチ境界（唯一の新機構）

§9.2 のとおりエンジンには評価境界が見えない。**行を跨ぐ順序主張には境界が要る。**

`writeCodeToEngine`（全経路の唯一のチョークポイント）が `//#evalBegin` / `//#evalEnd` を注入する。
**`//#evalMark`（#614）と `setDocumentDirectory` 注入の、既存パターンの3例目。**

生 stdin（手動 REPL）は文 = バッチに退化し、値更新として安全に動く。

### 10.4 新規作成の既定位置（🔴 owner 確認 1 件）

単独文で**初めて**要素を作る場合だけ、置く規則が要る。

**推奨: チャンネルストリップ既定 `[ラック → gain → pan → sends → output]`**
— 現行実装の固定順（§9.3）と MX.3「post-fader 固定」を再現し、
**既存スコアの独立文スタイルが挙動そのままで動く**。

> **611 での扱い（正本・owner 裁定 2026-09-03）**: 既定は
> **`[ラック → gain → pan → sends(= output thru:true) → output(master)]`**。
> `sends` は独立の種別ではなく `thru: true` の出口として同じ列に並ぶ。
> `pan` は **ライン要素**である（Q-611-4 = B・611 §2.4b。バス上の L/R バランスとして
> instrument にも効く。per-event / ランダム pan は発音側のまま）。
> `seq.gain(固定)` の既定位置は**ラック後**（Q-611-8）。ただし位置は自由で、
> `gain` / `pan` / 標準プラグインはラック内にもライン上にも置ける。611 §2.4b / §2.6。

### 10.5 削除

評価は「書かれたもの」しか運ばない（**不在は伝わらない**）ので、行の削除は要素を消さない
— **これは今日の挙動そのもの**。各要素の既存リセットイディオム（`gain(0)` / `send(aux, 0)` /
`output("master")` / `effect([...])` の像置換）を維持。**新規則なし。**
