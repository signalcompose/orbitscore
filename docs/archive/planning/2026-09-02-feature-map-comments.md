## 1. Splice — MCP サーバがあるので統合の形が変わる（#666）

> これAPIとかないのかなぁ、、、／ VST3だとLLM側から使えないよね。／ **というかMCPサーバあるじゃん。**

**事実確認**: Splice は**公式のリモート MCP サーバ**を提供している。エンドポイントは
`https://mcp.splice.com/mcp`、現在 **beta**。自然言語でのサンプル検索・stack 構築・
ダウンロードまで持ち、Claude Code / Codex / Cursor / VS Code から接続できる。

**構図が変わる**:

| | 誰が使うか | 何をするか |
|---|---|---|
| Splice Sounds VST3（#666 の元案） | **人間** | アプリ内でブラウズ・試聴・ダウンロード |
| Splice MCP サーバ | **LLM** | 検索してローカルへダウンロード |

LLM は MCP から落とし、OrbitScore は**落ちてきたファイルのパスを受け取るだけ**でよい。
Splice 連携を自前で実装する必要がない。

**#666 のスコープが縮む**: 「Splice を統合する」ではなく
「**ダウンロード先を OrbitScore のプロジェクトが解決できる形にする**」。
これは import 宣言（#456 系）と同じ問題に落ちる。

**制約**: ダウンロードはアカウント・サブスクリプション・クレジットに依存するので、
**CI や無人 E2E からは駆動できない**。beta なので契約が変わりうる。

**過去の誤り**: 以前 main が「Splice に公開 API は無い」と書いたのは誤りだった
（検索語が悪く別物の Splice を拾っていた）。公式の Splice Sounds VST3 も実在しカタログにも載っている。

## 2. リアルタイム・サンプリング — 設計 issue **#679**

> AudioDSL にリアルタイムに楽器の演奏をサンプリングするような仕組みを追加して
> （サンプルのトリガーは何かしらの恣意的なトリガーもしくはループの頭、など考えないとならない）、
> それを AudioDSL の中で使えるようにしたい。
> ある意味 DAW の入力を作り分けだけど、Ableton, Bitwig, Opcode Vision 的なオーディオの扱いになるのかなと。

**現状との距離**: OrbitScore には**オーディオ入力の経路が無い**。capture（`capture.rs`）は
出力を WAV へ書くもので、入力ではない。cpal は入力ストリームを扱えるので土台はある。

**設計で詰めること**:

- **トリガーの意味論**（owner 自身が「考えないとならない」と書いている箇所）。
  「ループの頭」は transport が持つ情報なので DSL から指せる。「恣意的なトリガー」は
  MCP からの明示コマンドか、DSL の評価そのものか
- **録れたものの同一性**。録音結果は `chop()` や `slot` の対象になるのか、
  それとも別種のソースなのか。既存の audio シーケンスと同じ語彙で扱えるのが望ましい
- **保存先とプロジェクト**。録音は消えては困るので、#456 の import / プロジェクト概念と接続する
- **レイテンシと同期**。入力ストリームと出力ストリームの位相をどう合わせるか

**参照される DAW**: Ableton / Bitwig / Opcode Vision。Vision が挙がっているのは、
おそらく「録ったものをそのままシーケンスの素材として扱う」感覚を指している。

## 3. VST3 / CLAP のパラメータを DSL から動かす — **#680**（CC は不要と判明）

> あと VST3 や CLAP に cc を使って変更等ができるようにする必要があるよね。

### 調査の結論 — CC は要らない。API は既に通っている

owner の問い「VST3 とか CLAP ってパラメータを動かせる API 生えてるの？名前とかも取得できるの？」
への答えは **両方 yes**。しかも**このリポジトリに既に実装がある**。

| | 渡し方 | 実装箇所 |
|---|---|---|
| CLAP | process の**入力イベント** `ParamValueEvent::new(sample_offset, id, Pckn, value, cookie)` | `orbit-clap-host/src/effect.rs:239` |
| VST3 | `IParameterChanges` = パラメータごとの点列キュー `(sampleOffset, value)` | `orbit-vst3-host/src/lib.rs:2534`（`single_gain`） |

**両方サンプル精度。** いま 1 個だけ使っている機構を **N 個・任意 ID へ一般化**するのが実作業。

**メタ情報も取れる**:

- **CLAP `ParamInfo`**: `id` / `name`（"Volume"）/ `module`（"Oscillators/Wavetable 1" = `/` 区切りの階層）/
  **`min_value` / `max_value` / `default_value`（プレーン値）** / `flags`。
  ホスト API に `count()` / `get_info()` / `get_value()` / `value_to_text()` / `text_to_value()`
- **VST3 `ParameterInfo`**: `id` / `title` / `shortTitle` / `units`（"dB"）/ `stepCount` /
  `defaultNormalizedValue` / `unitId` / `flags`。`IEditController` に
  `getParameterCount` / `getParameterInfo` / `getParamStringByValue` / `getParamValueByString`

**CC を選ぶ理由が無い。** CC は受け側のマッピング次第で効くかどうかが決まるが、
パラメータは**契約として存在が保証**されていて、既に経路も通っている。

### 🔴 確定した決定 — DSL はプレーン値（案 B・owner 決定 2026-09-02）

VST3 の値は**正規化 0..1** で、**数値としての範囲は規格上取れない**（`units` は文字列、
`defaultNormalizedValue` はデフォルト値のみ）。CLAP はプレーン値で min/max を持つ。
この差を DSL に出さない（CAP.6-1）ための 2 案のうち **B を採用**。

| 案 | 内容 | 判定 |
|---|---|---|
| A | DSL を 0..1 に統一 | ❌ `gain(db: -6)` のような自然な書き方ができない |
| **B** | **DSL はプレーン値**。VST3 は `getParamValueByString("-6 dB")` で文字列→数値 | ✅ **採用**。確定済みの `gain(db: -10)`（SC.10）と同じ書き味 |

**B の弱点への対処**: 文字列の書式がプラグイン依存になる点は、`orbit-plugin-scan` の
カタログ作成時に `getParamStringByValue(0.0)` / `(1.0)` で両端を引いて**範囲を記録しておく**
ことで軽減する（既存のスキャン経路に相乗り）。

### 残る設計の論点

- **パラメータの指し方** — ID は数値なので人にも LLM にも書けない。**名前で指す**必要があり、
  #623（重複解決）や PC.2 の名前解決と**同じ問題**。CLAP の `module` が階層パスを持つので
  `"Oscillators/Wavetable 1/Volume"` のように曖昧さなく指せる
- **時間の粒度** — 両形式ともサンプルオフセットを持つので、**#674（OSC）や `midi()` と同じ
  「シーケンス上の位置」で指せる**はず。表面を揃える
- **DSL の表面** — #649 の「メソッドチェーンの順序が信号順」と衝突しない形にする

**副次的な効果**: 人間がつまみで動かした値は DSL に残らないという既知の非対称が、
パラメータを DSL から動かせるようになれば解消に向かう。

**関連**: #674（OSC・表面を揃える）、#623、#644、#672

## 4. 標準プラグインに Patina を検討（#669）

> 標準プラグインを用意する。https://github.com/ShmKnd/Patina を使うことを検討したい。

**事実確認**（2026-09-02）: `ShmKnd/Patina` は実在。**C++17 の標準ライブラリのみ**で書かれた
アナログモデリング DSP ライブラリ（BBD ディレイ、コンパンダ、トーン回路、真空管アンプ等）。
**JUCE も Boost も外部依存も無し**。**MIT**。

**相性**: 良い。OrbitScore は既に `orbit-std-gain` を **CLAP プラグインとして同梱**する経路を
持っている（#628 で通した）。Patina を CLAP でくるむのは、その経路にそのまま乗る。
依存が標準ライブラリだけなのでバンドルとライセンスの検討も軽い。

**#669 との関係**: #669 は「compressor / limiter / normalizer を標準 CLAP プラグインとして
作り直す」。Patina はまさにその中身の候補になる。

## 5. 専用シンセに unworklet — WASM ラッパーで載る（owner が正しかった）

> unworklet を採用して orbitscore に専用シンセを組み込む。標準エフェクターにも使えるのかも含めて
> レイテンシーなどの計測をして実用できるかどうか検討したい。12EDO 以外の音程とか初期にあった
> １５半音を十二分割する新しいドレミ、みたいなものを表現できるようになると平均率の別の拡張も
> できるので。前例はあると思うけどこの辺は要調査。midi で表現するのがかなり難しいので。
>
> ただ標準エフェクターなどは https://github.com/ShmKnd/Patina こっちの方がいいかも。
> unworklet はユーザーランドにエフェクターを解放するための仕組みにしておくといいかも。
> シンセもフィックスしちゃうなら Patina でいいかもなんけど、unworklet だと楽に更新できるという
> 良さがあるよね。この辺は比較したい。
>
> （main の「ホストが違う」という反論に対して）
> **unworklet は WASM を吐き出すことが出来るはずなのでラッパーを用意すれば良くないですか？**

### 🔴 main の当初の反論は誤りだった

main は当初「unworklet は AudioWorklet 前提なので Rust native daemon とはホストが違う。
WASM だけ借りても**リアルタイム安全性の保証は付いてこない**」と書いた。**これは誤り。**
README の説明文だけを読んで一般化しており、生成物を見ていなかった。

### 実際に確かめたこと（2026-09-02・`packages/core/src/compile/emit.ts`）

```
mod.setMemory(pages, pages, "memory", ...)   ← memory を export。initial == maximum（成長しない）
mod.addFunctionExport("process", "process")  ← export はこの 1 本
addFunctionImport                            ← リポジトリ全体で 0 件
```

**生成される WASM は何も import しない。** export は `process` 関数と線形メモリだけ。
ホストは instantiate して、メモリへ入力とパラメータを書き、`process` を呼び、出力を読むだけでよい。
**AudioWorklet も JS グルーも要らない。**

裏付け:

| 事実 | 出典 |
|---|---|
| ブラウザ限定ではない | README 冒頭 "for any audio thread: **browser, server, or microcontroller**" |
| ブラウザ非依存の実行経路が既にある | `@unworklet/offline` = "**pure JS over `WebAssembly.instantiate`**"（Node / Bun / Deno） |
| **RT 安全性は WASM 自体の性質** | "The compiler **proves** it's allocation-free, GC-free, and bounded **before it ever runs**" |
| トラップを出さない設計 | `emit.ts` の "no-trap invariant: integer conversion uses `trunc_s_sat`" |

RT 安全性が**コンパイル時に証明される**以上、その保証はホストを替えても失われない。
これが main の反論の中核だったので、反論はここで崩れている。

### 残る作業 — メモリレイアウトの受け渡し

入出力バッファ・パラメータ・state のオフセットは `packages/core/src/compile/layout.ts` が
**コンパイル時に**決め、`Layout` 型として JS 側のオブジェクトに乗る。Rust ホストはこれを
知らないと書き込み先が分からない。

**ビルド時に `Layout` を JSON で吐いて `.wasm` と対にする**のが実装作業の本体になる。
ラッパーのコードより、この受け渡しの契約を決める方が仕事。

実装上の注意:

- **instantiate は RT スレッドの外で行う**（JIT が走る）。RT では作り置きしたインスタンスの
  `process` を呼ぶだけにする
- **sample rate が焼き込まれる**（README: 48kHz で係数を焼く）。デバイスレートとの整合を決める
- 計測は owner の要望どおり必要（レイテンシ・1 ブロックあたりのコスト）。ただし**可否の判断ではなく
  実用域の確認**として行う

### unworklet と Patina は競合しない

| | 何か | OrbitScore での役割 |
|---|---|---|
| **unworklet** | DSP の**記述と実行系**（TypeScript → WASM・RT 安全性を証明） | **ユーザーランドに DSP を解放する**経路。更新が楽 |
| **Patina** | C++17 標準ライブラリのみの**DSP ライブラリ** | **同梱する標準プラグイン**の中身（#669） |

owner の整理（「unworklet はユーザーランドにエフェクターを解放するための仕組み、
標準エフェクターは Patina」）がそのまま成り立つ。**どちらかを選ぶ問題ではない。**

### 音律の動機

12EDO 以外・「15 半音を十二分割」を表現したいという要求は #497（シンセ DSL 構想）と同じ。
**MIDI では表現しにくい**ので自前シンセが要る、という筋は一貫している。前例の調査は未実施。

### #671 / #672 との関係

「ユーザーが書いた DSP をどう受け入れるか」は #671 / #672（DSL Plugin / DSP Plugin の契約）
そのもの。unworklet はその**実行系の有力候補**として具体性を与える。
決めるべきは「ユーザーが書いた DSP は、どのプロセスの、どのスレッドで走るのか」で、
unworklet を採るなら答えは「daemon の RT スレッドで、作り置きした WASM インスタンスとして」になる。

## 7. 出力チャンネルとスルー（#611）

> これもデバイスが使えるチャンネルは全て使えるようにしたいよね。あとどこにアウトを指すかは
> DSL で自由にしたらいいよね。ちなみに、オーディオ信号はスルーするしない、をつけると
> 複数のアウトを１つのオーディオラインに作ったり、エフェクトマーの音をアウトして
> エフェクト後の音もアウトしてみたいなことができるようになるよね。

**#611（ミキサーの出力側）に直結**。3 つの要求が入っている:

1. **デバイスが持つ全チャンネルを使えるようにする**（現在 8ch @ 2048 で instrument が無音になる問題あり）
2. **アウトの位置を DSL で自由に指せる**
3. 🔴 **「スルーする / しない」** — これが新しい。信号をそこで**分岐させて先へも流す**か、
   **そこで出して終わりにする**かを選べると、**エフェクト前とエフェクト後の両方を出せる**

3 は send / insert の区別を、専用の語ではなく**オーディオライン上の 1 要素の属性**として
表現する案になっている。#649 の「フェーダーという段は作らない・順序がモデル」と同じ思想。
